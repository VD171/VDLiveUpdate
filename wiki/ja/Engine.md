# Engine

エンジンは VDLU の端末側です。スマートフォン上で動作し、何が変わったかを判断し、それをダウンロードして適用する部分です。これは単一の POSIX シェルスクリプト `engine/update.sh` と、小さな署名チェッカー `engine/vdlu-verify` から成ります。どちらもホストモジュールの `<module>/vdlu/` にベンダリングされ、root によって実行されます。

エンジン全体は一つの考え方を中心に組み立てられています。すなわち、更新は**再開可能なトランザクション**であるということです。スマートフォンが途中で再起動されても、強制終了されても、ネットワークを失っても、次回の実行は止まったまさにその地点から引き継ぎ、モジュールが完了を装いながら半適用のまま放置されることは決してありません。

まず全体像が欲しい場合は [[Architecture]] を参照してください。可能な限り更新がどう再起動を避けるかについては [[Reboot Handling]] を参照してください。

## ノートパソコンではなく端末のために書かれている

`update.sh` は純粋な POSIX `sh` です。mksh、busybox、toybox の下で動作し、bash 固有の機能は使わず、`sh -n` を通過します。これは、root 化された Android 端末の環境が小さく厳格だからこそ重要です。

特に `jq` はありません。VDLU は `manifest.json` を、`awk` で書かれた小さな gron スタイルのフラット化処理で解析します。JSON を一文字ずつ辿り、葉ごとに一行の `path<TAB>value` を出力します(例えば `files/0/sha256<TAB>ab..` や `version<TAB>6`)。シェルはその行を `grep` と `cut` で読みます。これはコンパクトな JSON にも整形された JSON にも効き、存在しない JSON ツールにシェルアウトすることは決してありません。

エンジンが依存するのは、toybox がすでに同梱しているもの(`sha256sum`、`gzip`/`gunzip`、`base64`、`date`)、組み込みの `ed25519-mini` 検証器、そして `https://` フィードの場合には一度だけ取得・検証される小さな静的 `curl` だけです。`file://` フィードには `curl` はまったく不要です。

## 六つのコマンド

モジュールのパスを環境変数に設定し、一つのコマンドでエンジンを呼び出します:

```sh
VDLU_DIR=/data/adb/<mod>/vdlu MODULE_DIR=/data/adb/modules/<mod> MODID=<mod> \
  sh "$MODULE_DIR/vdlu/update.sh" <cmd>
```

終了コード `0` は成功を意味します。それ以外のコードはエラーを意味し、理由が stderr に出力されます。

| コマンド | 機能 |
|---|---|
| `check` | 読み取り専用の差分。マニフェストをダウンロードし、インストール済みのものと比較し、一行の JSON 要約を出力します: `{"update":bool,"from":N,"to":M,"fetch":K,"reboot":bool}`。ディスク上の何も変更しません。端末がフィードより新しい場合(ブロックされたダウングレード)、エラーではなく `{"update":false,"ahead":true,...}` を終了コード `0` で報告します。 |
| `run` | ライブの完全サイクル: DIFF、FETCH、APPLY、COMMIT。すべてのライブファイルを即座に適用し、わずかな再起動クラスのファイルをステージングします。`cancel` を尊重します。進捗を `journal.json` に書き込みます。 |
| `resume` | 中断されたトランザクションを、その時いたフェーズから続行します。冪等です。ステージングされた `.so` の入れ替えは**行いません**(それは `boot` に予約されています)。 |
| `boot` | プリzygote のパス。`resume` を行い、その後ステージングされた `*.vdlu-new` ファイルを所定の位置に入れ替え、`PENDING_REBOOT` を `DONE` に閉じます。保留中のトランザクションがなければ、新しいサイクルを実行し、その一度のブートで `.so` を含むすべてを適用します。 |
| `status` | `journal.json` を出力します。進行中のものがなければ `{"state":"idle"}` を出力します。 |
| `cancel` | `cancel` マーカーを作成します。進行中の `run` は次の安全なポイントでクリーンに停止します。 |

`check` コマンドはあえて軽量に作られており、どんなネットワーク上でも UI が更新の存在を知らせられるようになっています。実際のダウンロードは別に制御されます(下記の fetch フェーズを参照)。

## トランザクション、ステップごと

すべての `run` は固定の状態機械を通過し、WebUI(とあなた)が見守れるよう `journal.json` に記録されます:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> (PENDING_REBOOT | DONE)
```

**DIFF。** エンジンは `manifest.json` を取得し、すべてのフィールドを検証し(下記および [[Security and Trust Model]] を参照)、署名付きのターゲットツリーを、すでにインストールされているバージョンのマニフェストである `current.json` と差分比較します。結果は `plan.tsv` に書き込まれるファイルごとのプランで、一行につき一ファイル、そのクラス、ターゲットハッシュ、mode、進捗状態を運びます。すでにターゲットハッシュと一致しているファイルはスキップ対象としてマークされます。

**FETCH。** まだ必要な各ファイルについて、エンジンはそのコンテンツアドレス方式の blob を `<source>/blobs/<sha>`(圧縮時は `<sha>.gz`)から `.part` ファイルへダウンロードします。blob が gzip されていれば展開し、その後その SHA-256 をマニフェストと照合します。一致した場合にのみ、`blobs/<sha>` へアトミックに `mv` します。正しいハッシュですでにキャッシュされている blob は完全にスキップされ、変更のないローカルファイルはダウンロードなしでキャッシュに種まきできます。同一 blob での 3 回の失敗で、何も適用せずにこのフェーズを中止します。このフェーズは、プラン内のすべての blob が存在し検証された場合にのみ `FETCHED` に到達します。これらの blob が由来する [[Feed Format]] については、そのページを参照してください。ツールチェーンのセットアップ時に、エンジンは解決された TLS 信頼 - CA パスとそれが読めるかどうか、加えてバンドルのサイズと証明書数 - をログに記録するため、boot 時の curl `rc 77` は `boot.log` で自己説明的になります (空の信頼ストアと読めないストア、すなわち boot の SELinux コンテキストのケースを区別します)。

fetch はネットワークポリシーによって制御されます。フィードは Wi-Fi のみ、モバイルのみ、または任意のネットワークに制限できます。現在のネットワークが許可されていない場合、fetch は失敗しません。無害な `DEFERRED` 状態に入り、プランとターゲットを固定したまま保持し、適切なネットワークが現れた次の check またはブートで再開します。その間データを消費することはありません。

**APPLY。** `FETCHED` からのみ入ります。各ファイルについて、エンジンはクラスごとに動作します:

- `live` および `soft` ファイル: 現在のファイルを `rollback/<version>/<path>` へバックアップし、新しい内容を兄弟の `.vdlu-tmp` に書き込み、`chmod` し、ハッシュを検証し、ターゲットの上へアトミックに `rename` します。すでにターゲットハッシュと一致しているファイルはスキップされます。
- `reboot` ファイル(`.so`、`/system` オーバーレイ、`sepolicy.rule`): `staged/<path>.vdlu-new` へ具現化します。ここでライブの inode には決して触れません。[[Reboot Handling]] を参照してください。
- 削除: バックアップしてから削除します。削除は、再起動が保留中の間ではなく、クリーンな `DONE` の最後にのみ適用されます。

**COMMIT。** エンジンは触れたすべての live および soft ファイルを再ハッシュします。それらすべてが一致した場合にのみ `current.json` を書き込み、新しいバージョンを差分の基準にします。再起動クラスのファイルがステージングされていた場合、状態は `DONE` ではなく `PENDING_REBOOT` になります。入れ替えと最終的な再検証は後で `boot` コマンドの下で行われます。

## 設計によるフェイルセーフ

無人で実行しても安全にする保証:

- **一致する再ハッシュなしに `DONE` とマークされることはない。** `DONE` には、適用された各ファイルが読み戻され、その SHA-256 がマニフェストと比較された後にのみ到達します。ステージングされた再起動ファイルは `PENDING_REBOOT` を強制し、偽の `DONE` にはなりません。
- **何も失われない。** すべてのファイルは上書きされる前に `rollback/<version>/` へバックアップされ、直近 3 バージョンが保持されます。適用が失敗すれば、ライブファイルはバックアップから復元されます。モジュールが半適用のまま、それを偽ることは決してありません。`apply_live` は、バックアップのステップが失敗した場合、戻る術もなく上書きする代わりに即座に中止します。
- **すべてがアトミック。** 新しい内容はターゲットの上への `rename`/`mv` を経て配置されるため、読み手は常に古いファイルか新しいファイルのいずれかを見ることになり、切り詰められた書き込みを見ることは決してありません。
- **クラッシュや強制終了の後も再開可能。** 途中でのクラッシュ、ネットワーク喪失、再起動は有効なジャーナルを残し、`resume`(または `boot`)が記録されたフェーズから続行します。設計は中断されることを前提としています。
- **きれいに縮退する。** バイナリの欠如、ネットワーク断、ディスク満杯は、モジュールを破損させることなく、stderr に明確なエラーを、ジャーナルに `state:ERROR` を生じます。
- **信頼アンカーは除外されます (`ENGINE_VERSION` 5)。** エンジンは取得されたプランのすべての `vdlu/` パス - 自身の `update.sh`、`vdlu-verify`、`verify/` バイナリ、キーリング、そして設定 - を無視するため、フィードが回線越しに検証器や署名鍵をすり替えることは決してできません。アンカーはフルの署名付き再フラッシュによってのみ変わります。[[Security and Trust Model]] を参照してください。
- **モジュールがビジーの間、更新は延期されます。** オプトインの `apply_busy_file` を、ホストモジュールが自身の操作中に touch する絶対パス (例えば実行中のバックアップ) に設定すると、そのパスが存在する間 APPLY は待機するため、ファイルが操作の途中ですり替えられることは決してありません。blob は既に取得済みなので、次のトリガーは再ダウンロードなしに適用します。
- **サイズ上限。** ファイルは **128 MiB** に、マニフェストは **2 MiB** に制限され、`update.sh` と `vdlu-verify` の両方でどちらも読み込まれる前に強制されます (anti 展開爆弾 / anti-OOM)。
- **フィードより先行しているモジュールは決して戻されない (`ENGINE_VERSION` 7)。** モジュール自身の `module.prop` から読み取ったライブのインストール済み `versionCode` が "from" バージョンの下限となるため、古いフィードを超えて手動で更新された端末は *先行* として読まれ、ダウングレードガードは無害を返し、プランもロールバックもない。`boot` は既存のインストールも自己修復する - target がインストール済みバージョンより下の永続化されたプラン、または `target <= 0` の古いジャーナル (`ENGINE_VERSION` 6) は、いかなる resume の前にもクリアされる。

## ロック

状態に触れられるトランザクションは一度に一つだけです。toybox では `flock` が信頼できないため、VDLU はディレクトリロックで直列化します。`mkdir "$VDLU_DIR/lock.d"` は正確に一人の呼び出し元に対して成功し、残りに対しては失敗します。これはまともなファイルシステムであればアトミックです。死んだプロセスが残した古いロックは、記録された PID を確認することで回収されます。

辛抱強いブート時リトライ(端末がブート時にオフラインの場合に使われる)は、待っている間このロックを**保持しません**。試行の間に取得と解放を行うため、ネットワークを待っているブートによって手動の `run` がブロックされることは決してなく、ウェイクロックを保持することもありません。設計上バッテリーに優しいのです。詳細は [[Reboot Handling]] にあります。

## 署名チェック: `vdlu-verify`

`vdlu-verify` は端末上の署名チェッカーで、あえて軽量に保たれています:

```
vdlu-verify <manifest.json> <keyring_dir>
```

終了コード `0` は、マニフェストの署名が、マニフェストの `key_id` と一致する id を持つキーリングの公開鍵に対して有効であることを意味します。それ以外のコードは拒否です。

これを軽量にしているのは、**端末上で `openssl` を使わない**ことです。キーリングの公開鍵を**生の 32 バイト**ファイルとして読み、マニフェストを正準化し(`sig` フィールドを取り除いたマニフェストのテキスト)、toybox の `sha256sum` でハッシュ化し、署名を base64 デコードし、生の鍵、メッセージ、64 バイトの署名を組み込みの `ed25519-mini` バイナリに渡します。このチェッカーは、検証を行う前にも不正なものを拒否します。欠落または空の `key_id` または `sig`、パス区切りを含む `key_id`、正確に 32 バイトでない公開鍵、正確に 64 バイトでない署名などです。

鍵を選ぶより前に、エンジンは**`key_id` 許可リスト**を強制します。マニフェストの `key_id` は、設定が*モジュール更新*への署名を許している鍵でなければならず、キーリングに単に存在するだけで許可リストにない鍵は、その公開鍵が読み込まれる前に拒否されます。単一鍵のキーリングは設定なしでその一つの鍵を自動的に固定し、複数鍵のキーリングは `key_id` を固定しなければ、さもなければエンジンはフェイルクローズドします。許可された集合は `VDLU_KEYID_ALLOW` として `vdlu-verify` に渡され、両方のプロファイルで適用されます。これにより、キーリングを共有するフィンガープリントフィード鍵のような、より低信頼の鍵が完全な root 更新に署名することを止めます。別個のフィンガープリントフィードは独自の固定された鍵 `FEED_KEY_ID` を保ちます。完全な物語は [[Security and Trust Model]] にあります。

正準化は producer の署名器とバイト単位で同一であり、これこそが署名をツール間で検証できるようにしているものです。対応する秘密鍵が端末や CI に触れることは決してなく、埋め込まれるのは生の公開鍵だけです。完全な信頼の物語、二つのプロファイル、そして `hardened` がなぜ反転によってフェイルクローズドなのかは [[Security and Trust Model]] にあります。

エンジンは diff フェーズの間に `vdlu-verify` を呼び出します。`hardened` プロファイルの下では検証の失敗が更新全体を中止させます。`trusted` の下では検証はベストエフォートですが、すべての blob のハッシュは依然として常にチェックされるため、プロファイルに関わらず破損した内容は捕捉されます。

## ディスク上の状態

エンジンのすべての状態は `$VDLU_DIR`(モジュールディレクトリの外)に存在するため、モジュールツリー自体は常に完成したファイルだけを保持します:

| パス | 役割 |
|---|---|
| `config` | key=value の設定(source、profile、channel、ネットワークポリシー、ブートリトライ) |
| `current.json` | アクティブなバージョンのマニフェスト。これが差分の基準。存在しない場合は一度も更新していないことを意味する |
| `target.json` | 進行中トランザクションの固定されたマニフェスト。その存在がアクティブなトランザクションを示す。`DONE` で `current.json` になる |
| `plan.tsv` / `plan.del` | ファイルごとのプランと進捗、および削除するパスのリスト |
| `journal.json` | WebUI 向けの進捗。状態が変わるたびに書き換えられる |
| `blobs/<sha256>` | 検証済みで展開された原本内容のキャッシュ |
| `rollback/<version>/<path>` | 上書きされたファイルのバックアップ。直近 3 バージョンが保持される |
| `staged/<path>.vdlu-new` | ブート時の入れ替えを待つ再起動クラスのファイル |
| `lock.d/` | mkdir ロック |
| `tools/<abi>/curl` | 取得・検証された静的 curl。更新をまたいで永続する |
| `cancel` | キャンセル要求 |

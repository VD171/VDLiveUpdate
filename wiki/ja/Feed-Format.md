# Feed Format

**フィード**は VDLU が回線越しに提供するものであり、端末が更新元にするものです。これはプレーンな静的ディレクトリで、あらゆるもの(GitHub Pages、rsync のターゲット、`file://` パス)で提供できます:

```
<source>/
  manifest.json          # the signed description of the current release
  blobs/<sha256>         # one blob per distinct file content
  blobs/<sha256>.gz      # (when the blob is stored gzipped)
```

モジュール自体はさらに一つのファイル、`baseline.json` を `.zip` の内側に同梱します(フィードからは提供されません)。これらすべてをビルドする producer は [[Producer]] で説明されています。このページは回線上の契約です。

---

## manifest.json

マニフェストは一つのリリースの完全な記述です。ターゲットツリー内のすべてのファイル、何を削除するか、そして全体に対する署名です。

```json
{
  "schema": 1,
  "module": "demo",
  "version": 106,
  "version_name": "v106",
  "built": "2026-11-19T12:00:00Z",
  "engine_min": 3,
  "channel": "stable",
  "key_id": "release-2026",
  "files": [
    {
      "path": "webroot/index.html",
      "sha256": "<hex64>",
      "size": 1234,
      "mode": "0644",
      "enc": "raw",
      "class": "live"
    }
  ],
  "delete": ["webroot/old.html"],
  "sig": "<base64>"
}
```

### フィールド

| フィールド | 意味 |
|---|---|
| `schema` | マニフェスト自体のフォーマットバージョン(現在は `1`)。 |
| `module` | モジュール id。端末は自身のモジュール id と一致しなければマニフェストを拒否するので、別のモジュール用に正当に署名されたフィードをすり替えて提供することはできない。 |
| `version` | 整数バージョン。エンジンは前方にのみ更新する。端末より古いフィードは、エラーではなく無害な「ahead」状態。 |
| `version_name` | 人間が読めるバージョン文字列(例えば `v106`)。 |
| `built` | ISO 8601 のビルドタイムスタンプ。再現性のために `SOURCE_DATE_EPOCH` を尊重する。 |
| `engine_min` | このマニフェストを適用するのに必要な最小エンジンバージョン。 |
| `channel` | リリースチャンネル(例えば `stable`)。 |
| `key_id` | 端末キーリングのどの鍵がこのマニフェストに署名したか。検証用の公開鍵を選択し、エンジンのモジュール更新許可リストに含まれていなければならない([[Security and Trust Model]] を参照)。キーリングに単に存在するだけで許可リストにない鍵は、その公開鍵が読み込まれる前に拒否される。 |
| `files[]` | **完全な**ターゲットツリー(差分ではない)。各エントリ: `path`、`sha256`、`size`、`mode`、`enc`(`raw`/`gz`)、`class`(`live`/`soft`/`reboot`)。 |
| `delete[]` | 前のリリースには存在したが今はなくなったパスで、端末が削除する。 |
| `sig` | ed25519 署名、base64。下記の正準化を参照。 |

`files[]` は**ツリー全体**を記述し、差分ではありません。端末は、マニフェストをすでに持っているものと比較することで差分自体を計算し、`sha256` が不足している blob だけを取得します。`sha256` は常に原本(非圧縮)内容のものです。`enc` は、その blob が `blobs/` にどう保存されているかを示すにすぎません。`class` の意味と端末が各値で行うことは [[Reboot Handling]] で扱います。

## Canonicalization(署名対象バイト列)

これはこの形式で最も重要な不変条件です。PC の署名器と端末上の検証器は、まったく異なるランタイムで動作します(PC 上の openssl、端末上の toybox + 小さな組み込み検証器、そして端末上には **JSON ライブラリがまったくない**)。それでも両者は、署名と検証のために正確に同じバイト列を導出しなければなりません。したがってルールは、JSON の再シリアライズではなく、意図的な**バイト変換**です。

**ステップ 1: 固定された格納形式。** `vdlu-pack` は `manifest.json` を、キーをソートし、UTF-8 で、常に `key_id` と `sig` を含めて(署名されるまでは空文字列として)、コンパクトに書きます:

```
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

**ステップ 2: `sig` だけを取り除く。** 正準形はその正確なテキストから **`"sig"` フィールドだけを取り除いた**ものです。キーがソートされているため、`sig` は常に `,"sig":"<value>",` として現れ、その前に `"schema"`、その後に `"version"`(どちらも常に存在)で挟まれているので、それを取り除いても整形式のテキストが残ります。JSON は文字列値内のすべての `"` を `\"` としてエスケープするので、構造トークン `"sig":"` は、`"sig":"` を文字通り含むファイル名に対しても曖昧になりません。

取り除きは、`sed` も `jq` も使わない、署名器と検証器で同一のわずかな POSIX パラメータ展開です:

```sh
# $1 = the full manifest text
_pre=${_c%%\"sig\":\"*}     # up to  ...,"schema":N,
_rest=${_c#*\"sig\":\"}      # after "sig":"
_tail=${_rest#*\",}          # after <value>",  ->  "version":...
printf '%s%s' "$_pre" "$_tail" | sha256sum | cut -d' ' -f1
```

**ステップ 3: そのハッシュに署名する。** 署名/検証されるメッセージは、正準形の **sha256 の 16 進**(64 ASCII 文字、改行なし)です。ed25519 はその 16 進に署名します。

この構造から二つの帰結が導かれます:

- `key_id` は正準形の一部です(取り除かれるのは `sig` だけ)。`vdlu-sign` はハッシュ化の**前に** `key_id` を設定するので、鍵の同一性は署名によってカバーされます。
- `sig` プレースホルダーが空(署名時の `"sig":""`)であれ埋まっている(検証時)であれ、それを取り除くと同一の正準バイト列が得られます。署名と検証は自動的に一致します。

二つの POSIX sh ツールが権威です。Python の等価物、`re.sub(r'"sig":"[^"]*",', '', text, count=1)` の後に sha256 するものは、それらを相互チェックするためだけに存在します。

これらすべてをめぐる信頼の推論(なぜ検証が端末上なのか、どのように `hardened` がフェイルクローズドするか)は [[Security and Trust Model]] にあります。

## baseline.json(インストールシード)

モジュールが新しくインストールされたとき、それは自身の配布バージョンについてすでに「current」であるべきで、たった今インストールしたバージョンを無駄に自己更新すべきではありません。それが `baseline.json` の役割です。

`baseline.json` は(フィード上ではなく)**モジュールの zip の内側**(`vdlu/baseline.json`)に同梱されます。新規インストール時、エンジンはそれから「アクティブバージョン」の記録を種まきするので、端末は `from:0` なしに、すでに持っているものの再取得なしに、current として誕生します。

主要な性質:

- これは配布バージョンのための**署名付きマニフェストの鍵なしコピー**です。同じ `vdlu-pack` の出力を未署名のまま(`key_id` と `sig` は空のまま)にしたものです。
- これは**検証されません**。エンジンはこれをローカルの信頼されたシードとして扱います。フラッシュされた zip の内側で届いたからであり、それがインストールの信頼境界です。*フィードから取得された*マニフェストだけが署名の検証を通過します。
- 署名を必要としないため、**CI が鍵なしで生成できます**。これが署名鍵を完全に CI の外に保つものです([[Producer]] を参照)。
- `vdlu-pack` は**自身のマニフェストから `baseline.json` を除外**するので、マニフェストがベースラインを参照することは決してありません(それは自己参照ループになります。マニフェストからベースライン、ベースラインからマニフェスト)。
- これは**なくても致命的ではありません**。それがなければ、端末は単に初回更新時に `from:0` から始め、必要なものを取得します。壊れることはなく、ただ最適でないだけです。

## Blobs

異なるファイル内容ごとに一つの blob が `blobs/` の下にあり、**原本内容の sha256** によって名付けられます:

- 生の blob には `blobs/<sha256>`。
- gzip された blob には `blobs/<sha256>.gz`(gzip はファイルが少なくとも 4096 バイトで圧縮が少なくとも 10 パーセントを節約するときにのみ保たれます)。

blob は一度、一つの形式で保存されます。コンテンツアドレッシングは重複排除を無料で提供します。変更のない、共有された、または元に戻された内容は、すでに存在する blob にマッピングされるので、フィードは本当に新しい内容だけで成長し、端末は不足しているハッシュだけをダウンロードします。端末は、使用する前に、ダウンロードされたすべての blob の `sha256` を(`gz` blob を展開した後に)マニフェストと照合します。

## フィードから除外されるもの、そしてその理由

フィードは**モジュール自身の内容だけ**を運びます。固定された一連のパスが意図的に外に置かれます。`vdlu-pack` は、ツリーを辿るときと `delete[]` を計算するときの両方で、一つの除外述語を適用します。

| 除外対象 | 理由 |
|---|---|
| `vdlu/keyring/`、`vdlu/verify/`(トラストルート: 生の公開鍵 + 検証器バイナリ) | **これが核心となるセキュリティ上の理由です。** トラストアンカーは**フラッシュ時のみ**です。キーリングや検証器がフィード配布可能であれば、マニフェストがそれを検証するまさにそのものを上書きできてしまいます。それらを回線から外しておくことで、マニフェストが端末上のトラストアンカーを書き換えることは決してできなくなります。 |
| `vdlu/baseline.json` | これは署名付きマニフェストのコピー(インストールシード)であり、それをパッキングすると自己参照ループになる。 |
| `.vd/` フラッシュインフラ | zip に同梱されるフラッシュゲートのスキャフォールディングで、ライブで適用されることはない。 |
| `update.json`、`update-mmrl.json` | それらの size/sha は zip がビルドされた*後*に CI によって埋められるので、配布されるコピーはどのフィードコピーとも異なる。それらをフィードに入れると、すべてのインストールの初回自己更新でファントムの単一ファイル取得を引き起こし、しかも端末上では痕跡的である(マネージャーはリモートの生の update JSON を読む)。 |
| `META-INF/`、`customize.sh`(インストーラのスキャフォールディング) | **フラッシュ**時にマネージャーによって消費され、インストール済みモジュールには保持されない。これらは VDLU の内容ではない。提供すれば blob を浪費し、バージョン間で変わった場合にはインストーラファイルとしてライブのモジュールディレクトリに書き込まれてしまう。 |
| ファイルごとの `.sha256` 伴奏ファイル | これらはフラッシュ可能な zip だけに属し、増分更新の後に陳腐化し、マニフェストを倍増させる。 |
| 開発/ドキュメントファイル(`RELEASE.md`、`CLAUDE.md`、`.gitignore`) | 端末に配布されることはない。提供すれば blob を浪費し、ドキュメント編集のたびに署名付きマニフェストを churn させる。 |

トラストルート除外の背後にある推論は [[Security and Trust Model]] で展開されています。

## delete[] の意味論

`delete[]` は端末にどのパスを削除するかを伝えるもので、リリース間で落とされたファイルが端末上に孤立物として残らないようにします。これは `vdlu-pack` に `--prev <previous manifest.json>` を渡すことで計算されます。前のリリースにあって現在のものにないパスが、削除エントリになります。

重要なルール: **除外されたパスは、`--prev` があっても決して削除として出力されません。** すべての前のパスは、ツリーを辿るときに使われるのと同じ除外述語を通されます。`--prev` が、今は除外されているパス(紛れ込んだ `baseline.json`、`META-INF/*`、キーリングエントリなど)を依然として列挙していた古いマニフェストを指している場合、それらのパスは削除エントリに**変わりません**。除外されたパスはフィードの内容であったことがないので、VDLU が削除すべきものではなく、フィードを通じて提供されなかったファイルの削除を端末が命じられることは決してありません。これが、除外リストが破壊的な命令として跳ね返ってくるのを防ぐものです。

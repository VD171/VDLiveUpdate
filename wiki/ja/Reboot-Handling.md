# Reboot Handling

VDLU の核心は、モジュールを再フラッシュせずに、そして可能な限り一切再起動せずに更新することです。モジュール内のほとんどのファイルは、端末が動作している間に置き換えられます。少数のファイルは本当にそれができません。カーネルまたは zygote プロセスがすでにそれらをマップしており、次回のブートまで変更に気づかないからです。

VDLU の仕事は、その二つのグループを自動的に見分け、安全に行えるすべてを**ライブで**適用し、本当にブートに束縛されたファイルだけを、明確にフラグする再起動へと遅延させることです。このページはその方法を説明します。

この下にあるエンジンの仕組みについては [[Engine]] を参照してください。全体像については [[Architecture]] を参照してください。

## なぜ毎回再起動しないのか

再起動は、更新が誰かに求められる最も高価なものです。相手が行っていることを中断させ、1 分以上かかり、人々に更新を恐れるよう仕向けます。良い増分更新ツールは目に見えないように感じられるべきです。更新をタップすると、動作中のシステムの下でいくつかのファイルが変わり、あなたはもう新しいバージョンにいます。

そこで VDLU は通常の前提を反転させます。デフォルトはライブです。ファイルが再起動へ遅延されるのは、それがカーネルまたは zygote に束縛された種類の一つであると証明可能なときだけであり、そのときでさえ待つのはそのファイルだけです。その周りのすべては依然として即座に更新されます。

## 三つのクラス

フィード内のすべてのファイルにクラスが割り当てられます。producer はマニフェストで明示的に設定できますが、実際にはクラスはパスから導出され、エンジンはファイルを `reboot` の方向へ引き上げることはあっても、`live` の方向へ引き下げることは決してありません。クラスは以下の通りです:

**LIVE** が一般的なケースです。Web UI のアセット、バイナリ、オンデマンドで読まれるスクリプト、設定ファイル、`module.prop`、そして下記のルールに一致しないその他すべてです。ライブファイルはバックアップされ、システムが動作している間にターゲットの上へアトミックに rename されます。再起動はなく、rename が着地した瞬間に変更が有効になります。

**SOFT** はモジュール自身のライフサイクルスクリプトです。`service.sh`、`post-fs-data.sh`、`boot-completed.sh`。これらは LIVE ファイルとまったく同じようにライブで適用されるので、新しいコピーはすでにディスク上にあります。これらが独自のクラスを得る理由は、動作中のシステムが今回のブートですでに古いコピーを実行してしまっているからです。新しいコピーは、ステージングもバナーもなしに、単に次回のブートで実行されます。遅延すべきものは何もなく、自然な引き継ぎがあるだけです。

**REBOOT-hard** は、動作中のシステムの下では変えられない小さな集合です:

- ネイティブライブラリ、`*.so`(`zygisk/` パスの下にあるもの)。zygote が起動時にそれらをすべてのアプリにマップするため。
- `/system` オーバーレイファイル。オーバーレイはブート時にマウントされるため。
- `sepolicy.rule` ファイル。SELinux ポリシーは早期に読み込まれるため。

REBOOT-hard ファイルは、システムが起動している間にそのライブの inode の上に書き込まれることは決してありません。zygote がすでにマップした `.so` を上書きすることが、クラッシュと不整合な状態を招く原因です。代わりに新しい内容は状態ディレクトリの隣に**ステージングされ**、次回のブート時、何かがそれをマップできるより前に入れ替えられます。

## パスからクラスへ、一目で

エンジンは次のようにパスからクラスを導出します:

| パスパターン | クラス | 適用 |
|---|---|---|
| `zygisk/**`、`**/zygisk/**`(`.so` ファイル) | REBOOT-hard | ステージングされ、ブート時にプリzygote で入れ替えられる |
| `system/**`(オーバーレイ) | REBOOT-hard | ステージングされ、ブート時に入れ替えられる |
| `*.rule`(sepolicy) | REBOOT-hard | ステージングされ、ブート時に入れ替えられる |
| `service.sh`、`post-fs-data.sh`、`boot-completed.sh` | SOFT | ライブで書き込まれ、次回ブート時に実行される |
| `webroot/**`、`bin/**`、`lib/**`、各種設定、`module.prop`、その他すべて | LIVE | ライブで書き込まれ、即座に有効 |

マニフェストはファイルごとに明示的な `class` を運べますが、導出されたクラスが下限として機能します。ファイルがそのパスから REBOOT-hard に見えるなら、マニフェストが別のことを言っていても REBOOT-hard として扱われます。これにより、ラベル付けを誤ったフィードが `.so` のホットスワップを試みることが決してないようにします。

## 一度の実行が両グループをどう扱うか

通常の `run`([[Engine]] で説明された DIFF から FETCH、APPLY、COMMIT のサイクル)の間、二つのグループは同じトランザクションで扱われます:

```
run:
  LIVE + SOFT  --> backup -> write .vdlu-tmp -> verify -> atomic rename   (effective now)
  REBOOT-hard  --> materialize into staged/<path>.vdlu-new                (live inode untouched)

  re-hash every LIVE + SOFT file
       |
       +-- nothing staged  --> DONE
       +-- something staged --> PENDING_REBOOT  (reboot banner in the WebUI)
```

したがって `.so` に触れた実行の後、あなたはすでにすべてのライブファイルについて新しいバージョンにいて、ステージングされた部分だけが待っています。ジャーナルは `reboot_pending` を報告し、WebUI はステージングされたファイルを有効化するための再起動を促す永続的なバナーを表示します。偽の「done」はありません。ステージングされたファイルを持つ実行は `DONE` ではなく `PENDING_REBOOT` で終わります。

## ブート時の入れ替え

ステージングされたファイルは `boot` コマンドによって適用されます。ホストモジュールはこれを `post-fs-data.sh` に組み込むので、同期的に、そして**プリzygote** で、どのプロセスも新しい `.so` をマップできるより前に実行されます。

`boot` は `resume`(中断されたフェーズを完了させるため)を行い、その後入れ替えを行います。ステージングされた各 REBOOT-hard ファイルについて:

1. ステージングされたパスがモジュールディレクトリの内側に留まることを確認する(封じ込めチェック);
2. `staged/<path>.vdlu-new` をマニフェストのハッシュに対して再ハッシュする;
3. 現在のライブファイルをバックアップする;
4. ステージングされたファイルをライブのものの上へ `mv -f` し、それを `chmod` する;
5. 今所定の位置にあるファイルを再ハッシュし、入れ替えが正しく着地したことを確認する;
6. 適用済みとマークする。

ステージングされたすべてのファイルが入れ替えられ再検証された後にのみ、トランザクションは `PENDING_REBOOT` から `DONE` へ閉じます。いずれかのステップが失敗した場合、ジャーナルはエラーを記録し、モジュールは以前のファイルを保ちます。半分だけ入れ替わった状態で残されるものは何もありません。

入れ替えは一連の再ハッシュとアトミックな rename であるため、前回中断されていても `boot` の実行は安全です。単にステージングされたファイルを拾い直すだけです。

## auto_on_reboot

ステージングは再起動不要な感覚の半分にすぎません。もう半分は、ユーザーが入れ替えの実行を覚えておく必要が決してないべきだということです。config に `auto_on_reboot=1` があると、ホストモジュールの `post-fs-data.sh` が毎回のブートで `update.sh boot` を呼び出します。つまり:

- トランザクションが再起動を保留している場合、ステージングされたファイルは zygote が起動する前に自動的に入れ替えられ、ユーザーは単に完全に新しいバージョンにいる自分を見出します;
- 保留中のものがなければ、`boot` は新しいサイクルを実行し、すでにプリzygote で動作しているので、その一度のブートで `.so` を含むすべてを適用できます。

言い換えれば、ステージングされた `.so` が、どのみちするつもりだった再起動を超えてユーザーに負わせるコストはありません。二度目に何かをタップする必要はないのです。

## ブート時オフライン、バッテリーを消耗させずに

ときには `boot` がフィードをチェックしたいのに端末にまだネットワークがないことがあります。VDLU は `boot_retry_minutes`(0 でオフ)によって制御され、辛抱強く、そして安価にそれを待てます。待機は意図的にバッテリーに優しくなっています:

- 試行の間、単に `sleep` するだけで、これは深いスリープ中に凍結するので、端末は通常通りスリープし、リトライは端末がすでに起きている時にのみ再開します;
- ウェイクロックを保持せず、待っている間エンジンのロックも保持しないので、手動の実行がブロックされることは決してありません;
- 各試行の前に、パケットを送らず無線機を起こさないカーネルのルートルックアップで、ネットワークが許可されているかどうかをチェックします;
- 不正な署名やブロックされたダウングレードのような決定論的な失敗を決してリトライせず、本当のネットワーク不在の条件だけをリトライします。

マニフェストのチェック自体はどんなネットワークでも無料のままなので、あなたは常に更新の存在を知ります。ダウンロードだけがネットワークポリシーが満たされるのを待ち、エラーを出す代わりにきれいに遅延します。

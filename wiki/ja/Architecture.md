# Architecture

VDLU は、中央にある一つのものでつながれた二つの側面を持ちます。PC 側では、[[Producer]] がモジュールツリーを署名付きのコンテンツアドレス方式のフィードに変換します。端末側では、[[Engine]] がそのフィードを読み、何が変わったかを判断して適用します。両者をつなぐ継ぎ目は、**署名付きマニフェストと blob ストア**([[Feed Format]])です。それ以外のものがこの境界を越えることはありません。

```
        PC / release host                                device
  +--------------------------+                 +---------------------------+
  |  Producer                |                 |  Engine  (update.sh)      |
  |  vdlu-pack  -> manifest  |    signed       |  POSIX sh, no jq          |
  |  vdlu-sign  -> sig       |    feed         |  DIFF FETCH APPLY COMMIT  |
  |  vdlu-gc    -> prune     | =============>  |  journal + rollback       |
  +--------------------------+   manifest.json |  ed25519-mini verify      |
                                 blobs/<sha>   +-------------+-------------+
                                                             |
                                                       +-----v------+
                                                       |  WebUI     |
                                                       |  Updates   |
                                                       |  panel     |
                                                       +------------+
```

二つの側面がランタイムを共有することは決してありません。Producer は `python3` と `openssl` を使い、Engine は純粋な POSIX `sh` に toybox と組み込みの `ed25519-mini` を加えたものです。両者が一致するのは、どちらもマニフェストから**同じ正準バイト列**を導出するからにほかなりません([[Security and Trust Model]] を参照)。WebUI は、root マネージャーのブリッジを通じてエンジンを駆動し、その進捗ジャーナルを読む薄いバニラ JS のパネルで、更新ロジックそのものは一切持ちません。[[WebUI]] を参照してください。

## 二つの側面

| 側面 | 動作環境 | 構成技術 | 役割 |
|---|---|---|---|
| [[Producer]] | PC / CI | `python3` + `sh` + `openssl` | モジュールツリーを `manifest.json` + `blobs/` に変換し、署名し、孤立した blob を削除する |
| [[Engine]] | 端末 | POSIX `sh` + toybox + `ed25519-mini` | インストール済みツリーをフィードと差分比較し、差分を取得し、適用し、コミットする |
| [[WebUI]] | 端末(webview) | バニラ JS/CSS | 更新の起動、進捗表示、設定の編集、再起動バナーの表示 |

## 更新パイプライン

すべての更新は一つのトランザクションであり、決まった順序で実行されます:

```
  DIFF  ------>  FETCH  ------>  APPLY  ------>  COMMIT
  read feed      download        write live     re-hash all,
  + validate     only missing    files now,      promote target
  + plan         blobs, verify   stage reboot     -> current,
  (no changes)   each sha256     ones             DONE or
                                                  PENDING_REBOOT
```

- **DIFF**(このフェーズが `update.sh check` であり、読み取り専用)。エンジンはマニフェストだけをダウンロードし、何かに触れる**前に**すべてのフィールドに対して `validate_plan()` を実行し、その後フィードを `current.json` と比較してファイルごとのプランを作成します。ディスク上の何も変更しません。フィードより先行している端末は、エラーではなく無害な「ahead」結果となります。
- **FETCH。** プランに不足している blob だけを `<sha>.part` にダウンロードし、`gz` を展開し、マニフェストと照合して `sha256sum` を検証し、検証済みの各 blob をキャッシュへアトミックに `mv` します。すでにキャッシュされている blob(あるいは変更のないローカルファイルから種まきされた blob)はスキップされるため、元に戻しや共有ファイルにコストはかかりません。同一 blob での 3 回の失敗で、何も適用せずにこのフェーズを中止します。ネットワークポリシーによってブロックされたダウンロードは、エラーではなく `DEFERRED`(再開可能)として終了します。
- **APPLY。** 通常(`live` / `soft`)のファイルは今すぐ書き込まれます。`rollback/<v>/` へバックアップし、`.vdlu-tmp` を書き込み、`chmod` し、検証し、そしてターゲットの上へアトミックに `rename` します。再起動クラスのファイルは `staged/<path>.vdlu-new` へ具現化され、ライブの inode はそのまま残されます。`delete[]` エントリはバックアップされてから削除されます。各ステップは冪等です。すでにターゲットハッシュと一致しているファイルはスキップされます。
- **COMMIT。** すべてのライブファイルを再ハッシュし、すべてが一致した場合にのみ、エンジンは `target.json` を `current.json` に昇格させます。何かがステージングされていた場合、トランザクションは `PENDING_REBOOT` で終わり、そうでなければ `DONE` となります。

## コンテンツアドレス方式のマニフェストと blob

フィードはコンテンツアドレス方式です。マニフェストは**完全な**ターゲットツリーを列挙し、各ファイルはその `sha256` によって運ばれ、blob ストアは個々の異なる内容ごとに一つのコピーを `blobs/<sha256>`(または `blobs/<sha256>.gz`)の下に保持します。

- **重複排除。** ツリー内のどこであれ、あるいはリリースをまたいで、同一の内容は一つの blob になります。公開は増分的です。`sha256` がすでにホスト上に存在する blob が再プッシュされることは決してなく、端末がすでに持っている内容を再取得することもありません。
- **sha256 は原本のもの。** ハッシュは常に非圧縮の内容を指し示します。`enc`(`raw` または `gz`)は、その一つの blob がたまたまどう保存されているかを記録するにすぎません。端末は toybox の `gunzip` で `gz` を展開するため、追加の圧縮ツールはバンドルされません。
- **フレーバー安定。** 端末は実際にインストールされているものと差分比較するため、フィードはモジュールファミリー全体を運ぶことができます。各インストールは、自身のフレーバーを完成させる blob だけを取得します。

フィールドごとの完全なレイアウトは [[Feed Format]] にあります。

## 再開可能なジャーナル

すべてのトランザクションがクラッシュセーフなのは、その進捗がジャーナル(`journal.json`)に存在し、進行中のトランザクションで固定されたターゲットが `target.json` に存在するからです。状態機械は決まった順序で動作します:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> ( PENDING_REBOOT | DONE )
                                                               \-> ERROR / DEFERRED
```

| 状態 | 意味 |
|---|---|
| `PLANNED` | プランが作成され、まだ何も取得していない |
| `FETCHING` / `FETCHED` | blob をダウンロード中 / すべての blob が存在し検証済み |
| `APPLYING` / `APPLIED_LIVE` | ファイルを書き込み中 / すべてのライブファイルを書き込み済み |
| `PENDING_REBOOT` | 再起動クラスのファイルがステージングされ、ブート時の入れ替えを待っている |
| `DONE` | すべての再ハッシュが一致し、`current.json` が昇格された |
| `ERROR` | 致命的な失敗。モジュールは破損せず残り、ライブファイルは `rollback/` から復元される |
| `DEFERRED` | ネットワークポリシーによってダウンロードが保留。プランは保持され、後で再開する |

`DONE` にはすべての再ハッシュが一致した場合に**のみ**到達するため、ジャーナルが半適用の更新を完了と偽ることは決してありません。途中でのクラッシュ、ネットワーク切断、再起動は再開可能なジャーナルを残し、`update.sh resume`(または `boot`)が現在のフェーズから引き継ぎます。コマンド群と端末上の状態ファイルについては [[Engine]] を参照してください。

## アトミック性とロールバック

その場で上書きされるものは決してなく、失われるものもありません:

- **アトミックな書き込み。** 各ファイルは一時ファイル(`.vdlu-tmp`)とアトミックな `rename` / `mv` を経て配置されるため、読み手が書きかけのファイルを目にすることはありません。
- **上書き前のバックアップ。** 新しいファイルがその上に rename される前に、以前の内容が `rollback/<version>/<path>` へ移されます(直近のいくつかのバージョンが保持されます)。適用が失敗した場合、ライブファイルは破損したまま残される代わりにロールバックコピーから復元されます。バックアップの失敗は、セーフティネットなしに上書きする代わりに適用を**中止**します。
- **直列化。** `mkdir` ベースのロック(toybox では `flock` が使えないため、PID による古いロックの回収を伴う `lock.d/`)が、同時実行を直列化します。

## 再起動不要の原則

ほとんどのファイルはモジュールがライブのまま入れ替えられるため、VDLU はそれらを即座に適用します。再起動を必要とするのは三つのクラスだけです。ライブプロセスがすでにそれらをマップしているからです。`.so`(Zygisk によって読み込まれる)、`/system` オーバーレイ、そして `sepolicy.rule` です。これらは**ステージングされ、決してライブの inode の上には書き込まれず**、次回ブート時に一度のプリzygote(pre-zygote)ステップで入れ替えられます。完全な分類とブートフローは [[Reboot Handling]] にあります。

## フェイルクローズドな信頼姿勢

フィードは PC から端末へ渡る唯一のものであるため、エンジンはそのすべてのバイトを敵対的なものとして扱います。`validate_plan()` は DIFF フェーズで、いかなるダウンロードよりも前に実行され、不正なフィールドがあればマニフェスト全体を拒否します。署名の検証には組み込みの `ed25519-mini` を使い(端末上に `openssl` はありません)、秘密鍵が端末や CI に触れることは決してなく、`hardened` プロファイルは反転によってフェイルクローズドなので、破損したプロファイル値が未署名のフィードを黙って受け入れてしまうことはあり得ません。完全なモデル、二つのプロファイル、それぞれが答える脅威については [[Security and Trust Model]] にあります。

# Security and Trust Model

VDLU はモジュールを、ネットワーク越しに、root として、その場で更新します。これはフィードから来るファイルに向けられた多大な権限であるため、エンジン全体が一つの前提の上に組み立てられています:

> **マニフェストのすべてのフィールドは敵対的な入力である。**

フィードはソースで毒を盛られることもあれば、MITM によって転送中にすり替えられ改ざんされることもあります。そうなっても、マニフェストは依然としてマニフェストに見える形で到着します。ファイルパス、`sha256` 文字列、`delete[]` リスト、mode、class、encoding フラグを運んでいます。VDLU はそれらのどれも信頼できるものとして扱いません。1 バイトでもダウンロードする前にプラン全体を検証し、マニフェストの値がシェルに届くことを決して許しません。

このページは信頼の物語の全体です。検証されるマニフェストスキーマについては [[Feed Format]]、これらのチェックが DIFF -> FETCH -> APPLY -> COMMIT トランザクションのどこに位置するかについては [[Engine]] を参照してください。

## サポートされるバージョン

セキュリティ修正は最新の `ENGINE_VERSION` に入る。署名された manifest は必要とする最小エンジンを `engine_min`
で宣言し、デバイス上のエンジンは自身が実装するより多くを要求する manifest を拒否する。古い vendor 済みエンジンは、
その場でバックパッチされるのではなく、修正を取り込むために**再 vendor**されることが期待される。

| ENGINE_VERSION | 状態 |
|---|---|
| 7 (現行) | サポート対象 - フィードより先行するモジュールを決して差し戻さない (ライブにインストールされた `versionCode` が "from" バージョンの下限となる)、古い downgrade plan の起動時自己修復 |
| 6 | 置き換え済み - 起動時の自己修復 - 古い `target <= 0` の journal (削除された stub が残した baseline 0 は UI も起動動作も駆動しない) |
| 5 | 置き換え済み - エンジン側の信頼アンカー除外 (フィードが運んでも `vdlu/` ディレクトリは無視される)、128 MiB のファイル単位 / 2 MiB の manifest 上限 |
| 4 | 置き換え済み - `key_id` allowlist、ドットセグメント/末尾スラッシュのパス拒否、サイズ上限、check 時ロック |
| <= 3 | サポート外 - 現行エンジンを再 vendor する |

エンジンの検証または適用ロジックへのいかなる変更も `ENGINE_VERSION` を bump する。

## 核心となる考え方: 何かが起こる前にフェイルクローズド

`validate_plan()` は `check`/diff フェーズの内部で、いかなる fetch より**も前に**、いかなる apply より**も前に**実行されます。計画されたファイルツリーのすべてのエントリと `delete[]` のすべてのエントリを辿り、単一のエントリでも不正があれば**マニフェスト全体を拒否**し、トランザクションは一切始まりません。部分的な受け入れも、「不正なものをスキップして残りを適用する」もありません。一つの不正なフィールドがバッチを毒する、それが意図です。

マニフェストが受け入れられるのは、**すべての**エントリについて以下の**すべて**が成り立つ場合のみです:

| フィールド | ルール | 理由 |
|---|---|---|
| `path` | 絶対でない、`..` 成分なし、`.` 成分なし、先頭の `./` なし、埋め込みの `/./` なし、末尾のスラッシュなし、制御文字(タブ / 改行)なし | パスは `MODULE_DIR` の内側に留まらなければならない。絶対または `..` パスは任意の場所への書き込みになる |
| `sha256` | `^[0-9a-f]{64}$` に正確に一致 | 16 進でない sha はシェルパスに補間されてしまう。これはコンテンツアドレスなので、純粋な 16 進ダイジェストでなければならず、それ以外は許されない |
| `mode` | 8 進のみ(`[0-7]`) | mode 文字列は `chmod` の引数になる |
| `size` | 数字のみ、かつエンジンのサイズ上限以下 | ダウンロードと展開の範囲を限定する |
| `class` | 正確に `live`、`soft`、または `reboot` | class はファイルがライブで適用されるか再起動用にステージングされるかを決める |
| `enc` | 正確に `raw` または `gz` | encoding は blob が gunzip されるかどうかを決める |
| `delete[]` エントリ | 上記と同じパスルール | `delete[]` エントリは削除を駆動する。チェックされない `..` はツリー外での `rm` になる |

これが最初に実行されるため、毒を盛られたマニフェストがモジュールの外に書き込むことも、モジュールの外を削除することも、16 進でないトークンをコマンドラインに注入することも決してできません。

### マニフェストの値がシェルに触れることはない

ルールの後半: 値が検証を通過した後でさえ、それが `sh` に補間されることは決してなく、`awk system()` に渡されることも決してありません。check コマンドは、`system()` 呼び出しを一切含まないように意図的に書き直されました。残りの仕事はコンテンツアドレッシングが行います。blob はその `sha256` によって取得され、その同じ `sha256` によって名付けられたキャッシュパスに書き込まれ、ダウンロードされたバイト列は何かが適用される前に再ハッシュされ比較されます。きれいな 64 桁の 16 進ダイジェストでない値がそこまで届くことはありません。`validate_plan()` がすでに拒否しているからです。

### 適用時の第二の防衛線

`validate_plan()` は `..` を**字句的に**ブロックしますが、ツリー内にすでに存在するシンボリックリンクが書き込みをリダイレクトできてしまう可能性があります。そこで適用時に `contained()` が実際のターゲットパスを解決し、それがモジュールベースの下にあることを確認し、解決できない場合はフェイルクローズドします。書き込みはアトミックで(一時名に書いてからターゲットの上へ `rename`)、すべての上書きはまず `rollback/` へバックアップされます。バックアップの失敗は、セーフティネットなしに上書きする代わりに適用を中止します。

## 二つのプロファイル

VDLU は二つの信頼プロファイルのいずれかで動作し、config の `profile=` で設定されます。

### `hardened`(公開時のデフォルト)

- **署名は必須。** マニフェストは端末上キーリングの鍵による有効な ed25519 署名を運ばなければならず、さもなければトランザクションは中止します。
- **ダウングレードはブロック。** `version` がインストール済みのバージョンより低いマニフェストは拒否されます。攻撃者が既知の脆弱なビルドへあなたを巻き戻すことはできません。
- これは `https://` 越しに公開配布されるあらゆるモジュールのためのプロファイルです。

### `trusted`(プライベートな SSH ステージングソース)

- 署名の検証は**ベストエフォート**です。ソースはあなたが管理するプライベートな `file://` または SSH ステージングフィードなので、署名の欠如や検証不能は致命的な中止にはなりません。
- **しかし、すべての blob の `sha256` は依然として常にチェックされます。** `trusted` が緩めるのは*誰がマニフェストに署名したか*であって、*バイト列がプランに一致するかどうか*では決してありません。内容の完全性はどちらのプロファイルでも譲れません。

## 反転によるフェイルクローズド

これは微妙な部分であり、ほとんどのシステムが誤る部分です。

`trusted` は、緩和された検証を選ぶ**唯一の**文字列です。エンジンは「これは `hardened` か?」をテストしません。「これは `trusted` では**ない**か?」をテストします:

```sh
prof=$(cfg profile hardened | tr -d '[:space:]')
...
if [ "$prof" != trusted ]; then
    # signature mandatory
fi
```

したがって、リテラルの `trusted` 以外の**あらゆるもの**は hardened の挙動に解決されます:

- 行が完全に欠けている -> hardened
- `hardend` のようなタイプミス -> hardened
- 末尾にスペースのある `trusted `、または CRLF 由来の `\r` -> hardened
- 大文字小文字が違う `Trusted` -> hardened
- MITM に改ざんされた値 -> hardened

以前のバージョンは*欠落した*行を hardened にデフォルトしていましたが、それでも破損した*値*は開いたパスに落ち込んでいました。これはフェイルオープンでした。改ざんされたプロファイル文字列が未署名のマニフェストを黙って受け入れることができ、未署名のマニフェストは MITM 下で攻撃者が供給した `.so` のすり替えを意味し、それは root レベルのリモートコード実行を意味します。反転がこれを閉じます。緩和された検証を得る唯一の方法は `trusted` を正確に綴ることであり、たとえそうしても blob のハッシュはチェックされます。エンジンが未署名のコードを受け入れるまで一つのタイプミスの距離にあることは決してありません。(`tr -d` は、穴を再び開くことなく、締まりのないスペースを持つ正当な `trusted` が誤って拒否されないよう、散在する空白を取り除きます。)

**このテストは要となるものです。`!= trusted` のまま保たれなければならず、決して `== hardened` になってはなりません。**

## マニフェストはモジュールに束縛される

一つのリリース鍵が多数のモジュールに署名します。したがって、*別の*モジュール用に正当に署名されたマニフェストが、原理的にはこのモジュールに提供され得(フィードの設定ミス、ソースのすり替え、または MITM のリダイレクト)、その署名は通ってしまいます。

VDLU はこれを束縛で閉じます。マニフェスト内の署名された `module` フィールドは、このインストールの `MODID` と等しくなければならず、さもなければマニフェストはクロスモジュールフィードとして拒否されます。`module` は署名された正準形の内側にあるため、攻撃者は署名を壊さずにそれを変更できません。モジュール B 用に正当に署名されたフィードは、モジュール A に適用することが単にできません。

## 軽量な端末上検証器

端末上の検証は **ed25519-mini** を使います。これは TweetNaCl(パブリックドメイン)の上に構築された、検証のみの小さなチェッカーです。**端末上に `openssl` はありません**。

- キーリングエントリは**生の 32 バイト公開鍵**で、`keyring/<key_id>.pub` として保存されます。(PEM 公開鍵は PC 側の成果物にすぎません。PEM を端末キーリングにコピーすると検証が壊れます。検証器は正確に 32 バイトの生のバイト列を期待するからです。)
- `vdlu-verify <manifest.json> <keyring_dir>` は正準形(`sig` フィールドを取り除いた、コンパクトでキーをソートしたマニフェストのテキスト)を再構築し、それを署名が覆う 64 文字の 16 進メッセージにハッシュ化し、base64 署名をデコードし、それが 64 バイトであることを確認し、`ed25519-mini <pub32> <msg> <sig64>` に判定を求めます。rc 0 = 有効、それ以外 = 拒否。
- バイナリは ABI ごとに静的で(arm64-v8a、armeabi-v7a、x86、x86_64)、正確な TweetNaCl のソース、ラッパーのハッシュ、ビルドフラグを固定する `PROVENANCE.json` を伴うので、root として動作するものは監査可能です。
- マニフェストの `key_id` 自体が、キーリングファイルを選ぶのに使われる前にサニタイズされ(`/` なし、`..` なし、クォートなし)、キーリングディレクトリから抜け出せないようになっています。

### キーリングはフラッシュ時のみ、コピーせず検証、安定

キーリングはフラッシュ時にモジュールの内側で配布され、更新エンジンによって書き換えられることはありません。再ベンダリング時のルールは**検証する、コピーしない**です。キーリングは意図的な鍵のローテーション時にのみ変わり、更新の副作用として変わることは決してありません。

### 鍵のローテーションは古いインストールをブリックしない

署名鍵がローテーションされるとき、キーリングは**現在と以前の両方の生の公開鍵**を配布します。検証器はマニフェストの `key_id` によって鍵ファイルを選ぶので、依然として古い鍵で署名されたフィードは古い公開鍵に対して検証され、新しい鍵で署名されたフィードは新しいものに対して検証されます。ローテーションを越えて更新していない端末は動き続け、何も取り残されません。

## モジュール更新 `key_id` 許可リスト

鍵のローテーションは、キーリングが正当に複数の鍵を保持しうることをすでに意味しており、モジュールは第二の理由からも複数を保持しうります。すなわち、*別の*フィードに署名する、より低信頼の鍵を同梱することがあります。フィンガープリントフィードはまさにその場合です。モジュールは、フィンガープリントフィードに署名することだけを役割とする狭い鍵を携えることができ、それはモジュール自体に署名するリリース鍵のすぐ隣、同じキーリングの中に収まります。

これは、ローテーションの話だけでは答えられない問いを生みます。すなわち、二つの鍵がキーリングに存在するようになったとき、そのうち*どちら*が**モジュール更新**への署名を許されるのか、という問いです。モジュール更新はマニフェストが要求しうる最も強力なものです。なぜなら端末が root として実行するファイルを書き換えるからです。検証器は以前、マニフェストの `key_id` が指す公開鍵を選び、キーリングにたまたま存在するどの鍵でも受け入れていました。したがって低信頼のフィンガープリントフィード鍵は、漏洩すればモジュール更新マニフェストに署名でき、端末はそれを尊重してしまうでしょう。これは信頼の根(トラストルート)のバイパスです。狭い役割のために意図された鍵が、フラッシュ不要の完全な root 更新を駆動しえたのです。

この修正は、受理されるモジュール更新の `key_id` を、フェイルクローズドな**許可リスト**に固定し、公開鍵が選ばれる**前に**チェックします。設定キーは `key_id` であり、エンジンはそれを次のように解決します:

- **単一鍵のキーリングはその一つの鍵を自動的に固定します。** 一般的なケースでは設定はまったく不要です。キーリングがちょうど一つの鍵を保持していれば、その鍵*こそが*許可リストであり、他のものがモジュール更新に署名することはできません。
- **複数鍵のキーリングは `key_id` を設定しなければなりません。** 二つめの鍵が現れた瞬間、エンジンは推測を拒否します。設定がモジュール更新に署名してよい鍵(あるいはローテーション期間中はカンマ区切りの複数の鍵)を指定するまで、"multiple keys in keyring; config must pin key_id" とともにフェイルクローズドします。

チェックは公開鍵の選択より前に走るため、存在するが許可リストにない鍵を指すマニフェストは、検証器がその鍵を読み込むことなく拒否されます。解決された集合は `VDLU_KEYID_ALLOW` を通じて `vdlu-verify` に反映されるので、軽量な端末上チェッカーも同じ固定を強制し、両者が食い違うことはありません。これは**両方の**プロファイルで成り立ちます。`hardened` も `trusted` もともに許可リストを参照します。なぜなら許可リストは、署名が必要*かどうか*ではなく、*どの鍵*が有効なモジュール更新の根であるかを決めるものだからです。

フィンガープリントフィードは、独自の別個の固定された信頼の根 `FEED_KEY_ID` を保ちます。それは別の役割を持つ別個の根であり、上記のモジュール更新経路から到達されることは決してありません。したがってモジュール更新の許可リストを固定してもそれには触れず、漏洩したフィード鍵は依然としてモジュール更新に署名できません。この変更により `ENGINE_VERSION` は 4 に引き上げられました。

## エンジン側の信頼アンカー除外

上記の許可リストは、*どの*鍵がモジュール更新に署名してよいかを決めます。後の変更 (`ENGINE_VERSION` 5) は、隣接するリスクをもう一方の側から塞ぎます。すなわち、正当に署名されたフィードがそもそも何に触れることを許されるのか、という点です。公開されたフィードはモジュールツリー全体を運び、そのツリーにはモジュール自身の `vdlu/` ディレクトリ - エンジン、`vdlu-verify` シム、`verify/` バイナリ、キーリング、そして設定 - が含まれます。これらが信頼アンカーです。もし更新がそれらを書き換えられるなら、漏洩した単一の署名鍵が新しい検証器や新しいキーリングを出荷し、無期限に root を永続化しうるでしょう。

そこでエンジンは、取得されたプランのすべての `vdlu/` パスを**無視します**。マニフェストがそれらを列挙していても、決して取得・適用・削除せず、またマニフェストを拒否することもしません。モジュールの残りは通常どおり更新され、`vdlu/` パスだけが黙って捨てられます。信頼アンカーはモジュール zip の完全な署名付き再フラッシュによって**のみ**変わり、回線越しには決して変わりません。これは `vdlu-pack` のプロデューサ側の除外 (そもそもそれらのパスをフィードに載せない) を、デバイス上の第二の独立したガードで補完します。同じ変更は、ハードニングの上限を**ファイルあたり 128 MiB** と**マニフェストあたり 2 MiB** にも引き下げました。Solomag によって報告されました (VD-Modules#1)。

## tools マニフェストが閉じるもの

軽量な fetch ブートストラップは、自身の `curl` を同梱しないモジュールのために、初回使用時に静的な `curl` をダウンロードします。そのバイナリは root として動作するため、それが導入または実行される前に、その自身のマニフェスト署名(ed25519-mini)とそのハッシュが、`trusted` を含むあらゆるプロファイルで**必須**です。webview は転送手段にすぎません。信頼は端末上の署名とハッシュのチェックから来るものであって、ダウンロードが成功したという事実から来るものでは決してありません。

## 攻撃者に**できないこと**

フィードを所有していても、あるいは完全な MITM として回線上に座っていても、攻撃者には以下ができません:

- **モジュールの外に書き込む。** 絶対パス、`..`、`.`、制御文字、末尾のスラッシュはすべて、いかなる apply より前に拒否され、シンボリックリンクのリダイレクトは apply 時に再び捕捉されます。
- **モジュールの外を削除する。** `delete[]` エントリは同じパス検証を通過します。
- **コマンドを注入する。** マニフェストの値がシェルや `awk system()` に補間されることはありません。`sha256` は純粋な 64 桁の 16 進でなければならず、さもなければマニフェスト全体が拒否されます。
- **公開インストールに未署名のコードを配布する。** `hardened` は署名を必須にし、プロファイルは反転によってフェイルクローズドなので、タイプミスや改ざんされた値がそれを格下げすることはありません。
- **より低信頼の鍵でモジュール更新に署名する。** モジュール更新の `key_id` はフェイルクローズドな許可リストに固定され、公開鍵が選ばれる前にチェックされるので、キーリングを共有する漏洩したフィンガープリントフィード鍵が完全な root 更新に署名することはできません。
- **別のモジュールの署名付きフィードをここに提供する。** 署名された `module` フィールドはこの `MODID` と等しくなければなりません。
- **あなたを巻き戻す。** `hardened` ではダウングレードがブロックされます。
- **blob を検知されずに破損させる。** ダウンロードされたすべての blob は、どちらのプロファイルでもマニフェストの `sha256` に対して再ハッシュされます。3 回の試行の後の不一致は、何も適用せずにフェーズを中止します。
- **偽の root フェッチャーをすり替える。** ブートストラップされた `curl` は、あらゆるプロファイルで、導入または実行される前に署名とハッシュがチェックされます。
- **破損した更新を半適用する。** トランザクションはすべての再ハッシュが一致したときにのみ `DONE` に到達します。適用の失敗は、バックアップなしに上書きする代わりにロールバックします。

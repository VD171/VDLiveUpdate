# Engine

Движок - это сторона устройства в VDLU: часть, которая работает на телефоне, решает, что изменилось, загружает это и применяет. Это единственный POSIX-скрипт оболочки, `engine/update.sh`, плюс крошечный проверяющий подпись, `engine/vdlu-verify`. Оба встраиваются в модуль-хост по пути `<module>/vdlu/` и запускаются от root.

Весь движок построен вокруг одной идеи: обновление - это **возобновляемая транзакция**. Если телефон перезагружают, убивают процесс или теряется сеть на полпути, следующий запуск продолжает ровно с того места, где остановился, и модуль никогда не остаётся наполовину применённым, притворяясь завершённым.

Если сначала хотите общую картину, см. [[Architecture]]. О том, как обновления избегают перезагрузки, когда это возможно, см. [[Reboot Handling]].

## Написан для устройства, а не для вашего ноутбука

`update.sh` - это чистый POSIX `sh`. Он работает под mksh, busybox или toybox, без фич только для bash, и проходит `sh -n`. Это важно, потому что окружение на рутованном Android-устройстве маленькое и строгое.

В частности, нет `jq`. VDLU разбирает `manifest.json` небольшим "выпрямителем" в стиле gron, написанным на `awk`: он проходит JSON по одному символу и выдаёт по одной строке `path<TAB>value` на каждый лист (например, `files/0/sha256<TAB>ab..` или `version<TAB>6`). Затем оболочка читает эти строки через `grep` и `cut`. Это работает как с компактным, так и с форматированным JSON, и никогда не вызывает JSON-инструмент, которого там нет.

Движок зависит только от того, что уже поставляет toybox (`sha256sum`, `gzip`/`gunzip`, `base64`, `date`), встроенного проверяющего `ed25519-mini`, и, для каналов по `https://`, небольшого статического `curl`, который загружается и проверяется один раз. Канал по `file://` вообще не требует `curl`.

## Шесть команд

Движок вызывается с путями модуля в окружении и одной командой:

```sh
VDLU_DIR=/data/adb/<mod>/vdlu MODULE_DIR=/data/adb/modules/<mod> MODID=<mod> \
  sh "$MODULE_DIR/vdlu/update.sh" <cmd>
```

Код возврата `0` означает успех; любой другой код означает ошибку, причём причина выводится в stderr.

| Команда | Что делает |
|---|---|
| `check` | Diff только для чтения. Загружает манифест, сравнивает его с тем, что установлено, и печатает однострочную JSON-сводку: `{"update":bool,"from":N,"to":M,"fetch":K,"reboot":bool}`. На диске ничего не меняет. Если устройство новее канала (заблокированный даунгрейд), выводит `{"update":false,"ahead":true,...}` с кодом `0`, а не ошибку. |
| `run` | Полный живой цикл: DIFF, FETCH, APPLY, COMMIT. Применяет каждый живой файл немедленно и подготавливает те немногие файлы класса reboot. Учитывает `cancel`. Пишет прогресс в `journal.json`. |
| `resume` | Продолжает прерванную транзакцию, начиная с той фазы, в которой она была. Идемпотентна. Она **не** заменяет подготовленный `.so` (это зарезервировано за `boot`). |
| `boot` | Предзиготный путь. Делает `resume`, а затем заменяет любые подготовленные файлы `*.vdlu-new` на место, закрывая `PENDING_REBOOT` в `DONE`. Если ожидающей транзакции нет, запускает свежий цикл и применяет всё, включая `.so`, в эту же загрузку. |
| `status` | Печатает `journal.json` или `{"state":"idle"}`, когда ничего не выполняется. |
| `cancel` | Создаёт маркер `cancel`. Выполняющийся `run` чисто останавливается в ближайшей безопасной точке. |

Команда `check` нарочно дешёвая, чтобы интерфейс мог сообщить о наличии обновления в любой сети. Сама загрузка ограничивается отдельно (см. фазу fetch ниже).

## Транзакция, шаг за шагом

Каждый `run` проходит через фиксированный конечный автомат, записываемый в `journal.json`, чтобы WebUI (и вы) могли наблюдать за ним:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> (PENDING_REBOOT | DONE)
```

**DIFF.** Движок загружает `manifest.json`, проверяет каждое поле (см. ниже и [[Security and Trust Model]]) и сравнивает подписанное целевое дерево с `current.json`, манифестом уже установленной версии. Результат - пофайловый план, записываемый в `plan.tsv`: по строке на файл, несущей его class, целевой хеш, mode и состояние прогресса. Файлы, уже имеющие целевой хеш, помечаются для пропуска.

**FETCH.** Для каждого ещё нужного файла движок загружает его адресуемый по содержимому блоб из `<source>/blobs/<sha>` (или `<sha>.gz`, когда сжат) в файл `.part`. Если блоб gzip-сжат, он распаковывается, затем его SHA-256 сверяется с манифестом. Только при совпадении он атомарно переносится (`mv`) в `blobs/<sha>`. Блоб, уже кэшированный с корректным хешем, полностью пропускается, а неизменный локальный файл может засеять кэш без всякой загрузки. Три сбоя на одном и том же блобе прерывают фазу, ничего не применив. Фаза достигает `FETCHED` только когда каждый блоб в плане присутствует и проверен. Про [[Feed Format]], откуда берутся эти блобы, см. ту страницу.

Fetch ограничивается сетевой политикой: канал может быть ограничен только Wi-Fi, только мобильной сетью или любой сетью. Когда текущая сеть не разрешена, fetch не падает; он входит в безобидное состояние `DEFERRED`, сохраняет план и закреплённую цель и возобновляется при следующей проверке или загрузке, как только появится нужная сеть. Трафик тем временем не расходуется.

**APPLY.** Входится только из `FETCHED`. Для каждого файла движок действует по классу:

- файлы `live` и `soft`: резервная копия текущего файла в `rollback/<version>/<path>`, запись нового содержимого в соседний `.vdlu-tmp`, `chmod`, проверка хеша, затем атомарный `rename` поверх цели. Файл, уже имеющий целевой хеш, пропускается.
- файлы `reboot` (`.so`, оверлей `/system`, `sepolicy.rule`): материализуются в `staged/<path>.vdlu-new`. Живой inode здесь никогда не трогается. См. [[Reboot Handling]].
- удаления: резервная копия, затем удаление. Удаления применяются только в самом конце, на чистом `DONE`, никогда пока перезагрузка ещё ожидается.

**COMMIT.** Движок повторно хеширует каждый файл `live` и `soft`, который тронул. Только когда все они совпадают, он записывает `current.json`, делая новую версию базой для diff. Если какой-либо файл класса reboot был подготовлен, состояние становится `PENDING_REBOOT` вместо `DONE`; замена и финальная повторная проверка происходят позже под командой `boot`.

## Отказобезопасность по построению

Гарантии, которые делают это безопасным для запуска без присмотра:

- **Ничто не помечается `DONE` без совпавшего повторного хеширования.** `DONE` достигается только после того, как каждый применённый файл был прочитан обратно, а его SHA-256 сверен с манифестом. Подготовленный файл reboot принудительно даёт `PENDING_REBOOT`, никогда ложный `DONE`.
- **Ничто не теряется.** Каждый файл резервируется в `rollback/<version>/` до перезаписи, и хранятся последние три версии. Если применение не удаётся, живые файлы восстанавливаются из резервной копии; модуль никогда не остаётся наполовину применённым, лгущим об этом. `apply_live` прерывается сразу, если шаг резервного копирования не удался, вместо перезаписи без пути назад.
- **Всё атомарно.** Новое содержимое попадает на место через `rename`/`mv` поверх цели, поэтому читатель всегда видит либо старый файл, либо новый, никогда усечённую запись.
- **Возобновляемость после сбоя или убийства процесса.** Сбой, потеря сети или перезагрузка на полпути оставляют валидный журнал; `resume` (или `boot`) продолжает с записанной фазы. Проектирование исходит из того, что процесс будет прерван.
- **Чистая деградация.** Отсутствующий бинарник, упавшая сеть или заполненный диск дают явную ошибку в stderr и `state:ERROR` в журнале, не повреждая модуль.

## Блокировка

В один момент времени состояние может трогать только одна транзакция. `flock` ненадёжен на toybox, поэтому VDLU сериализует с помощью блокировки-каталога: `mkdir "$VDLU_DIR/lock.d"` удаётся ровно для одного вызывающего и проваливается для остальных, что атомарно на любой вменяемой файловой системе. Устаревшая блокировка, оставленная мёртвым процессом, восстанавливается проверкой записанного PID.

Терпеливый повтор во время загрузки (используемый, когда устройство офлайн при загрузке) **не** удерживает эту блокировку, пока ждёт. Он захватывает и освобождает её между попытками, поэтому ручной `run` никогда не блокируется загрузкой, которая ждёт сеть, и он никогда не удерживает wakelock. Безопасен для батареи по замыслу. Подробнее об этом в [[Reboot Handling]].

## Проверка подписи: `vdlu-verify`

`vdlu-verify` - это проверяющий подпись на устройстве, намеренно сделанный лёгким:

```
vdlu-verify <manifest.json> <keyring_dir>
```

Код `0` означает, что подпись манифеста валидна относительно публичного ключа связки (keyring), чей id совпадает с `key_id` манифеста; любой другой код - отказ.

Лёгким его делает то, что он использует **никакого `openssl` на устройстве**. Он читает публичный ключ связки как файл из **сырых 32 байт**, канонизирует манифест (текст манифеста с удалённым полем `sig`), хеширует его toybox `sha256sum`, декодирует base64-подпись и передаёт сырой ключ, сообщение и 64-байтовую подпись встроенному бинарнику `ed25519-mini`. Проверяющий также отклоняет всё некорректное ещё до того, как что-либо проверяет: отсутствующий или пустой `key_id` или `sig`, `key_id`, содержащий разделители путей, публичный ключ, не равный ровно 32 байтам, или подпись, не равную ровно 64 байтам.

Канонизация побайтово идентична подписывающему на стороне продюсера, и именно это делает подпись проверяемой между инструментами. Соответствующий приватный ключ никогда не попадает на устройство или в CI; встраивается только сырой публичный ключ. Полная история доверия, два профиля и почему `hardened` отказоустойчив за счёт инверсии - в [[Security and Trust Model]].

Движок вызывает `vdlu-verify` в фазе diff. Под профилем `hardened` неудавшаяся проверка прерывает всё обновление; под `trusted` проверка выполняется по возможности (best-effort), но хеш каждого блоба всё равно всегда проверяется, поэтому повреждённое содержимое ловится независимо от профиля.

## Состояние на диске

Всё состояние движка живёт в `$VDLU_DIR` (вне каталога модуля), поэтому само дерево модуля всегда содержит только завершённые файлы:

| Путь | Роль |
|---|---|
| `config` | настройки key=value (source, profile, channel, сетевая политика, повтор при загрузке) |
| `current.json` | манифест активной версии; это база для diff. Отсутствие означает, что обновлений не было |
| `target.json` | закреплённый манифест текущей транзакции. Его наличие отмечает активную транзакцию; на `DONE` он становится `current.json` |
| `plan.tsv` / `plan.del` | пофайловый план и прогресс, а также список путей к удалению |
| `journal.json` | прогресс для WebUI, переписывается при каждом изменении состояния |
| `blobs/<sha256>` | кэш проверенного, распакованного оригинального содержимого |
| `rollback/<version>/<path>` | резервные копии перезаписанных файлов; хранятся последние три версии |
| `staged/<path>.vdlu-new` | файл класса reboot, ожидающий замены при загрузке |
| `lock.d/` | mkdir-блокировка |
| `tools/<abi>/curl` | загруженный, проверенный статический curl; сохраняется между обновлениями |
| `cancel` | запрос на отмену |

# Архитектура

У VDLU две стороны, соединённые одной вещью посередине. На ПК [[Producer]] превращает дерево модуля в подписанный, адресуемый по содержимому канал. На устройстве [[Engine]] читает этот канал, выясняет, что изменилось, и применяет это. Шов между ними - **подписанный манифест плюс хранилище блобов** ([[Feed Format]]). Больше ничего через этот зазор не проходит.

```
        PC / release host                                device
  +--------------------------+                 +---------------------------+
  |  Producer                |                 |  Engine  (update.sh)      |
  |  vdlu-pack  -> manifest  |    signed       |  POSIX sh, no jq          |
  |  vdlu-sign  -> sig       |    feed         |  DIFF FETCH APPLY COMMIT  |
  |  vdlu-gc    -> prune     | =============>  |  journal + rollback       |
  +--------------------------+   manifest.json |  ed25519-mini verify      |
                                 blobs/<sha>   +-------------+-------------+
                                                             |
                                                       +-----v------+
                                                       |  WebUI     |
                                                       |  Updates   |
                                                       |  panel     |
                                                       +------------+
```

Две стороны никогда не разделяют общий рантайм. Producer использует `python3` и `openssl`; Engine - это чистый POSIX `sh` с toybox и встроенным `ed25519-mini`. Они согласуются лишь потому, что обе выводят **одни и те же канонические байты** из манифеста (см. [[Security and Trust Model]]). WebUI - это тонкая панель на чистом JS, которая управляет движком через мост root-менеджера и читает его журнал прогресса; она не содержит собственной логики обновления. См. [[WebUI]].

## Две стороны

| Сторона | Где работает | Из чего собрана | Задача |
|---|---|---|---|
| [[Producer]] | ПК / CI | `python3` + `sh` + `openssl` | Обойти дерево модуля в `manifest.json` + `blobs/`, подписать его, вычистить осиротевшие блобы |
| [[Engine]] | устройство | POSIX `sh` + toybox + `ed25519-mini` | Вычислить разницу установленного дерева с каналом, загрузить дельты, применить, зафиксировать |
| [[WebUI]] | устройство (webview) | vanilla JS/CSS | Запускать обновления, показывать прогресс, редактировать конфиг, показывать баннер перезагрузки |

## Конвейер обновления

Каждое обновление - это одна транзакция, выполняемая в фиксированном порядке:

```
  DIFF  ------>  FETCH  ------>  APPLY  ------>  COMMIT
  read feed      download        write live     re-hash all,
  + validate     only missing    files now,      promote target
  + plan         blobs, verify   stage reboot     -> current,
  (no changes)   each sha256     ones             DONE or
                                                  PENDING_REBOOT
```

- **DIFF** (`update.sh check` - это данная фаза, только чтение). Движок загружает лишь манифест, прогоняет `validate_plan()` по каждому полю **до того**, как что-либо трогать, затем сравнивает канал с `current.json`, чтобы построить пофайловый план. На диске ничего не меняется. Устройство, опережающее канал, - это безобидный результат "ahead", а не ошибка.
- **FETCH.** Загружает только недостающие по плану блобы в `<sha>.part`, распаковывает `gz`, сверяет `sha256sum` с манифестом и атомарно переносит (`mv`) каждый проверенный блоб в кэш. Блоб, уже находящийся в кэше (или засеянный из неизменного локального файла), пропускается, поэтому откат или общий файл ничего не стоят. Три сбоя на одном блобе прерывают фазу, не применяя ничего. Загрузка, заблокированная сетевой политикой, завершается как `DEFERRED` (возобновляемо), а не как ошибка.
- **APPLY.** Обычные (`live` / `soft`) файлы записываются сейчас: резервная копия в `rollback/<v>/`, запись `.vdlu-tmp`, `chmod`, проверка, затем атомарный `rename` поверх цели. Файлы класса reboot материализуются в `staged/<path>.vdlu-new`, а живой inode остаётся нетронутым. Запись из `delete[]` сначала резервируется, затем удаляется. Каждый шаг идемпотентен: файл, уже имеющий целевой хеш, пропускается.
- **COMMIT.** Повторно хешируется каждый живой файл; только если всё совпадает, движок продвигает `target.json` в `current.json`. Если что-то было подготовлено (staged), транзакция завершается в состоянии `PENDING_REBOOT`; иначе - `DONE`.

## Адресуемый по содержимому манифест и блобы

Канал адресуется по содержимому: манифест перечисляет **полное** целевое дерево, каждый файл несёт свой `sha256`, а хранилище блобов хранит по одной копии каждого отдельного содержимого под `blobs/<sha256>` (или `blobs/<sha256>.gz`).

- **Дедупликация.** Идентичное содержимое где угодно в дереве или между релизами - это один блоб. Публикация инкрементальна: блоб, чей `sha256` уже существует на хосте, никогда не заливается повторно, а устройство никогда повторно не загружает содержимое, которое у него уже есть.
- **sha256 - от оригинала.** Хеш всегда именует несжатое содержимое; `enc` (`raw` или `gz`) лишь фиксирует, как именно этот блоб хранится. Устройство распаковывает `gz` с помощью toybox `gunzip`, поэтому никакой дополнительный компрессор не поставляется.
- **Стабильность сборки.** Поскольку устройство сравнивается с тем, что фактически установлено, канал может нести целое семейство модуля; каждая установка подтягивает только те блобы, которые завершают её собственную сборку.

Полное пофайловое устройство - в [[Feed Format]].

## Возобновляемый журнал

Каждая транзакция устойчива к сбоям, потому что её прогресс живёт в журнале (`journal.json`), а закреплённая цель текущей транзакции живёт в `target.json`. Конечный автомат работает в фиксированном порядке:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> ( PENDING_REBOOT | DONE )
                                                               \-> ERROR / DEFERRED
```

| Состояние | Значение |
|---|---|
| `PLANNED` | План построен, пока ничего не загружено |
| `FETCHING` / `FETCHED` | Загрузка блобов / все блобы на месте и проверены |
| `APPLYING` / `APPLIED_LIVE` | Запись файлов / все живые файлы записаны |
| `PENDING_REBOOT` | Файл класса reboot подготовлен, ждёт замены при загрузке |
| `DONE` | Повторное хеширование всего совпало; `current.json` продвинут |
| `ERROR` | Жёсткий сбой; модуль не повреждён, живые файлы откатаны из `rollback/` |
| `DEFERRED` | Загрузка придержана сетевой политикой; план сохраняется, возобновляется позже |

`DONE` достигается **только** после того, как повторное хеширование всего совпадает, поэтому журнал никогда не заявляет, что наполовину применённое обновление завершено. Сбой, обрыв сети или перезагрузка на полпути оставляют возобновляемый журнал; `update.sh resume` (или `boot`) продолжает с текущей фазы. См. [[Engine]] про набор команд и файлы состояния на устройстве.

## Атомарность и откат

Ничто никогда не перезаписывается на месте и ничто не теряется:

- **Атомарная запись.** Каждый файл попадает на место через временный (`.vdlu-tmp`) и атомарный `rename` / `mv`, поэтому читатель никогда не видит наполовину записанный файл.
- **Резервная копия перед перезаписью.** Прежнее содержимое уходит в `rollback/<version>/<path>` до того, как новый файл будет переименован поверх него (хранятся последние несколько версий). Если применение не удаётся, живые файлы восстанавливаются из резервной копии, а не остаются повреждёнными. Неудавшееся резервное копирование **прерывает** применение вместо перезаписи без страховки.
- **Сериализация.** Блокировка на основе `mkdir` (`lock.d/`, поскольку `flock` неработоспособен на toybox, с восстановлением устаревшей блокировки по PID) сериализует параллельные запуски.

## Принцип отсутствия перезагрузки

Большинство файлов можно заменить, пока модуль живой, поэтому VDLU применяет их немедленно. Только три класса требуют перезагрузки, потому что живой процесс уже отобразил их: `.so` (загружаемый Zygisk), оверлей `/system` и `sepolicy.rule`. Они **подготавливаются, а не записываются поверх живого inode** и заменяются в одном предзиготном (pre-zygote) шаге при следующей загрузке. Полная таксономия и процесс загрузки - в [[Reboot Handling]].

## Отказоустойчивая позиция доверия

Канал - единственное, что переходит с ПК на устройство, поэтому движок рассматривает каждый его байт как враждебный. `validate_plan()` работает в фазе DIFF, до любой загрузки, и отклоняет весь манифест при любом некорректном поле. Проверка подписи использует встроенный `ed25519-mini` (на устройстве нет `openssl`), приватный ключ никогда не попадает на устройство или в CI, а профиль `hardened` отказоустойчив за счёт инверсии, поэтому повреждённое значение профиля никогда не сможет молча принять неподписанный канал. Полная модель, два профиля и угрозы, на которые отвечает каждый из них, - в [[Security and Trust Model]].

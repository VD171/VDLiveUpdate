# Feed Format

**Feed** - це те, що VDLU віддає по дротах, і те, з чого оновлюється пристрій. Це звичайний статичний каталог, який можна віддавати будь-чим (GitHub Pages, ціль rsync, шлях `file://`):

```
<source>/
  manifest.json          # the signed description of the current release
  blobs/<sha256>         # one blob per distinct file content
  blobs/<sha256>.gz      # (when the blob is stored gzipped)
```

Сам модуль також відвантажує один додатковий файл, `baseline.json`, усередині `.zip` (він не віддається з feed). Producer, що будує все це, описаний у [[Producer]]; ця сторінка - контракт у дротах.

---

## manifest.json

Маніфест - це повний опис одного випуску: кожен файл у цільовому дереві, що видалити, і підпис над усім цим.

```json
{
  "schema": 1,
  "module": "demo",
  "version": 106,
  "version_name": "v106",
  "built": "2026-11-19T12:00:00Z",
  "engine_min": 3,
  "channel": "stable",
  "key_id": "release-2026",
  "files": [
    {
      "path": "webroot/index.html",
      "sha256": "<hex64>",
      "size": 1234,
      "mode": "0644",
      "enc": "raw",
      "class": "live"
    }
  ],
  "delete": ["webroot/old.html"],
  "sig": "<base64>"
}
```

### Поля

| Поле | Значення |
|---|---|
| `schema` | Версія формату самого маніфесту (наразі `1`). |
| `module` | Id модуля. Пристрій відхиляє маніфест, якщо він не збігається з його власним id модуля, тож дійсно підписаний feed для іншого модуля не може бути поданий замість нього. |
| `version` | Цілочисельна версія. Рушій оновлює лише вперед; feed, старіший за пристрій, - це нешкідливий стан "ahead", а не помилка. |
| `version_name` | Зручний для людини рядок версії (наприклад `v106`). |
| `built` | Мітка часу збірки ISO 8601. Зважає на `SOURCE_DATE_EPOCH` для відтворюваності. |
| `engine_min` | Мінімальна версія рушія, потрібна для застосування цього маніфесту. |
| `channel` | Канал випуску (наприклад `stable`). |
| `key_id` | Який ключ у keyring пристрою підписав цей маніфест. Обирає публічний ключ для перевірки. |
| `files[]` | **Повне** цільове дерево (не diff). Кожен запис: `path`, `sha256`, `size`, `mode`, `enc` (`raw`/`gz`), `class` (`live`/`soft`/`reboot`). |
| `delete[]` | Шляхи, наявні в попередньому випуску, але зниклі тепер, щоб пристрій їх видалив. |
| `sig` | Підпис ed25519, base64. Див. канонізацію нижче. |

`files[]` описує **усе** дерево, не дельту. Пристрій обчислює дельту сам, порівнюючи маніфест із тим, що вже має, і тягне лише ті blob-и, чийого `sha256` йому бракує. `sha256` завжди від оригінального (нестисненого) вмісту; `enc` лише каже, як цей blob зберігається в `blobs/`. Значення `class` і те, що пристрій робить з кожним значенням, розкрито в [[Reboot Handling]].

## Канонізація (підписані байти)

Це найважливіший інваріант у форматі. Підписувач на ПК і перевіряч на пристрої працюють на цілком різних runtime-ах (openssl на ПК, toybox + крихітний вбудований перевіряч на пристрої, і **жодної JSON-бібліотеки взагалі** на пристрої). Вони все одно мають вивести точно ті самі байти, щоб підписати й перевірити. Тож правило - це свідоме **байтове перетворення**, а не повторна JSON-серіалізація.

**Крок 1: фіксована форма зберігання.** `vdlu-pack` пише `manifest.json` компактно, зі впорядкованими ключами, UTF-8, завжди включно з `key_id` та `sig` (як порожні рядки до підписання):

```
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

**Крок 2: зчистити лише `sig`.** Канонічна форма - це той самий точний текст, із **лише вилученим полем `"sig"`**. Оскільки ключі впорядковані, `sig` завжди з'являється як `,"sig":"<value>",`, узятий у дужки `"schema"` перед ним і `"version"` після (обидва завжди наявні), тож його вилучення лишає коректний текст. JSON екранує кожну `"` всередині рядкового значення як `\"`, тож структурний токен `"sig":"` однозначний навіть проти імені файлу, що буквально містить `"sig":"`.

Вилучення - це жменька розширень параметрів POSIX, ідентичних у підписувачі й перевірячі, без `sed` і без `jq`:

```sh
# $1 = the full manifest text
_pre=${_c%%\"sig\":\"*}     # up to  ...,"schema":N,
_rest=${_c#*\"sig\":\"}      # after "sig":"
_tail=${_rest#*\",}          # after <value>",  ->  "version":...
printf '%s%s' "$_pre" "$_tail" | sha256sum | cut -d' ' -f1
```

**Крок 3: підписати хеш від цього.** Підписуване/перевірюване повідомлення - це **sha256 hex** (64 ASCII-символи, без переходу рядка) канонічної форми. ed25519 підписує цей hex.

Два наслідки випливають із цього за конструкцією:

- `key_id` є частиною канонічної форми (зчищається лише `sig`). `vdlu-sign` встановлює `key_id` **перед** хешуванням, тож ідентичність ключа покрита підписом.
- Незалежно від того, порожній заповнювач `sig` (`"sig":""`, під час підписання) чи заповнений (під час перевірки), його зчищення дає ідентичні канонічні байти. Підписання й перевірка узгоджуються автоматично.

Два інструменти POSIX sh є авторитетними. Еквівалент на Python, `re.sub(r'"sig":"[^"]*",', '', text, count=1)` тоді sha256, існує лише для їхньої перехресної звірки.

Міркування про довіру навколо всього цього (чому перевірка на пристрої, як `hardened` є fail-closed) живуть у [[Security and Trust Model]].

## baseline.json (насіння встановлення)

Коли модуль щойно встановлено, він уже має бути "поточним" для власної відвантаженої версії, без зайвого самооновлення версії, яку щойно встановив. Саме це робить `baseline.json`.

`baseline.json` відвантажується **всередині zip модуля** (за `vdlu/baseline.json`), а не з feed. При свіжому встановленні рушій засіває свій запис "active version" із нього, тож пристрій народжується поточним, без `from:0` і без повторного завантаження того, що вже має.

Ключові властивості:

- Це **безключова копія підписаного маніфесту** для відвантаженої версії: той самий вивід `vdlu-pack`, залишений непідписаним (`key_id` та `sig` лишаються порожніми).
- Він **не перевіряється**. Рушій трактує його як локальне довірене насіння, бо він прибув усередині прошитого zip, що є межею довіри встановлення. Лише маніфест, *завантажений із feed*, проходить перевірку підпису.
- Оскільки він не потребує підпису, **CI може генерувати його безключовим**, і саме це тримає ключ підпису цілком поза CI (див. [[Producer]]).
- `vdlu-pack` **виключає `baseline.json` зі свого власного маніфесту**, тож маніфест ніколи не посилається на baseline (це був би цикл самопосилання: маніфест на baseline на маніфест).
- Його відсутність **не фатальна**. Без нього пристрій просто починає з `from:0` при першому оновленні й тягне те, що йому треба. Ніколи не зламаний, лише менш оптимальний.

## Blob-и

Кожен окремий вміст файлу - це один blob під `blobs/`, іменований за **sha256 оригінального вмісту**:

- `blobs/<sha256>` для сирого blob-а.
- `blobs/<sha256>.gz` для gzip-нутого blob-а (gzip зберігається лише коли файл не менший за 4096 байтів і стиснення заощаджує щонайменше 10 відсотків).

Blob зберігається раз, в одному форматі. Адресація за вмістом дає дедуплікацію задарма: незмінений, спільний чи відкочений вміст відображається на blob, що вже існує, тож feed розростається лише справді новим вмістом, а пристрій завантажує лише ті хеші, яких йому бракує. Пристрій перевіряє `sha256` кожного завантаженого blob-а проти маніфесту (після розпакування `gz`-blob-а) перед використанням.

## Що виключено з feed і чому

Feed несе **лише власний вміст модуля**. Фіксований набір шляхів навмисно тримається поза ним. `vdlu-pack` застосовує один виключний предикат і при обході дерева, і при обчисленні `delete[]`.

| Виключено | Чому |
|---|---|
| `vdlu/keyring/`, `vdlu/verify/` (корінь довіри: сирі публічні ключі + бінарник перевіряча) | **Це головна причина безпеки.** Якір довіри (trust anchor) - **лише через прошивку**. Якби keyring чи перевіряч можна було доставити через feed, маніфест міг би перезаписати саме те, що його перевіряє. Тримання їх поза дротами означає, що маніфест ніколи не зможе переписати якір довіри на пристрої. |
| `vdlu/baseline.json` | Це копія підписаного маніфесту (насіння встановлення); його packing був би циклом самопосилання. |
| інфраструктура прошивки `.vd/` | Риштування flash-gate, що відвантажується в zip, ніколи не застосовується наживо. |
| `update.json`, `update-mmrl.json` | Їхні size/sha заповнює CI *після* того, як zip-и зібрано, тож відвантажена копія відрізняється від будь-якої копії з feed. Їх подача спричиняла б фантомний fetch одного файлу при першому самооновленні кожного встановлення, і вони все одно рудиментарні на пристрої (менеджер читає віддалений сирий update JSON). |
| `META-INF/`, `customize.sh` (риштування інсталятора) | Споживаються менеджером під час **прошивки** й не зберігаються у встановленому модулі. Це не вміст VDLU; їх подача марнує blob-и і, якби один колись змінився між версіями, він був би записаний як файл інсталятора в живий каталог модуля. |
| Супутники `.sha256` по файлах | Вони належать лише прошиваному zip, застарівають після інкрементного оновлення й подвоїли б маніфест. |
| Dev/doc-файли (`RELEASE.md`, `CLAUDE.md`, `.gitignore`) | Ніколи не відвантажуються на пристрій; їх подача марнує blob-и й збовтує підписаний маніфест при кожному редагуванні doc. |

Міркування за виключенням кореня довіри розширено в [[Security and Trust Model]].

## Семантика delete[]

`delete[]` каже пристрою, які шляхи видалити, щоб файл, викинутий між випусками, не затримувався на пристрої як сирота. Вона обчислюється передачею `--prev <previous manifest.json>` у `vdlu-pack`: шлях, що був у попередньому випуску й відсутній у поточному, стає записом видалення.

Важливе правило: **виключені шляхи ніколи не видаються як видалення, навіть із `--prev`.** Кожен попередній шлях прогониш через той самий виключний предикат, що й при обході дерева. Якщо `--prev` вказує на старіший маніфест, що все ще перелічував тепер-виключені шляхи (випадковий `baseline.json`, `META-INF/*`, запис keyring тощо), ці шляхи **не** перетворюються на записи видалення. Виключений шлях ніколи не був вмістом feed, тож це не справа VDLU його видаляти, і пристрою ніколи не наказують видалити файл, що не подавався через feed. Саме це тримає список виключень від того, щоб коли-небудь повернутися руйнівною інструкцією.

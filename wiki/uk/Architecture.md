# Architecture

VDLU має дві сторони, з'єднані однією річчю посередині. На ПК [[Producer]] перетворює дерево модуля на підписаний, адресований за вмістом feed. На пристрої [[Engine]] читає цей feed, з'ясовує, що змінилося, і застосовує це. Шов між ними - це **підписаний маніфест плюс сховище blob-ів** ([[Feed Format]]). Більше ніщо не перетинає цей проміжок.

```
        PC / release host                                device
  +--------------------------+                 +---------------------------+
  |  Producer                |                 |  Engine  (update.sh)      |
  |  vdlu-pack  -> manifest  |    signed       |  POSIX sh, no jq          |
  |  vdlu-sign  -> sig       |    feed         |  DIFF FETCH APPLY COMMIT  |
  |  vdlu-gc    -> prune     | =============>  |  journal + rollback       |
  +--------------------------+   manifest.json |  ed25519-mini verify      |
                                 blobs/<sha>   +-------------+-------------+
                                                             |
                                                       +-----v------+
                                                       |  WebUI     |
                                                       |  Updates   |
                                                       |  panel     |
                                                       +------------+
```

Дві сторони ніколи не поділяють один runtime. Producer використовує `python3` та `openssl`; Engine - це чистий POSIX `sh` із toybox та вбудованим `ed25519-mini`. Вони узгоджуються лише тому, що обидва виводять **ті самі канонічні байти** з маніфесту (див. [[Security and Trust Model]]). WebUI - це тонка панель на vanilla JS, яка керує рушієм через міст root-менеджера та читає його журнал прогресу; власної логіки оновлення вона не містить. Див. [[WebUI]].

## Дві сторони

| Сторона | Працює на | Зібрано з | Завдання |
|---|---|---|---|
| [[Producer]] | PC / CI | `python3` + `sh` + `openssl` | Обійти дерево модуля у `manifest.json` + `blobs/`, підписати, вичистити сироти |
| [[Engine]] | device | POSIX `sh` + toybox + `ed25519-mini` | Порівняти встановлене дерево з feed, завантажити дельти, застосувати, зафіксувати |
| [[WebUI]] | device (webview) | vanilla JS/CSS | Запускати оновлення, показувати прогрес, редагувати конфіг, показувати банер перезавантаження |

## Конвеєр оновлення

Кожне оновлення - це одна транзакція, що виконується у фіксованому порядку:

```
  DIFF  ------>  FETCH  ------>  APPLY  ------>  COMMIT
  read feed      download        write live     re-hash all,
  + validate     only missing    files now,      promote target
  + plan         blobs, verify   stage reboot     -> current,
  (no changes)   each sha256     ones             DONE or
                                                  PENDING_REBOOT
```

- **DIFF** (`update.sh check` - це саме ця фаза, лише для читання). Рушій завантажує тільки маніфест, прогониш `validate_plan()` по кожному полю **перед** тим, як щось чіпати, а тоді порівнює feed із `current.json`, щоб побудувати план по файлах. На диску він нічого не змінює. Пристрій, що випереджає feed, - це нешкідливий результат "ahead", а не помилка.
- **FETCH.** Завантажує лише ті blob-и, яких бракує плану, у `<sha>.part`, розпаковує `gz`, перевіряє `sha256sum` відносно маніфесту й атомарно `mv`-ить кожен перевірений blob у кеш. Blob, що вже в кеші (або засіяний із незміненого локального файлу), пропускається, тож відкочення чи спільний файл не коштують нічого. Три невдачі на одному blob-і переривають фазу без жодного застосування. Завантаження, заблоковане мережевою політикою, виходить як `DEFERRED` (з можливістю відновлення), а не як помилка.
- **APPLY.** Звичайні (`live` / `soft`) файли записуються зараз: резервна копія в `rollback/<v>/`, запис у `.vdlu-tmp`, `chmod`, перевірка, тоді атомарний `rename` поверх цілі. Файли класу reboot матеріалізуються у `staged/<path>.vdlu-new`, а живий inode лишається недоторканим. Запис `delete[]` резервується, тоді видаляється. Кожен крок ідемпотентний: файл, що вже на цільовому хеші, пропускається.
- **COMMIT.** Повторно хешує кожен живий файл; лише якщо все збігається, рушій просуває `target.json` у `current.json`. Якщо щось було поставлено у staged, транзакція завершується станом `PENDING_REBOOT`; інакше `DONE`.

## Маніфест і blob-и, адресовані за вмістом

Feed адресований за вмістом: маніфест перелічує **повне** цільове дерево, кожен файл несе свій `sha256`, а сховище blob-ів зберігає одну копію кожного окремого вмісту під `blobs/<sha256>` (або `blobs/<sha256>.gz`).

- **Дедуплікація.** Однаковий вміст будь-де в дереві чи між випусками - це один blob. Публікація інкрементна: blob, чий `sha256` уже є на хості, ніколи не відвантажується знову, і пристрій ніколи повторно не тягне вмісту, який у нього вже є.
- **sha256 - від оригіналу.** Хеш завжди іменує нестиснений вміст; `enc` (`raw` або `gz`) лише фіксує, як саме цей blob зберігається. Пристрій розпаковує `gz` через toybox `gunzip`, тож жодного зайвого компресора не додано.
- **Стабільність варіанта.** Оскільки пристрій порівнює з фактично встановленим, feed може нести цілу родину модулів; кожне встановлення тягне лише ті blob-и, що доповнюють його власний варіант.

Повна структура поле-за-полем - у [[Feed Format]].

## Журнал із можливістю відновлення

Кожна транзакція стійка до збоїв, бо її прогрес живе в журналі (`journal.json`), а закріплена ціль поточної транзакції живе у `target.json`. Скінченний автомат виконується у фіксованому порядку:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> ( PENDING_REBOOT | DONE )
                                                               \-> ERROR / DEFERRED
```

| Стан | Значення |
|---|---|
| `PLANNED` | План побудовано, ще нічого не завантажено |
| `FETCHING` / `FETCHED` | Завантаження blob-ів / усі blob-и наявні й перевірені |
| `APPLYING` / `APPLIED_LIVE` | Запис файлів / усі живі файли записано |
| `PENDING_REBOOT` | Файл класу reboot поставлено у staged, очікує підміни при завантаженні |
| `DONE` | Повторне хешування всього збіглося; `current.json` просунуто |
| `ERROR` | Тяжкий збій; модуль лишається неушкодженим, живі файли відкочено з `rollback/` |
| `DEFERRED` | Завантаження стримане мережевою політикою; план зберігається, відновлюється згодом |

`DONE` досягається **лише** тоді, коли повторне хешування всього збігається, тож журнал ніколи не стверджує, що напівзастосоване оновлення завершене. Збій, обрив мережі чи перезавантаження посеред процесу лишають журнал із можливістю відновлення; `update.sh resume` (або `boot`) продовжує з поточної фази. Див. [[Engine]] щодо набору команд і файлів стану на пристрої.

## Атомарність і відкочення

Ніщо ніколи не перезаписується на місці і ніщо не втрачається:

- **Атомарні записи.** Кожен файл приземляється через тимчасовий (`.vdlu-tmp`) і атомарний `rename` / `mv`, тож читач ніколи не бачить напівзаписаного файлу.
- **Резервна копія перед перезаписом.** Попередній вміст іде в `rollback/<version>/<path>` перед тим, як новий файл перейменовується поверх (зберігаються кілька останніх версій). Якщо застосування провалюється, живі файли відкочуються з резервної копії, а не лишаються зіпсованими. Невдале резервування **перериває** застосування, замість перезапису без страхувальної сітки.
- **Серіалізація.** Блокування на основі `mkdir` (`lock.d/`, оскільки `flock` непрацездатний на toybox, з відновленням застарілого блокування за PID) серіалізує паралельні запуски.

## Принцип "без перезавантаження"

Більшість файлів можна підмінити, поки модуль живий, тож VDLU застосовує їх одразу. Лише три класи потребують перезавантаження, бо живий процес уже відобразив (map) їх у пам'ять: `.so` (завантажений Zygisk), overlay `/system` та `sepolicy.rule`. Вони **ставляться у staged, ніколи не записуються поверх живого inode** і підмінюються за один крок pre-zygote під час наступного завантаження. Повна таксономія та потік завантаження - у [[Reboot Handling]].

## Fail-closed позиція довіри

Feed - єдине, що перетинає шлях від ПК до пристрою, тож рушій трактує кожен його байт як ворожий. `validate_plan()` виконується у фазі DIFF, перед будь-яким завантаженням, і відхиляє весь маніфест за будь-яким спотвореним полем. Перевірка підпису використовує вбудований `ed25519-mini` (на пристрої немає `openssl`), приватний ключ ніколи не торкається ні пристрою, ні CI, а профіль `hardened` є fail-closed за інверсією, тож зіпсоване значення профілю ніколи не зможе тихо прийняти непідписаний feed. Повна модель, два профілі та загрози, на які відповідає кожен, - у [[Security and Trust Model]].

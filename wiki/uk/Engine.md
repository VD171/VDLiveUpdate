# Engine

Рушій - це бік VDLU на пристрої: частина, що працює на телефоні, вирішує, що змінилося, завантажує це й застосовує. Це єдиний скрипт оболонки POSIX, `engine/update.sh`, плюс крихітний перевіряч підпису, `engine/vdlu-verify`. Обидва вбудовуються в модуль-хост у `<module>/vdlu/` і запускаються від root.

Увесь рушій побудований навколо однієї ідеї: оновлення - це **транзакція з можливістю відновлення**. Якщо телефон перезавантажено, процес вбито чи втрачено мережу на півдорозі, наступний запуск продовжує точно з того місця, де зупинився, і модуль ніколи не лишається напівзастосованим, вдаючи, що завершений.

Якщо хочете спочатку велику картину, див. [[Architecture]]. Про те, як оновлення уникають перезавантаження щоразу, коли можуть, див. [[Reboot Handling]].

## Написано для пристрою, а не для вашого ноутбука

`update.sh` - це чистий POSIX `sh`. Він працює під mksh, busybox чи toybox, без суто bash-функцій, і проходить `sh -n`. Це важливо, бо середовище на root-пристрої Android мале й суворе.

Зокрема, тут немає `jq`. VDLU розбирає `manifest.json` малим розплющувачем у стилі gron, написаним на `awk`: він обходить JSON по одному символу й видає рядок `path<TAB>value` на кожен листок (наприклад `files/0/sha256<TAB>ab..` чи `version<TAB>6`). Оболонка тоді читає ці рядки через `grep` та `cut`. Це працює і на компактному, і на гарно оформленому JSON, і ніколи не викликає JSON-інструмент, якого там немає.

Рушій залежить лише від того, що вже постачається з toybox (`sha256sum`, `gzip`/`gunzip`, `base64`, `date`), вбудованого перевіряча `ed25519-mini`, і, для `https://`-feed-ів, малого статичного `curl`, який завантажується й перевіряється один раз. `file://`-feed не потребує `curl` взагалі.

## Шість команд

Ви викликаєте рушій зі шляхами модуля у середовищі та однією командою:

```sh
VDLU_DIR=/data/adb/<mod>/vdlu MODULE_DIR=/data/adb/modules/<mod> MODID=<mod> \
  sh "$MODULE_DIR/vdlu/update.sh" <cmd>
```

Код виходу `0` означає успіх; будь-який інший код означає помилку, причину якої виведено в stderr.

| Команда | Що робить |
|---|---|
| `check` | Diff лише для читання. Завантажує маніфест, порівнює його зі встановленим і друкує однорядкове JSON-зведення: `{"update":bool,"from":N,"to":M,"fetch":K,"reboot":bool}`. Нічого не змінює на диску. Якщо пристрій новіший за feed (заблокований даунґрейд), він звітує `{"update":false,"ahead":true,...}` з кодом виходу `0`, а не помилкою. |
| `run` | Повний живий цикл: DIFF, FETCH, APPLY, COMMIT. Застосовує кожен живий файл одразу й ставить у staged ті небагато файлів класу reboot. Зважає на `cancel`. Пише прогрес у `journal.json`. |
| `resume` | Продовжує перервану транзакцію, починаючи з тієї фази, у якій вона була. Ідемпотентна. Вона **не** підмінює staged-`.so` (це зарезервовано для `boot`). |
| `boot` | Шлях pre-zygote. Виконує `resume`, а тоді підмінює будь-які staged-файли `*.vdlu-new` на місце, закриваючи `PENDING_REBOOT` у `DONE`. Якщо немає незавершеної транзакції, він запускає свіжий цикл і застосовує все, зокрема `.so`, за одне це завантаження. |
| `status` | Друкує `journal.json`, або `{"state":"idle"}`, коли нічого не виконується. |
| `cancel` | Створює маркер `cancel`. Запущений `run` чисто зупиняється в наступній безпечній точці. |

Команда `check` навмисно дешева, тож інтерфейс може повідомити вам про наявність оновлення в будь-якій мережі. Власне завантаження керується окремо (див. фазу fetch нижче).

## Транзакція, крок за кроком

Кожен `run` проходить фіксований скінченний автомат, зафіксований у `journal.json`, щоб WebUI (і ви) могли за ним спостерігати:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> (PENDING_REBOOT | DONE)
```

**DIFF.** Рушій завантажує `manifest.json`, перевіряє кожне поле (див. нижче та [[Security and Trust Model]]) і порівнює підписане цільове дерево з `current.json`, маніфестом уже встановленої версії. Результат - план по файлах, записаний у `plan.tsv`: один рядок на файл, що несе його клас, цільовий хеш, mode та стан прогресу. Файли, що вже на цільовому хеші, позначаються до пропуску.

**FETCH.** Для кожного ще потрібного файлу рушій завантажує його адресований за вмістом blob із `<source>/blobs/<sha>` (або `<sha>.gz`, коли стиснений) у файл `.part`. Якщо blob gzip-нутий, його розпаковують, а тоді його SHA-256 звіряється з маніфестом. Лише при збігу він атомарно `mv`-иться у `blobs/<sha>`. Blob, що вже в кеші з правильним хешем, пропускається повністю, а незмінений локальний файл може засіяти кеш без жодного завантаження. Три невдачі на тому самому blob-і переривають фазу без жодного застосування. Фаза сягає `FETCHED` лише тоді, коли кожен blob у плані наявний і перевірений. Про [[Feed Format]], звідки походять ці blob-и, див. ту сторінку.

Fetch керується мережевою політикою: feed може бути обмежений лише Wi-Fi, лише мобільним або будь-якою мережею. Коли поточна мережа не дозволена, fetch не провалюється; він входить у нешкідливий стан `DEFERRED`, тримає план і ціль закріпленими й відновлюється при наступному check чи boot, щойно з'явиться потрібна мережа. Жодних даних тим часом не витрачається.

**APPLY.** Входить сюди лише з `FETCHED`. Для кожного файлу рушій діє за класом:

- файли `live` та `soft`: зарезервувати поточний файл у `rollback/<version>/<path>`, записати новий вміст у сусідній `.vdlu-tmp`, `chmod` його, перевірити хеш, тоді атомарно `rename` його поверх цілі. Файл, що вже на цільовому хеші, пропускається.
- файли `reboot` (`.so`, overlay `/system`, `sepolicy.rule`): матеріалізувати у `staged/<path>.vdlu-new`. Живий inode тут ніколи не чіпається. Див. [[Reboot Handling]].
- видалення: зарезервувати, тоді видалити. Видалення застосовуються лише в самому кінці, при чистому `DONE`, ніколи поки перезавантаження ще очікується.

**COMMIT.** Рушій повторно хешує кожен live- та soft-файл, якого торкнувся. Лише коли всі вони збігаються, він пише `current.json`, роблячи нову версію базою для diff. Якщо будь-який файл класу reboot було поставлено у staged, стан стає `PENDING_REBOOT`, а не `DONE`; підміна й фінальна повторна перевірка відбуваються згодом під командою `boot`.

## Безпечно за конструкцією

Гарантії, що роблять це безпечним для запуску без нагляду:

- **Ніщо не позначається `DONE` без збіжного повторного хешування.** `DONE` досягається лише після того, як кожен застосований файл прочитано назад і його SHA-256 порівняно з маніфестом. Staged reboot-файл примушує `PENDING_REBOOT`, ніколи не фальшивий `DONE`.
- **Ніщо не втрачається.** Кожен файл резервується у `rollback/<version>/` перед перезаписом, і три останні версії зберігаються. Якщо застосування провалюється, живі файли відкочуються з резервної копії; модуль ніколи не лишається напівзастосованим, брешучи про це. `apply_live` одразу переривається, якщо крок резервування провалився, замість перезапису без шляху назад.
- **Усе атомарно.** Новий вміст приземляється через `rename`/`mv` поверх цілі, тож читач завжди бачить або старий файл, або новий, ніколи не обрізаний запис.
- **З можливістю відновлення після збою чи вбивства.** Збій, втрата мережі чи перезавантаження посеред процесу лишають дійсний журнал; `resume` (або `boot`) продовжує із зафіксованої фази. Конструкція припускає, що її перервуть.
- **Чисто деградує.** Відсутній бінарник, впала мережа чи повний диск дають чітку помилку в stderr та `state:ERROR` у журналі, не псуючи модуль.

## Блокування

Лише одна транзакція може торкатися стану за раз. `flock` ненадійний на toybox, тож VDLU серіалізує каталоговим блокуванням: `mkdir "$VDLU_DIR/lock.d"` вдається рівно одному викликачу й провалюється в решти, що є атомарним на будь-якій осмисленій файловій системі. Застаріле блокування, залишене мертвим процесом, відновлюється перевіркою зафіксованого PID.

Терпляче повторне очікування під час завантаження (використовується, коли пристрій офлайн при boot) **не** тримає цього блокування під час очікування. Воно захоплює й відпускає між спробами, тож ручний `run` ніколи не блокується завантаженням, що чекає на мережу, і воно ніколи не тримає wakelock. Безпечне для батареї за конструкцією. Докладніше про це в [[Reboot Handling]].

## Перевірка підпису: `vdlu-verify`

`vdlu-verify` - це перевіряч підпису на пристрої, навмисно тримається компактним:

```
vdlu-verify <manifest.json> <keyring_dir>
```

Код виходу `0` означає, що підпис маніфесту дійсний відносно публічного ключа з keyring, чий id збігається з `key_id` маніфесту; будь-який інший код - відмова.

Компактним його робить те, що він використовує **жодного `openssl` на пристрої**. Він читає публічний ключ keyring як **сирий 32-байтовий** файл, канонізує маніфест (текст маніфесту з вилученим полем `sig`), хешує його через toybox `sha256sum`, base64-декодує підпис і передає сирий ключ, повідомлення й 64-байтовий підпис вбудованому бінарнику `ed25519-mini`. Перевіряч також відхиляє будь-що спотворене ще до перевірки: відсутній чи порожній `key_id` або `sig`, `key_id` із роздільниками шляху, публічний ключ, що не рівно 32 байти, або підпис, що не рівно 64 байти.

Канонізація байт-у-байт ідентична підписувачу producer, і саме це дає підпису перевірятися між інструментами. Відповідний приватний ключ ніколи не торкається ні пристрою, ні CI; вбудовується лише сирий публічний ключ. Повна історія довіри, два профілі й те, чому `hardened` є fail-closed за інверсією, - у [[Security and Trust Model]].

Рушій викликає `vdlu-verify` під час фази diff. За профілю `hardened` невдала перевірка перериває все оновлення; за `trusted` перевірка best-effort, але хеш кожного blob-а все одно завжди перевіряється, тож зіпсований вміст виловлюється незалежно від профілю.

## Стан на диску

Увесь стан рушія живе в `$VDLU_DIR` (поза каталогом модуля), тож саме дерево модуля завжди містить лише завершені файли:

| Шлях | Роль |
|---|---|
| `config` | налаштування key=value (source, profile, channel, мережева політика, boot retry) |
| `current.json` | маніфест активної версії; це база для diff. Відсутність означає, що оновлень не було |
| `target.json` | закріплений маніфест незавершеної транзакції. Його наявність позначає активну транзакцію; він стає `current.json` при `DONE` |
| `plan.tsv` / `plan.del` | план і прогрес по файлах та список шляхів до видалення |
| `journal.json` | прогрес для WebUI, перезаписується при кожній зміні стану |
| `blobs/<sha256>` | кеш перевіреного, розпакованого оригінального вмісту |
| `rollback/<version>/<path>` | резервні копії перезаписаних файлів; три останні версії зберігаються |
| `staged/<path>.vdlu-new` | файл класу reboot, що очікує підміни при завантаженні |
| `lock.d/` | блокування mkdir |
| `tools/<abi>/curl` | завантажений, перевірений статичний curl; зберігається між оновленнями |
| `cancel` | запит на скасування |

# WebUI

VDLU постачається з необов'язковим віджетом WebUI "вставив і працює": невелика панель "Updates" для WebUI root-менеджера KernelSU чи APatch. Вона дає користувачу кнопку Check, кнопку Update now, живий toast прогресу зі скасуванням, банер перезавантаження та панель налаштувань - і все це без жодного дотику до термінала.

Це **vanilla JavaScript**: без фреймворку, без кроку збірки, без CDN. Три файли:

| Файл | Що це |
|---|---|
| `vdlu.js` | віджет; відкриває `window.VDLU` |
| `vdlu.css` | стилі для toast-а, банера й панелі (темна тема, успадковує CSS-змінні хоста) |
| `demo.html` | окрема сторінка, що мокає міст пристрою, тож увесь інтерфейс працює у звичайному браузері |

Віджет цілком необов'язковий. [[Engine]] чудово працює сам від тригерів завантаження; WebUI - лише приємне обличчя поверх нього. Про підключення його до модуля див. [[Quick Start]].

## Як інтерфейс говорить із рушієм: міст `ksu.exec`

Віджет сам ніколи не робить нічого привілейованого. Він будує команду оболонки й передає її мосту `ksu.exec` root-менеджера, який запускає її від root і повертає stdout / stderr / код виходу. Усе, що показує панель, зчитується назад із файлів, які пише рушій.

Віджет обгортає цей міст в єдину функцію `exec(cmd)`, що повертає `Promise`:

- **resolve** зі stdout, коли команда виходить з 0
- **reject** зі stderr (або `rc=N`) інакше

Кожна команда несе середовище контракту, зібране віджетом:

```
VDLU_DIR=... MODULE_DIR=... MODID=... sh $MODULE_DIR/vdlu/update.sh <cmd>
```

Кілька конкретних викликів:

- **Запустити оновлення:** `update.sh run` запускається у **фоні** (`(... &)`), тож інтерфейс ніколи не блокується довгим завантаженням.
- **Читати прогрес:** легке опитування (приблизно раз на секунду) через `cat $VDLU_DIR/journal.json`.
- **Скасувати:** `touch $VDLU_DIR/cancel` (рушій зупиняється в наступній безпечній точці).
- **Конфіг:** читати й писати `$VDLU_DIR/config` (key=value), зберігаючи порядок і невідомі ключі й торкаючись лише тих ключів, які користувач змінив.

Якщо хост передає власні помічники `exec`, `toast` та `confirm` у `init()`, віджет маршрутизує через власну серіалізовану чергу команд і візуалізацію хоста, тож він виглядає й поводиться як решта того WebUI. Якщо їх опущено, віджет повертається до прямого виклику `ksu.exec` і впорскує власний міні-toast.

## Toast прогресу (зі скасуванням)

Щойно оновлення запущено, віджет показує неблокувальний кутовий toast і опитує `journal.json`. Toast відображає скінченний автомат рушія:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> (PENDING_REBOOT | DONE)
```

Він малює смугу прогресу плюс рядок `phase done/total - current file - bytes` і несе кнопку **Cancel** протягом усього. Кожен термінальний стан отримує власну обробку:

- **DONE** -> зелений toast, "vX applied - all verified".
- **PENDING_REBOOT** -> зелений toast плюс стійкий банер перезавантаження (нижче).
- **ERROR** -> червоний toast із причиною з `journal.error` чи stderr, із пропозицією Retry. Він ніколи не вдає успіху.
- **Cancelled** -> бурштиновий toast, "cancelled - N/M applied, resumable", із пропозицією **Resume**.
- **DEFERRED** -> ніжний синій інфо-toast, "download deferred, waiting for the allowed network". Це нешкідливе очікування мережевої політики, а не помилка; воно відновлюється при наступному check чи boot у потрібній мережі.

Опитування оборонне. Напівзаписаний журнал (рушій пише паралельно) ігнорується для того такту, замість бути хибно розібраним. Якщо журнал зникає після того, як прогрес було видно, це означає, що commit його очистив: віджет звітує DONE. Якщо журнал відсутній від самого початку протягом 8 тактів, він звітує "no response". А якщо журнал застигає на тих самих значеннях протягом 20 тактів, віджет перевіряє `lock.d` рушія: якщо блокування живе, це просто повільний fetch одного blob-а, і toast далі чекає; якщо блокування мертве, запуск помер посеред процесу, тож віджет виводить помилку з кнопкою Resume, замість вічно крутитися на "updating".

## Банер перезавантаження

Деякі файли не можна підмінити на живій системі: `.so`, overlay `/system`, `sepolicy.rule`. Рушій ставить їх у staged і мітить транзакцію `PENDING_REBOOT`. Віджет тоді показує **стійкий верхній банер**: "Reboot to activate the new `.so` (vX)". Він лишається, доки staged-файли не підмінять під час наступного завантаження. При відкритті WebUI банер переоцінюється з журналу, тож користувач, який закриває й знову відкриває інтерфейс, усе одно його бачить. Про те, що відбувається при завантаженні, див. [[Reboot Handling]].

Зауважте, що банер зважає на термінальний стан `PENDING_REBOOT`, а не на прапорець `reboot_pending` (який стає true, щойно будь-який `.so` входить у план). Це тримає банер від появи посеред запуску, перш ніж щось справді поставлено у staged.

## Панель "Updates": незалежні перемикачі по категоріях

`mountUpdatesPanel(el)` рендерить панель налаштувань у порожній `<div>`, який надає хост. Вона має три секції, і кожен елемент керування незалежний і зберігається сам по собі:

**Actions**
- **Check for updates** -> запускає `check`, показує результат вбудовано (актуально / новіше за feed / доступне оновлення з кількістю файлів і міткою reboot).
- **Update now** -> запускає `run` плюс toast прогресу.

**Automation** (незалежні перемикачі, кожен записується в `config` тієї ж миті, коли його перемкнуто)
- **On WebUI open** (`auto_on_webui_open`) -> запустити тихе оновлення, коли інтерфейс відкривається.
- **On reboot** (`auto_on_reboot`) -> застосувати в pre-zygote при завантаженні.
- **Boot retry every (s)** та **Boot retry up to (min)** -> числові поля для повтору fetch-у маніфесту, коли пристрій завантажується офлайн.

**Source**
- `source` (URL feed), `channel` (stable / canary), `profile` (trusted / hardened) та селектор **Network**, що відображається на `net_policy` (Wi-Fi + mobile / Wi-Fi only / mobile only).

Перемикачі й числові поля зберігаються одразу й візуально відкочуються, якщо запис провалився. Текстові поля й селектори в секції Source позначають себе dirty й зберігаються разом по явній кнопці Save. Панель завжди переписує лише ті ключі, яких торкнувся користувач, тож будь-які невідомі чи майбутні ключі конфігу зберігаються.

### Поведінка автовідкриття

`onWebUIOpen()` викликається при завантаженні хоста. Вона оцінює журнал (показуючи банер перезавантаження чи пропонуючи Resume для нетермінальної транзакції, залишеної попередньою сесією), а тоді, якщо `auto_on_webui_open=1`, спершу запускає **тихий** `check()`. Стійкий toast прогресу й власне `run` запускаються лише тоді, коли є реальне завантаження (`update && fetch > 0`). Якщо пристрій актуальний чи випереджає feed, результат показується вбудовано в панелі, і жодного toast-а на екрані не лишається, тож автооновлення так само ненав'язливе, як ручна кнопка.

## i18n (рядки по мовах)

Кожен рядок інтерфейсу типово **англійською**, що є нейтральним вибором для публічних багатомовних модулів. Повна карта ключів живе в об'єкті `DEFAULT_I18N` у `vdlu.js` (також відкрита як `VDLU.i18n`). Хост перевизначає будь-яку підмножину ключів, передавши карту в `init({ i18n: ... })`:

```html
<script src="i18n/pt-BR.js"></script>   <!-- defines window.VDLU_I18N_PT_BR -->
<script>
  VDLU.init({ exec: ex, moduleDir: MOD, vdluDir: VDL, modid: 'x',
              i18n: window.VDLU_I18N_PT_BR });
</script>
```

- **Часткова** карта - це нормально: будь-який відсутній ключ повертається до англійського типового.
- Мітки фаз і станів використовують ключі `ph_<phase>` та `st_<STATE>`; решта - пласкі ключі на кшталт `cancel`, `updateNow`.
- Пропрацьований переклад (`i18n/pt-BR.js`) постачається як шаблон; нова мова - це просто файл `i18n/<lang>.js` тієї ж форми, або хост будує карту зі своєї власної системи i18n.

## demo.html: запустити інтерфейс без пристрою

`demo.html` мокає міст `ksu.exec`, тож ті самі `vdlu.js` та `vdlu.css` працюють у звичайному браузері, без root і без телефона:

```sh
xdg-open webui/demo.html
```

Мок симулює `update.sh` та `journal.json`, що еволюціонує, а його кнопки перемикають між сценаріями: живе оновлення аж до DONE, завершення `reboot_pending`, помилка посеред процесу та запуск, який можна скасувати. Це найшвидший спосіб побачити інтерфейс та ітерувати його, і це те, що ви перевіряєте перед вбудовуванням віджета в модуль.

## Підключення до модуля (тригер відкриття WebUI)

`index.html` хоста завантажує два файли й викликає три функції:

```html
<link rel="stylesheet" href="vdlu.css">
<script src="vdlu.js"></script>
<script>
  VDLU.init({
    moduleDir: '/data/adb/modules/' + MODID,   // $MODULE_DIR (where the engine is vendored)
    vdluDir:   '/data/adb/' + MODID + '/vdlu',  // $VDLU_DIR  (Tier-2 state, outside the module dir)
    modid:     MODID,
    module:    'Demo',        // friendly name shown in the toast (default: modid)
    exec:   ex,               // optional: the host's ksu.exec wrapper
    toast:  toast,            // optional: the host's transient toast
    confirm: askConfirm       // optional: the host's modal
  });

  VDLU.onWebUIOpen();                          // the WebUI-open trigger: banner + auto-update eval
  VDLU.mountUpdatesPanel('b-updates');         // render the "Updates" tab into an empty div
</script>
```

Хосту потрібно лише надати шляхи Tier-2 й виділити один порожній `<div>` для панелі; toast і банер впорскуються у `document.body` віджетом. `onWebUIOpen()` - це тригер відкриття WebUI: саме він оцінює банер перезавантаження, пропонує Resume при перерваній транзакції й запускає тихе автооновлення, коли встановлено `auto_on_webui_open`.

### Єдине джерело, пере-вбудоване байт-у-байт

`vdlu.js` та `vdlu.css` - це **канонічна копія**. Модуль, що вбудовує віджет, пере-вбудовує ці файли незмінними у свій `webroot/`; він ніколи не редагує власну копію на місці. Нова функція народжується в канонічних файлах і стікає вниз через пере-вбудовування. Редагування вбудованої копії породжує тихий дрейф (це вже траплялося: застаріла копія не мала `net_policy`, toast-а DEFERRED та полів boot-retry). Вартовий парності у дереві джерел знаходить кожну копію й мітить чи пере-вбудовує ті, що розійшлися, покриваючи лише віджет; keyring має власний ритм verify-not-copy.

### Публічний API (`window.VDLU`)

| Функція | Робить |
|---|---|
| `init(opts)` | налаштувати віджет; повертає `window.VDLU` |
| `onWebUIOpen()` | викликати при завантаженні: банер, пропозиція Resume й тихе автооновлення |
| `mountUpdatesPanel(el)` | відрендерити панель Updates у `el` (рядок id чи елемент) |
| `check()` | запустити `update.sh check`; `Promise<{update, from, to, fetch, reboot}>` |
| `startUpdate()` | запустити `run` у фоні плюс toast прогресу з Cancel |
| `cancel()` | створити `$VDLU_DIR/cancel` (рушій зупиняється в безпечній точці) |
| `resume()` | відновити поточну транзакцію плюс toast |
| `refreshBanner()` | переоцінити стійкий банер очікуваного перезавантаження |

# Contributing

Внески вітаються. VDLU - це інкрементний рушій самооновлення без перепрошивки,
вбудований у модулі KernelSU / APatch / Magisk. Ця сторінка - практичний робочий процес
розробника; про те, як частини поєднуються, спершу прочитайте [[Architecture]], [[Engine]] та
[[Producer]].

## Ніщо не компілюється

VDLU - це скрипти (POSIX sh, трохи Python на боці випусків, vanilla JS для
WebUI), тож кроку збірки немає. Ви перевіряєте зміну, запускаючи конвеєр
наскрізь і статично перевіряючи кожну частину.

## Спершу контракт шва

Контракт інтерфейсу між компонентами (сигнатури CLI, імена файлів та
JSON-ключі, спільні для рушія, producer та WebUI) - це **закон збіжності**.
Трактуйте його як незмінний. Якщо ваша зміна торкається шва producer-до-рушія
(схема маніфесту, схема журналу, ключі конфігу, правило підпису/канонізації),
**спершу вирівняйте контракт інтерфейсу**, а тоді змініть код з обох боків для збігу.
Зміна з одного боку шва без іншого тихо ламає тих, хто впроваджує.
Про правило канонізації, яке підписувач і перевіряч мають узгодити байт-у-байт, див. [[Producer]].

## Тестуйте наскрізь перед PR

Запускайте producer і рушій разом на одноразовому дереві, тим самим способом, що й
випуск того, хто впроваджує:

```sh
# 1. a signing key
producer/vdlu-keygen demo /tmp/k

# 2. pack a module tree into a feed
producer/vdlu-pack /tmp/tree /tmp/feed demo 1 --version-name v1

# 3. sign the manifest in place
producer/vdlu-sign /tmp/feed/manifest.json /tmp/k/demo.pem demo

# 4. verify the manifest the way the device will (RAW 32B keyring)
engine/vdlu-verify /tmp/feed/manifest.json /tmp/keyring

# 5. drive the engine against the feed (source=file:///tmp/feed in the config)
VDLU_DIR=... MODULE_DIR=... MODID=demo sh engine/update.sh check   # then run / boot
```

Тоді статично перевірте кожен компонент:

```sh
sh -n engine/*.sh            # POSIX sh syntax, must pass
node --check webui/vdlu.js   # WebUI JS syntax
```

І відкрийте `webui/demo.html` у браузері: він мокає міст root-менеджера
(`ksu.exec`), тож ви можете прогнати панель Updates, toast прогресу, скасування
й банер перезавантаження без пристрою. Див. [[WebUI]].

## Внутрішні правила

- **POSIX sh на пристрої.** Жодних bash-конструкцій понад `local`, і жодного `jq`. Воно має
  працювати на toybox / busybox.
- **Безпека неузгоджувана.** Кожне поле маніфесту - ворожий вхід;
  `validate_plan()` лишається fail-closed, а приватний ключ підпису ніколи не торкається
  CI чи пристрою. Не послаблюйте перевірку, аби тест пройшов.
- **Суворість при збої.** Тримайте транзакцію з можливістю відновлення: ніщо не звітує "done"
  без збіжного повторного хешування, ніщо не перезаписується без резервної копії, а
  apply лишаються атомарними.
- **Завжди якість випуску.** Тримайте коментарі стислими; жодних зайвих коментарів.
- **Одна логічна зміна на PR.** Скажіть, що змінилося й чому.

## Створення issue

Відкрийте issue з описом того, що ви зробили, чого очікували й що сталося.
Для бага включіть id модуля, профіль джерела (`hardened` чи `trusted`),
команду `update.sh`, яку ви запускали, та відповідний `journal.json` (він записує
фазу, стан і помилку). Для функції скажіть, якого компонента вона торкається (рушій,
producer чи WebUI), щоб вплив на шов був ясним від початку.

# Security and Trust Model

VDLU 以 root 身份、通过网络、就地更新一个模块。这是对准一个来自 feed 的文件的大量权力，因此整个引擎建立在一个单一假设之上：

> **清单中的每个字段都是敌对输入。**

一个 feed 可以在源头被投毒，也可以在传输途中被一个 MITM 调包并篡改。当这发生时，清单仍然以清单的样子到达：它承载着文件路径、`sha256` 字符串、一个 `delete[]` 列表、mode、class 和一个编码标志。VDLU 不把其中任何一项当作可信的。它在下载哪怕一个字节之前就校验整个计划，而且它绝不让一个清单值到达 shell。

本页是完整的信任叙述。它所校验的清单模式见 [[Feed Format]]，而这些检查在 DIFF -> FETCH -> APPLY -> COMMIT 事务中位于何处见 [[Engine]]。

## 核心理念：故障即关闭，先于任何事情发生

`validate_plan()` 在 `check`/diff 阶段内运行，**先于**任何 fetch 且**先于**任何 apply。它遍历计划文件树中的每个条目以及 `delete[]` 中的每个条目，如果有任何单个条目是畸形的，它就**拒绝整个清单**，事务永不开始。没有部分接受，没有"跳过坏的、应用其余的"。一个坏字段毒害整批，这是故意的。

一个清单只有在**每个**条目的以下**所有**条件都成立时才被接受：

| 字段 | 规则 | 为什么 |
|---|---|---|
| `path` | 非绝对路径，无 `..` 组件，无 `.` 组件，无前导 `./`，无内嵌的 `/./`，无尾部斜杠，无控制字符（tab / newline） | 路径必须留在 `MODULE_DIR` 内；一个绝对路径或 `..` 路径就是随处写入 |
| `sha256` | 精确匹配 `^[0-9a-f]{64}$` | 一个非十六进制的 sha 否则会被插值进一个 shell 路径；它是内容地址，因此必须是一个纯十六进制摘要、别无其他 |
| `mode` | 仅八进制（`[0-7]`） | 一个 mode 字符串会成为一个 `chmod` 参数 |
| `size` | 仅数字，且 `<=` 引擎的尺寸上限 | 限定下载与解压 |
| `class` | 精确为 `live`、`soft` 或 `reboot` | class 决定一个文件是实时应用还是为 reboot 被 staged |
| `enc` | 精确为 `raw` 或 `gz` | 编码决定 blob 是否被 gunzip |
| `delete[]` 条目 | 与上面相同的路径规则 | 一个 `delete[]` 条目驱动一次移除；一个未检查的 `..` 会是在树外的 `rm` |

由于这先运行，一个被投毒的清单永远无法写到模块之外，永远无法删除到模块之外，也永远无法把一个非十六进制 token 注入一条命令行。

### 清单值从不接触 shell

规则的后半部分：即使在一个值通过校验之后，它也绝不会被插值进 `sh`，也绝不会被喂给 `awk system()`。check 命令被刻意重写为不含任何 `system()` 调用。按内容寻址完成其余工作：一个 blob 按其 `sha256` 被拉取，写入一个以同一个 `sha256` 命名的缓存路径，而下载的字节在任何内容被应用之前会被重新哈希并比较。一个不是干净的 64 位十六进制摘要的值永远走不了那么远，因为 `validate_plan()` 已经拒绝了它。

### apply 时的第二道防线

`validate_plan()` 在**词法上（lexically）**拦截 `..`，但一个树内已存在的符号链接仍可能把一次写入重定向。因此在 apply 时，`contained()` 解析真实的目标路径并确认它位于模块基址之下，在无法解析时故障即关闭。写入是原子的（写入一个临时名字，然后 `rename` 覆盖目标），而且每一次覆盖都会先备份到 `rollback/`；一次失败的备份会中止 apply，而不是在没有安全网的情况下覆盖。

## 两个配置档

VDLU 运行在两个信任配置档之一，由配置中的 `profile=` 设置。

### `hardened`（公开默认）

- **签名是强制的。**清单必须携带一个来自设备 keyring 中某个密钥的有效 ed25519 签名，否则事务中止。
- **降级被阻止。**一个 `version` 低于已安装版本的清单会被拒绝。攻击者无法把你回退到一个已知存在漏洞的构建。
- 这是任何通过 `https://` 向公众分发的模块所用的配置档。

### `trusted`（私有、经 SSH staged 的源）

- 签名验证是**尽力而为（best-effort）**：源是一个你所控制的私有 `file://` 或经 SSH staged 的 feed，因此一个缺失或无法验证的签名不会硬性中止。
- **但每个 blob 的 `sha256` 始终仍会被校验。**`trusted` 放松的是*谁签了清单*，绝不是*字节是否与计划匹配*。内容完整性在两个配置档中都不可商量。

---

## 通过反向判断实现故障即关闭

这是微妙的部分，也是大多数系统弄错的部分。

`trusted` 是**唯一**选择进入放松验证的字符串。引擎不测试"这是 `hardened` 吗？"它测试"这是**不是** `trusted` 吗？"：

```sh
prof=$(cfg profile hardened | tr -d '[:space:]')
...
if [ "$prof" != trusted ]; then
    # signature mandatory
fi
```

因此，任何**除了**字面 `trusted` 之外的东西都解析为 hardened 行为：

- 该行完全缺失 -> hardened
- 一个像 `hardend` 的笔误 -> hardened
- 带尾部空格的 `trusted `，或来自 CRLF 的 `\r` -> hardened
- 大小写错误的 `Trusted` -> hardened
- 一个被 MITM 篡改的值 -> hardened

一个较早的版本把一个*缺失*的行默认为 hardened，这仍然让一个被损坏的*值*穿透到开放路径。那是一个 fail-open：一个被篡改的配置档字符串可能悄悄接受一个未签名的清单，而一个未签名的清单意味着一个在 MITM 下被调包进来的、由攻击者提供的 `.so`，这就是 root 级别的远程代码执行。反向判断把它堵上了。得到放松验证的唯一方式是精确拼出 `trusted`，而即便如此，blob 哈希仍会被校验。引擎永远不会离接受未签名代码只差一个笔误。（`tr -d` 剥除杂散空白，这样一个带马虎空格的合法 `trusted` 不会被错误拒绝，同时又不重新打开那个漏洞。）

**这个测试是承重的。它必须保持 `!= trusted`，并且永远不能变成 `== hardened`。**

## 清单被绑定到模块

一个发布密钥签署许多模块。因此一个为*不同*模块有效签名的清单，原则上可能被提供给这一个（一次 feed 配置错误、一次源调包，或一次 MITM 重定向），而它的签名会通过校验。

VDLU 用一个绑定来堵住这一点：清单内部已签名的 `module` 字段必须等于本安装的 `MODID`，否则清单会被作为一个跨模块 feed 拒绝。由于 `module` 位于已签名的规范化形式内部，攻击者无法在不破坏签名的情况下更改它。一个为模块 B 有效签名的 feed 就是无法应用到模块 A。

## 精简的设备端校验器

设备上的验证使用 **ed25519-mini**，一个建立在 TweetNaCl（公有领域）之上、微小的仅验证校验器。**设备上没有 `openssl`。**

- keyring 条目是**原始 32 字节公钥**，存储为 `keyring/<key_id>.pub`。（PEM 公钥只是一个 PC 端产物；把一个 PEM 复制进设备 keyring 会破坏验证，因为校验器期望恰好 32 个原始字节。）
- `vdlu-verify <manifest.json> <keyring_dir>` 重建规范化形式（去掉 `sig` 字段的清单文本，紧凑、键已排序），把它哈希成签名所覆盖的 64 字符十六进制消息，解码 base64 签名，检查它是 64 字节，并向 `ed25519-mini <pub32> <msg> <sig64>` 询问一个裁决。rc 0 = 有效，其他任何值 = 拒绝。
- 该二进制按每个 ABI（arm64-v8a、armeabi-v7a、x86、x86_64）是静态的，并带一个 `PROVENANCE.json` 固定确切的 TweetNaCl 源码、包装器哈希和构建标志，因此以 root 运行的那个东西是可审计的。
- 来自清单的 `key_id` 本身在被用于挑选一个 keyring 文件之前会被净化（无 `/`、无 `..`、无引号），因此它无法逃出 keyring 目录。

### keyring 仅经刷入、verify-not-copy、稳定

keyring 在刷入时交付在模块内部，不会被更新引擎重写。在重新内嵌时，规则是 **verify，不 copy**：keyring 只在一次刻意的密钥轮换时更改，绝不作为一次更新的副作用。

### 密钥轮换不会砖掉较旧的安装

当一个签名密钥被轮换时，keyring 会交付**当前和先前两个原始公钥**。校验器按清单的 `key_id` 选择密钥文件，因此一个仍由旧密钥签名的 feed 会相对于旧 pubkey 验证，而一个由新密钥签名的 feed 会相对于新的验证。一台尚未更新越过轮换的设备会继续工作；没有任何东西被搁浅。

## 模块更新 key_id 允许列表

密钥轮换本就意味着 keyring 可以合法地持有不止一个密钥，而一个模块还可能出于第二个原因持有不止一个：它可能交付一个较低信任的密钥，用来签名一个*不同的* feed。指纹 feed 正是这种情况。一个模块可以携带一个狭窄的密钥，它唯一的工作就是签名一个指纹 feed，就坐在同一个 keyring 里、紧挨着签名模块本身的 release 密钥。

这提出了一个仅凭轮换故事无法回答的问题：一旦两个密钥同处 keyring 之中，其中*哪一个*被允许签名一次**模块更新**？模块更新是清单能请求的最强有力的事情，因为它重写设备以 root 身份运行的文件。校验器过去会挑选清单 `key_id` 所指名的 pubkey，并接受任何恰好存在于 keyring 中的密钥。于是那个较低信任的指纹 feed 密钥，一旦泄露，就能签名一个模块更新清单，而设备会认可它。这是一次信任根绕过：一个本为单一狭窄工作而设的密钥，竟能驱动一次完整的 flashless root 更新。

此修复把所接受的模块更新 `key_id` 钉定到一个故障即关闭的**允许列表**，在 pubkey 被选择*之前*就加以检查。配置键是 `key_id`，引擎如此解析它：

- **单密钥 keyring 自动钉定那一个密钥。**常见情形完全不需要配置：如果 keyring 恰好持有一个密钥，那个密钥*就是*允许列表，再无他物能签名一次模块更新。
- **多密钥 keyring 必须设置 `key_id`。**第二个密钥一出现，引擎就拒绝猜测。它以 "multiple keys in keyring; config must pin key_id" 故障即关闭，直到配置指名那个（或多个，在轮换窗口期内以逗号分隔的）可以签名模块更新的密钥。

由于该检查在 pubkey 选择之前运行，一个指名了存在但不在允许列表中的密钥的清单会被拒绝，而校验器根本不会加载那个密钥。解析出的集合通过 `VDLU_KEYID_ALLOW` 镜像进 `vdlu-verify`，于是精简的设备端校验器强制同一个钉定，二者不会分歧。这在**两个**配置档中都成立：`hardened` 和 `trusted` 都会查阅允许列表，因为允许列表决定的是*哪个密钥*是有效的模块更新根，而不是*是否*需要一个签名。

指纹 feed 保留它自己独立的、钉定的信任根，`FEED_KEY_ID`。它是一个独立的根、负有独立的工作，永远无法经由上述模块更新路径到达，因此钉定模块更新允许列表并不触及它，而一个泄露的 feed 密钥仍然无法签名一次模块更新。此项改动把 `ENGINE_VERSION` 提升到 4。

## tools-manifest 堵住了什么

精简的 fetch 引导程序在首次使用时为那些不自带 `curl` 的模块下载一个静态 `curl`。由于那个二进制以 root 运行，它自己的清单签名（ed25519-mini）和它的哈希在**任何配置档中都是强制的**，包括 `trusted`，在它被安装或执行之前。webview 只是传输；信任来自设备上的签名和哈希检查，绝不来自一次下载成功这一事实。

## 攻击者不能做什么

即便拥有 feed，或作为一个完全的 MITM 坐在链路上，攻击者也不能：

- **写到模块之外。**绝对路径、`..`、`.`、控制字符和尾部斜杠都在任何 apply 之前被拒绝，而符号链接重定向在 apply 时会再次被抓住。
- **删除到模块之外。**`delete[]` 条目通过相同的路径校验。
- **注入一条命令。**没有任何清单值被插值进一个 shell 或 `awk system()`；`sha256` 必须是纯 64 位十六进制，否则整个清单被拒绝。
- **向一个公开安装交付未签名代码。**`hardened` 使签名成为强制的，而配置档通过反向判断故障即关闭，因此没有笔误或被篡改的值能降低它。
- **用一个较低信任的密钥签名一次模块更新。**模块更新 `key_id` 被钉定到一个故障即关闭的允许列表，在 pubkey 被选择之前就加以检查，因此一个与之共享 keyring 的、泄露的指纹 feed 密钥无法签名一次完整的 root 更新。
- **在此处提供另一个模块的已签名 feed。**已签名的 `module` 字段必须等于这个 `MODID`。
- **把你回退。**在 `hardened` 中降级被阻止。
- **不被察觉地损坏一个 blob。**每个下载的 blob 在两个配置档中都相对于清单的 `sha256` 被重新哈希；三次尝试之后的不匹配会中止该阶段，不应用任何内容。
- **调包进一个假冒的 root 拉取器。**被引导的 `curl` 在被安装或运行之前，在每个配置档中都经过签名和哈希检查。
- **半应用一个损坏的更新。**事务只有在对一切的一次重新哈希匹配时才到达 `DONE`；一次失败的 apply 会回滚，而不是在没有备份的情况下覆盖。

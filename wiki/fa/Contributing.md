# Contributing

مشارکت‌ها خوش‌آمدند. VDLU یک موتور به‌روزرسانی خودکار، افزایشی و بدون فلش است که
در ماژول‌های KernelSU / APatch / Magisk جاسازی می‌شود. این صفحه جریان کاری عملی توسعه
است؛ برای اینکه قطعات چگونه کنار هم قرار می‌گیرند، ابتدا [[Architecture]]، [[Engine]] و
[[Producer]] را بخوانید.

## هیچ‌چیز کامپایل نمی‌شود

VDLU اسکریپت است (`sh` POSIX، کمی Python در سمت انتشار، JS ساده برای
WebUI)، بنابراین هیچ گام build وجود ندارد. یک تغییر را با اجرای خط لوله
سر تا ته و با بررسی ایستای هر قطعه تأیید می‌کنید.

## ابتدا قرارداد درز

قرارداد رابط میان مؤلفه‌ها (امضاهای CLI، نام‌های فایل و
کلیدهای JSON مشترک میان موتور، تولیدکننده و WebUI) **قانون
همگرایی** است. آن را تغییرناپذیر تلقی کنید. اگر تغییر شما درز
تولیدکننده-به-موتور را لمس می‌کند (شِمای مانیفست، شِمای ژورنال، کلیدهای config،
قاعده امضا/کانونیک‌سازی)، **ابتدا قرارداد رابط را هم‌تراز کنید**، سپس
کد را در هر دو سمت تغییر دهید تا مطابقت کند. یک تغییر در یک سمت درز بدون
سمت دیگر به‌خاموشی پذیرندگان را می‌شکند. برای قاعده کانونیک‌سازی که امضاکننده و
تأیید‌کننده باید بایت‌به‌بایت روی آن توافق کنند ببینید [[Producer]].

## پیش از یک PR سر تا ته آزمایش کنید

تولیدکننده و موتور را با هم روی یک درخت دورریختنی اجرا کنید، به همان روشی که
انتشار یک پذیرنده انجام می‌دهد:

```sh
# 1. a signing key
producer/vdlu-keygen demo /tmp/k

# 2. pack a module tree into a feed
producer/vdlu-pack /tmp/tree /tmp/feed demo 1 --version-name v1

# 3. sign the manifest in place
producer/vdlu-sign /tmp/feed/manifest.json /tmp/k/demo.pem demo

# 4. verify the manifest the way the device will (RAW 32B keyring)
engine/vdlu-verify /tmp/feed/manifest.json /tmp/keyring

# 5. drive the engine against the feed (source=file:///tmp/feed in the config)
VDLU_DIR=... MODULE_DIR=... MODID=demo sh engine/update.sh check   # then run / boot
```

سپس هر مؤلفه را به‌صورت ایستا بررسی کنید:

```sh
sh -n engine/*.sh            # POSIX sh syntax, must pass
node --check webui/vdlu.js   # WebUI JS syntax
```

و `webui/demo.html` را در یک مرورگر باز کنید: پل مدیر روت
(`ksu.exec`) را شبیه‌سازی می‌کند، بنابراین می‌توانید پنل Updates، toast پیشرفت، لغو
و بنر ریبوت را بدون دستگاه تمرین دهید. ببینید [[WebUI]].

## قوانین خانه

- **`sh` POSIX روی دستگاه.** بدون bashایسم فراتر از `local`، و بدون `jq`. باید
  روی toybox / busybox اجرا شود.
- **امنیت غیرقابل‌مذاکره است.** هر فیلد مانیفست ورودی خصمانه است؛
  `validate_plan()` fail-closed می‌ماند، و کلید امضای خصوصی هرگز به
  CI یا یک دستگاه دست نمی‌زند. یک بررسی را برای گذراندن یک آزمون سست نکنید.
- **سخت‌گیری در شکست.** تراکنش را قابل‌ازسرگیری نگه دارید: هیچ‌چیز بدون یک re-hash مطابق
  «done» گزارش نمی‌کند، هیچ‌چیز بدون یک پشتیبان بازنویسی نمی‌شود، و
  applyها اتمیک می‌مانند.
- **همیشه کیفیت نسخه.** کامنت‌ها را موجز نگه دارید؛ بدون کامنت‌های بیهوده.
- **یک تغییر منطقی به‌ازای هر PR.** بگویید چه تغییر کرده و چرا.

## ثبت issueها

یک issue باز کنید که توصیف می‌کند چه کردید، چه انتظار داشتید، و چه رخ داد.
برای یک باگ، id ماژول، پروفایل منبع (`hardened` یا `trusted`)،
دستور `update.sh` که اجرا کردید، و `journal.json` مربوط را بگنجانید (فاز،
حالت و خطا را ثبت می‌کند). برای یک ویژگی، بگویید کدام مؤلفه را لمس می‌کند (موتور،
تولیدکننده، یا WebUI) تا تأثیر درز از همان ابتدا روشن باشد.

# Feed Format

**feed** چیزی است که VDLU روی سیم سرو می‌کند و چیزی است که دستگاه از آن به‌روز می‌شود. یک دایرکتوری ایستای ساده است، که توسط هر چیزی قابل‌سرو است (GitHub Pages، یک هدف rsync، یک مسیر `file://`):

```
<source>/
  manifest.json          # the signed description of the current release
  blobs/<sha256>         # one blob per distinct file content
  blobs/<sha256>.gz      # (when the blob is stored gzipped)
```

خود ماژول نیز یک فایل اضافی، `baseline.json`، را درون `.zip` عرضه می‌کند (که از feed سرو نمی‌شود). تولیدکننده‌ای که همه این‌ها را می‌سازد در [[Producer]] توصیف شده؛ این صفحه قرارداد روی-سیم است.

## manifest.json

مانیفست توصیف کامل یک نسخه است: هر فایل در درخت هدف، چه چیزی باید حذف شود، و امضا روی کل آن.

```json
{
  "schema": 1,
  "module": "demo",
  "version": 106,
  "version_name": "v106",
  "built": "2026-11-19T12:00:00Z",
  "engine_min": 5,
  "channel": "stable",
  "key_id": "release-2026",
  "files": [
    {
      "path": "webroot/index.html",
      "sha256": "<hex64>",
      "size": 1234,
      "mode": "0644",
      "enc": "raw",
      "class": "live"
    }
  ],
  "delete": ["webroot/old.html"],
  "sig": "<base64>"
}
```

### فیلدها

| فیلد | معنا |
|---|---|
| `schema` | نسخه فرمت خود مانیفست (در حال حاضر `1`). |
| `module` | id ماژول. دستگاه اگر با id ماژول خودش مطابقت نکند مانیفست را رد می‌کند، بنابراین یک feed که به‌درستی برای یک ماژول متفاوت امضا شده نمی‌تواند به‌جای آن سرو شود. |
| `version` | نسخه صحیح. موتور فقط رو به جلو به‌روز می‌کند؛ یک feed قدیمی‌تر از دستگاه یک حالت خوش‌خیم «ahead» است، نه یک خطا. |
| `version_name` | رشته نسخه خوانا برای انسان (برای مثال `v106`). |
| `built` | برچسب زمانی build به‌صورت ISO 8601. برای بازتولیدپذیری به `SOURCE_DATE_EPOCH` احترام می‌گذارد. |
| `engine_min` | حداقل نسخه موتور لازم برای اعمال این مانیفست. |
| `channel` | کانال نسخه (برای مثال `stable`). |
| `key_id` | کدام کلید در keyring دستگاه این مانیفست را امضا کرده. کلید عمومی را برای تأیید انتخاب می‌کند، و باید در فهرست مجاز به‌روزرسانی ماژولِ موتور باشد (ببینید [[Security and Trust Model]])؛ کلیدی که صرفاً در keyring حاضر است اما در فهرست مجاز نیست پیش از آنکه pubkey آن بارگذاری شود رد می‌شود. |
| `files[]` | درخت هدف **کامل** (نه یک diff). هر ورودی: `path`، `sha256`، `size`، `mode`، `enc` (`raw`/`gz`)، `class` (`live`/`soft`/`reboot`). |
| `delete[]` | مسیرهایی که در نسخه قبلی حاضر بودند اما اکنون رفته‌اند، برای اینکه دستگاه آن‌ها را حذف کند. |
| `sig` | امضای ed25519، base64. کانونیک‌سازی را در پایین ببینید. |

`files[]` **کل** درخت را توصیف می‌کند، نه یک دلتا را. دستگاه دلتا را خودش با مقایسه مانیفست با آنچه از پیش دارد محاسبه می‌کند، و فقط blobهایی را که `sha256` آن‌ها را گم دارد دریافت می‌کند. `sha256` همیشه متعلق به محتوای اصلی (فشرده‌نشده) است؛ `enc` فقط می‌گوید آن blob چگونه در `blobs/` ذخیره شده است. معنای `class` و اینکه دستگاه با هر مقدار چه می‌کند در [[Reboot Handling]] پوشش داده شده است.

## کانونیک‌سازی (بایت‌های امضاشده)

این مهم‌ترین تغییرناپذیر در این فرمت است. امضاکننده PC و تأیید‌کننده دستگاه روی runtimeهای کاملاً متفاوت اجرا می‌شوند (openssl روی PC، toybox + یک تأیید‌کننده جاسازی‌شده کوچک روی دستگاه، و **اصلاً هیچ کتابخانه JSON** روی دستگاه). با این حال باید دقیقاً همان بایت‌ها را برای امضا و برای تأیید استخراج کنند. بنابراین قاعده یک **تبدیل بایتی** عمدی است، نه یک سریال‌سازی مجدد JSON.

**گام ۱: یک فرم ذخیره ثابت.** `vdlu-pack`، `manifest.json` را فشرده، با کلیدهای مرتب‌شده، UTF-8، که همیشه `key_id` و `sig` را شامل می‌شود (به‌صورت رشته‌های خالی تا امضا شود) می‌نویسد:

```
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

**گام ۲: فقط `sig` را بردارید.** فرم کانونیک همان متن دقیق است با **فقط فیلد `"sig"` حذف‌شده**. چون کلیدها مرتب‌اند، `sig` همیشه به‌صورت `,"sig":"<value>",` ظاهر می‌شود که با `"schema"` پیش از آن و `"version"` پس از آن (هر دو همیشه حاضر) محصور شده، بنابراین حذف آن متنی خوش‌شکل باقی می‌گذارد. JSON هر `"` درون یک مقدار رشته‌ای را به‌صورت `\"` فرار می‌دهد، بنابراین token ساختاری `"sig":"` حتی در برابر یک نام فایل که به‌طور واقعی حاوی `"sig":"` است بدون‌ابهام است.

حذف مشتی از بسط‌های پارامتر POSIX است، یکسان در امضاکننده و تأیید‌کننده، بدون `sed` و بدون `jq`:

```sh
# $1 = the full manifest text
_pre=${_c%%\"sig\":\"*}     # up to  ...,"schema":N,
_rest=${_c#*\"sig\":\"}      # after "sig":"
_tail=${_rest#*\",}          # after <value>",  ->  "version":...
printf '%s%s' "$_pre" "$_tail" | sha256sum | cut -d' ' -f1
```

**گام ۳: hash آن را امضا کنید.** پیام امضا/تأییدشده **sha256 hex** (۶۴ کاراکتر ASCII، بدون newline) فرم کانونیک است. ed25519 آن hex را امضا می‌کند.

دو پیامد با طراحی از این بیرون می‌آیند:

- `key_id` بخشی از فرم کانونیک است (فقط `sig` برداشته می‌شود). `vdlu-sign`، `key_id` را **پیش** از hash تنظیم می‌کند، بنابراین هویت کلید توسط امضا پوشش داده می‌شود.
- چه جانگهدار `sig` خالی باشد (`"sig":""`، در زمان امضا) چه پر (در زمان تأیید)، برداشتن آن همان بایت‌های کانونیک یکسان را می‌دهد. امضا و تأیید به‌طور خودکار توافق دارند.

دو ابزار sh POSIX معتبرند. یک معادل Python، `re.sub(r'"sig":"[^"]*",', '', text, count=1)` سپس sha256، فقط برای بررسی متقابل آن‌ها وجود دارد.

استدلال اعتماد پیرامون همه این‌ها (اینکه چرا تأیید روی دستگاه است، اینکه چگونه `hardened` به‌صورت بسته شکست می‌خورد) در [[Security and Trust Model]] زندگی می‌کند.

## baseline.json (بذر نصب)

وقتی یک ماژول تازه نصب می‌شود، باید از پیش برای نسخه عرضه‌شده خودش «به‌روز» باشد، بدون یک به‌روزرسانی خودکار غیرضروری نسخه‌ای که همین حالا نصب کرده. این همان کاری است که `baseline.json` انجام می‌دهد.

`baseline.json` **درون زیپ ماژول** (در `vdlu/baseline.json`) عرضه می‌شود، نه روی feed. در یک نصب تازه، موتور رکورد «نسخه فعال» خود را از آن بذر می‌دهد، بنابراین دستگاه به‌روز متولد می‌شود، بدون `from:0` و بدون دریافت مجدد آنچه از پیش دارد.

ویژگی‌های کلیدی:

- یک **کپی بدون‌کلید از مانیفست امضاشده** برای نسخه عرضه‌شده است: همان خروجی `vdlu-pack`، که امضانشده مانده (`key_id` و `sig` خالی می‌مانند).
- **تأیید نمی‌شود.** موتور آن را به‌عنوان یک بذر محلی قابل‌اعتماد تلقی می‌کند چون درون زیپ فلش‌شده رسیده، که مرز اعتماد نصب است. فقط یک مانیفست که *از feed دریافت شده* از تأیید امضا عبور می‌کند.
- چون به امضا نیاز ندارد، **CI می‌تواند آن را بدون‌کلید تولید کند**، که همان چیزی است که کلید امضا را کاملاً بیرون از CI نگه می‌دارد (ببینید [[Producer]]).
- `vdlu-pack`، **`baseline.json` را از مانیفست خودش حذف می‌کند**، بنابراین مانیفست هرگز به baseline ارجاع نمی‌دهد (آن یک حلقه خودارجاعی می‌بود: مانیفست به baseline به مانیفست).
- اگر غایب باشد **غیرکشنده** است. بدون آن، دستگاه به‌سادگی در اولین به‌روزرسانی خود از `from:0` شروع می‌کند و آنچه را لازم دارد دریافت می‌کند. هرگز خراب نیست، فقط کمتر بهینه.

## Blobs

هر محتوای فایل متمایز یک blob زیر `blobs/` است، که با **sha256 محتوای اصلی** نام‌گذاری می‌شود:

- `blobs/<sha256>` برای یک blob خام.
- `blobs/<sha256>.gz` برای یک blob فشرده‌شده با gzip (gzip فقط زمانی نگه داشته می‌شود که فایل دست‌کم ۴۰۹۶ بایت باشد و فشرده‌سازی دست‌کم ۱۰ درصد صرفه‌جویی کند).

یک blob یک‌بار، در یک فرمت، ذخیره می‌شود. آدرس‌دهی بر اساس محتوا حذف تکرار را رایگان می‌دهد: محتوای بدون تغییر، مشترک یا بازگردانده‌شده به یک blob که از پیش وجود دارد نگاشت می‌شود، بنابراین feed فقط با محتوای واقعاً جدید رشد می‌کند، و دستگاه فقط hashهایی را که گم دارد دانلود می‌کند. دستگاه `sha256` هر blob دانلودشده را (پس از از‌فشرده‌خارج‌کردن یک blob `gz`) پیش از استفاده با مانیفست بررسی می‌کند.

## چه چیزی از feed حذف شده، و چرا

feed **فقط محتوای خود ماژول** را حمل می‌کند. مجموعه ثابتی از مسیرها عمداً از آن بیرون نگه داشته می‌شوند. `vdlu-pack` یک محمول حذف را هم هنگام پیمایش درخت و هم هنگام محاسبه `delete[]` اعمال می‌کند.

| حذف‌شده | چرا |
|---|---|
| `vdlu/keyring/`, `vdlu/verify/` (ریشه اعتماد: کلیدهای عمومی خام + باینری تأیید‌کننده) | **این دلیل امنیتی اصلی است.** لنگر اعتماد **فقط-فلش** است. اگر keyring یا تأیید‌کننده از طریق feed قابل‌تحویل بودند، یک مانیفست می‌توانست همان چیزی را که آن را اعتبارسنجی می‌کند بازنویسی کند. نگه‌داشتن آن‌ها بیرون از سیم یعنی یک مانیفست هرگز نمی‌تواند لنگر اعتماد روی دستگاه را بازنویسی کند. به‌عنوان یک نگهبان دوم و مستقل (`ENGINE_VERSION` 5)، موتور همچنین هر مسیر `vdlu/` را در یک برنامه دریافت‌شده **نادیده می‌گیرد**، بنابراین حتی یک feed که آن‌ها را حمل کند نمی‌تواند به لنگر دست بزند. |
| `vdlu/baseline.json` | یک کپی از مانیفست امضاشده است (بذر نصب)؛ بسته‌بندی آن یک حلقه خودارجاعی می‌بود. |
| `.vd/` زیرساخت فلش | داربست دروازه فلش که در زیپ عرضه می‌شود، هرگز زنده اعمال نمی‌شود. |
| `update.json`, `update-mmrl.json` | size/sha آن‌ها توسط CI *پس از* ساخته‌شدن زیپ‌ها پر می‌شود، بنابراین کپی عرضه‌شده با هر کپی feed فرق دارد. تغذیه آن‌ها یک fetch شبح‌وار تک‌فایلی در اولین به‌روزرسانی خودکار هر نصب ایجاد می‌کرد، و به‌هرحال روی دستگاه بازمانده‌اند (مدیر، JSON به‌روزرسانی خام راه دور را می‌خواند). |
| `META-INF/`, `customize.sh` (داربست نصب‌کننده) | توسط مدیر در زمان **فلش** مصرف می‌شوند و در ماژول نصب‌شده نگه داشته نمی‌شوند. محتوای VDLU نیستند؛ سرو آن‌ها blobها را هدر می‌دهد و، اگر یکی هرگز میان نسخه‌ها تغییر می‌کرد، به‌عنوان یک فایل نصب‌کننده در دایرکتوری ماژول زنده نوشته می‌شد. |
| همتایان `.sha256` به‌ازای هر فایل | فقط به زیپ قابل‌فلش تعلق دارند، پس از یک به‌روزرسانی افزایشی کهنه می‌شوند، و مانیفست را دو برابر می‌کردند. |
| فایل‌های dev/doc (`RELEASE.md`, `CLAUDE.md`, `.gitignore`) | هرگز به دستگاه عرضه نمی‌شوند؛ سرو آن‌ها blobها را هدر می‌دهد و مانیفست امضاشده را در هر ویرایش doc می‌چرخاند. |

استدلال پشت حذف ریشه اعتماد در [[Security and Trust Model]] گسترش یافته است.

## معنای delete[]

`delete[]` به دستگاه می‌گوید کدام مسیرها را حذف کند، تا فایلی که میان نسخه‌ها رها شده روی دستگاه به‌عنوان یک یتیم باقی نماند. با پاس‌دادن `--prev <manifest.json قبلی>` به `vdlu-pack` محاسبه می‌شود: مسیری که در نسخه قبلی بود و در نسخه فعلی نیست یک ورودی حذف می‌شود.

قاعده مهم: **مسیرهای حذف‌شده هرگز به‌عنوان حذف تولید نمی‌شوند، حتی با `--prev`.** هر مسیر قبلی از همان محمول حذف که هنگام پیمایش درخت استفاده شده عبور می‌کند. اگر یک `--prev` به یک مانیفست قدیمی‌تر اشاره کند که هنوز مسیرهای اکنون‌حذف‌شده را فهرست کرده بود (یک `baseline.json` سرگردان، `META-INF/*`، یک ورودی keyring، و الی آخر)، آن مسیرها به ورودی‌های حذف **تبدیل نمی‌شوند**. یک مسیر حذف‌شده هرگز محتوای feed نبوده، بنابراین حذف آن کار VDLU نیست، و به دستگاه هرگز دستور داده نمی‌شود فایلی را که از طریق feed سرو نشده بردارد. این همان چیزی است که مانع می‌شود فهرست حذف هرگز به‌عنوان یک دستور مخرب به عقب برگردد.

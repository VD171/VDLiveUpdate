# WebUI

VDLU มาพร้อมวิดเจ็ต WebUI แบบ drop-in ที่เป็นทางเลือก: แผง "Updates" เล็ก ๆ สำหรับ WebUI โปรแกรมจัดการ root ของ KernelSU หรือ APatch มันให้ผู้ใช้มีปุ่ม Check ปุ่ม Update now toast ความคืบหน้าแบบสดพร้อมยกเลิก แบนเนอร์รีบูต และแผงการตั้งค่า ทั้งหมดโดยที่ผู้ใช้ไม่ต้องแตะเทอร์มินัลเลย

มันเป็น **vanilla JavaScript**: ไม่มีเฟรมเวิร์ก ไม่มีขั้นตอนบิลด์ ไม่มี CDN สามไฟล์:

| ไฟล์ | มันคืออะไร |
|---|---|
| `vdlu.js` | วิดเจ็ต; เปิดเผย `window.VDLU` |
| `vdlu.css` | สไตล์สำหรับ toast แบนเนอร์ และแผง (ธีมมืด สืบทอดตัวแปร CSS ของโฮสต์) |
| `demo.html` | หน้าเดี่ยวที่จำลองสะพานอุปกรณ์เพื่อให้ UI ทั้งหมดทำงานในเบราว์เซอร์ธรรมดา |

วิดเจ็ตเป็นทางเลือกทั้งหมด [[Engine]] ทำงานได้ดีด้วยตัวเองจากทริกเกอร์การบูต; WebUI เป็นเพียงใบหน้าที่เป็นมิตรอยู่ด้านบน ดู [[Quick Start]] สำหรับการต่อเชื่อมเข้ากับโมดูล

## UI คุยกับเอนจินอย่างไร: สะพาน `ksu.exec`

วิดเจ็ตไม่เคยทำสิ่งที่มีสิทธิพิเศษด้วยตัวเอง มันสร้างคำสั่งเชลล์และส่งให้สะพาน `ksu.exec` ของโปรแกรมจัดการ root ซึ่งรันมันในฐานะ root และคืน stdout / stderr / รหัสออก ทุกสิ่งที่แผงแสดงถูกอ่านกลับมาจากไฟล์ที่เอนจินเขียน

วิดเจ็ตห่อสะพานนั้นไว้ในฟังก์ชัน `exec(cmd)` เดียวที่คืน `Promise`:

- **resolve** ด้วย stdout เมื่อคำสั่งออกด้วย 0
- **reject** ด้วย stderr (หรือ `rc=N`) ในกรณีอื่น

ทุกคำสั่งพกสภาพแวดล้อมของสัญญา ที่ประกอบขึ้นโดยวิดเจ็ต:

```
VDLU_DIR=... MODULE_DIR=... MODID=... sh $MODULE_DIR/vdlu/update.sh <cmd>
```

การเรียกที่เป็นรูปธรรมไม่กี่อย่าง:

- **เริ่มการอัปเดต:** `update.sh run` ถูกเปิดใช้ใน **พื้นหลัง** (`(... &)`) เพื่อให้ UI ไม่เคยถูกบล็อกโดยการดาวน์โหลดที่ยาวนาน
- **อ่านความคืบหน้า:** การ poll เบา ๆ (ประมาณหนึ่งครั้งต่อวินาที) ของ `cat $VDLU_DIR/journal.json`
- **ยกเลิก:** `touch $VDLU_DIR/cancel` (เอนจินหยุด ณ จุดปลอดภัยถัดไป)
- **คอนฟิก:** อ่านและเขียน `$VDLU_DIR/config` (key=value) โดยรักษาลำดับและคีย์ที่ไม่รู้จัก และแตะเฉพาะคีย์ที่ผู้ใช้เปลี่ยน

หากโฮสต์ส่งตัวช่วย `exec`, `toast` และ `confirm` ของตัวเองไปยัง `init()` วิดเจ็ตจะส่งผ่านคิวคำสั่งที่ทำแบบลำดับและองค์ประกอบภาพของโฮสต์เอง เพื่อให้ดูและทำงานเหมือนส่วนอื่น ๆ ของ WebUI นั้น หากละไว้ วิดเจ็ตจะย้อนกลับไปเรียก `ksu.exec` โดยตรงและฉีด mini-toast ของตัวเอง

## toast ความคืบหน้า (พร้อมยกเลิก)

เมื่อการอัปเดตกำลังทำงาน วิดเจ็ตแสดง toast ที่มุมแบบไม่บล็อกและ poll `journal.json` toast สะท้อนเครื่องสถานะของเอนจิน:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> (PENDING_REBOOT | DONE)
```

มันเรนเดอร์แถบความคืบหน้าบวกกับบรรทัด `phase done/total - current file - bytes` และพกปุ่ม **Cancel** ตลอดทั้งกระบวนการ สถานะปลายทางแต่ละอันได้รับการจัดการของตัวเอง:

- **DONE** -> toast สีเขียว "vX applied - all verified"
- **PENDING_REBOOT** -> toast สีเขียวบวกกับแบนเนอร์รีบูตแบบคงอยู่ (ด้านล่าง)
- **ERROR** -> toast สีแดงพร้อมเหตุผลจาก `journal.error` หรือ stderr เสนอ Retry มันไม่เคยแสร้งทำว่าสำเร็จ
- **Cancelled** -> toast สีเหลืองอำพัน "cancelled - N/M applied, resumable" เสนอ **Resume**
- **DEFERRED** -> toast ข้อมูลสีน้ำเงินแบบนุ่มนวล "download deferred, waiting for the allowed network" นี่คือการรอเนื่องจากนโยบายเครือข่ายที่ไม่เป็นอันตราย ไม่ใช่ข้อผิดพลาด; มันดำเนินต่อในการตรวจสอบหรือการบูตครั้งถัดไปบนเครือข่ายที่ถูกต้อง

การ poll เป็นแบบป้องกัน journal ที่เขียนไปครึ่งเดียว (เอนจินเขียนพร้อมกัน) จะถูกเพิกเฉยสำหรับ tick นั้นแทนที่จะแจงผิด หาก journal หายไปหลังจากเห็นความคืบหน้าแล้ว นั่นหมายถึง commit ล้างมันทิ้ง: วิดเจ็ตรายงาน DONE หาก journal หายไปตั้งแต่ต้นเป็นเวลา 8 tick มันรายงาน "no response" และหาก journal ค้างอยู่บนค่าเดิมเป็นเวลา 20 tick วิดเจ็ตจะตรวจสอบ `lock.d` ของเอนจิน: หากล็อกยังมีชีวิต มันเป็นเพียงการ fetch blob เดียวที่ช้าและ toast ก็รอต่อไป; หากล็อกตายแล้ว การรันตายกลางคัน ดังนั้นวิดเจ็ตจึงนำข้อผิดพลาดขึ้นมาพร้อมปุ่ม Resume แทนที่จะหมุนอยู่บน "updating" ตลอดกาล

## แบนเนอร์รีบูต

ไฟล์บางตัวไม่สามารถสลับเปลี่ยนได้บนระบบที่ทำงานอยู่: ไฟล์ `.so`, overlay ของ `/system`, `sepolicy.rule` เอนจินจัดเตรียมไฟล์เหล่านั้นและทำเครื่องหมายธุรกรรมเป็น `PENDING_REBOOT` จากนั้นวิดเจ็ตแสดง **แบนเนอร์ด้านบนแบบคงอยู่**: "Reboot to activate the new `.so` (vX)" มันคงอยู่จนกว่าไฟล์ที่จัดเตรียมไว้จะถูกสลับเปลี่ยนในการบูตครั้งถัดไป เมื่อเปิด WebUI แบนเนอร์จะถูกประเมินใหม่จาก journal ดังนั้นผู้ใช้ที่ปิดและเปิด UI ใหม่ก็ยังเห็นมัน ดู [[Reboot Handling]] สำหรับสิ่งที่เกิดขึ้นตอนบูต

สังเกตว่าแบนเนอร์อิงกับสถานะปลายทาง `PENDING_REBOOT` ไม่ใช่จากแฟล็ก `reboot_pending` (ซึ่งเป็นจริงทันทีที่ `.so` ใด ๆ เข้าสู่แผน) นั่นป้องกันแบนเนอร์จากการปรากฏกลางการรันก่อนที่สิ่งใดจะถูกจัดเตรียมไว้จริง

## แผง "Updates": สวิตช์แยกอิสระต่อหมวดหมู่

`mountUpdatesPanel(el)` เรนเดอร์แผงการตั้งค่าเข้าไปใน `<div>` ว่างที่โฮสต์จัดหาให้ มันมีสามส่วน และแต่ละตัวควบคุมเป็นอิสระและบันทึกด้วยตัวเอง:

**การกระทำ**
- **Check for updates** -> รัน `check` แสดงผลลัพธ์แบบ inline (เป็นปัจจุบัน / ใหม่กว่าฟีด / มีอัปเดตพร้อมจำนวนไฟล์และแท็กรีบูต)
- **Update now** -> ยิง `run` บวกกับ toast ความคืบหน้า

**ระบบอัตโนมัติ** (สวิตช์อิสระ แต่ละอันเขียนลง `config` ในวินาทีที่มันถูกพลิก)
- **On WebUI open** (`auto_on_webui_open`) -> รันการอัปเดตเงียบ ๆ เมื่อ UI เปิด
- **On reboot** (`auto_on_reboot`) -> นำไปใช้ในขั้นตอนก่อน zygote ตอนบูต
- **Boot retry every (s)** และ **Boot retry up to (min)** -> ฟิลด์ตัวเลขสำหรับการลอง fetch manifest ใหม่เมื่ออุปกรณ์บูตแบบออฟไลน์

**ต้นทาง (Source)**
- `source` (URL ของฟีด), `channel` (stable / canary), `profile` (trusted / hardened) และ select **Network** ที่แมปไปยัง `net_policy` (Wi-Fi + มือถือ / Wi-Fi เท่านั้น / มือถือเท่านั้น)

สวิตช์และฟิลด์ตัวเลขบันทึกทันทีและย้อนกลับทางสายตาหากการเขียนล้มเหลว ฟิลด์ข้อความและ select ในส่วน Source ทำเครื่องหมายตัวเองว่าสกปรก (dirty) และบันทึกพร้อมกันเมื่อกดปุ่ม Save อย่างชัดแจ้ง แผงเขียนทับเฉพาะคีย์ที่ผู้ใช้แตะต้องเท่านั้น ดังนั้นคีย์คอนฟิกที่ไม่รู้จักหรือในอนาคตใด ๆ จึงถูกรักษาไว้

### พฤติกรรมการเปิดอัตโนมัติ

`onWebUIOpen()` ถูกเรียกเมื่อโฮสต์โหลด มันประเมิน journal (แสดงแบนเนอร์รีบูตหรือเสนอ Resume สำหรับธุรกรรมที่ไม่ใช่สถานะปลายทางที่ถูกทิ้งไว้โดยเซสชันก่อนหน้า) แล้วหาก `auto_on_webui_open=1` มันรัน `check()` **แบบเงียบ** ก่อน toast ความคืบหน้าแบบคงอยู่และการ `run` จริงจะยิงเฉพาะเมื่อมีการดาวน์โหลดที่ต้องทำจริง (`update && fetch > 0`) หากอุปกรณ์เป็นปัจจุบันหรือล้ำหน้าฟีด ผลลัพธ์จะแสดงแบบ inline ในแผงและไม่มี toast ค้างอยู่บนหน้าจอ ดังนั้นการอัปเดตอัตโนมัติจึงไม่รบกวนพอ ๆ กับปุ่มแบบแมนนวล

## i18n (สตริงต่อภาษา)

ทุกสตริง UI ตั้งค่าเริ่มต้นเป็น **ภาษาอังกฤษ** ซึ่งเป็นตัวเลือกที่เป็นกลางสำหรับโมดูลหลายภาษาสาธารณะ แผนที่คีย์ฉบับเต็มอยู่ในอ็อบเจกต์ `DEFAULT_I18N` ใน `vdlu.js` (เปิดเผยในชื่อ `VDLU.i18n` ด้วย) โฮสต์เขียนทับคีย์ชุดย่อยใด ๆ ได้โดยการส่งแผนที่ไปยัง `init({ i18n: ... })`:

```html
<script src="i18n/pt-BR.js"></script>   <!-- defines window.VDLU_I18N_PT_BR -->
<script>
  VDLU.init({ exec: ex, moduleDir: MOD, vdluDir: VDL, modid: 'x',
              i18n: window.VDLU_I18N_PT_BR });
</script>
```

- แผนที่ **บางส่วน** ก็ใช้ได้: คีย์ที่ขาดหายไปใด ๆ จะย้อนกลับไปใช้ค่าเริ่มต้นภาษาอังกฤษ
- ป้ายเฟสและสถานะใช้คีย์ `ph_<phase>` และ `st_<STATE>`; ที่เหลือเป็นคีย์แบน ๆ เช่น `cancel`, `updateNow`
- คำแปลที่ทำไว้เป็นตัวอย่าง (`i18n/pt-BR.js`) มาเป็นเทมเพลต; ภาษาใหม่เป็นเพียงไฟล์ `i18n/<lang>.js` ในรูปแบบเดียวกัน หรือโฮสต์สร้างแผนที่จากระบบ i18n ของตัวเอง

## demo.html: รัน UI โดยไม่มีอุปกรณ์

`demo.html` จำลองสะพาน `ksu.exec` เพื่อให้ `vdlu.js` และ `vdlu.css` ตัวเดียวกันเป๊ะทำงานในเบราว์เซอร์ธรรมดา โดยไม่มี root และไม่มีโทรศัพท์:

```sh
xdg-open webui/demo.html
```

ตัวจำลองจำลอง `update.sh` และ `journal.json` ที่เปลี่ยนแปลงไป และปุ่มของมันสลับระหว่างสถานการณ์ต่าง ๆ: การอัปเดตสดไปจนถึง DONE การจบแบบ `reboot_pending` ข้อผิดพลาดกลางคัน และการรันที่ยกเลิกได้ มันเป็นวิธีที่เร็วที่สุดในการดูและทำซ้ำ (iterate) บน UI และเป็นสิ่งที่คุณตรวจสอบก่อนฝังวิดเจ็ตเข้าไปในโมดูล

## การต่อเชื่อมเข้ากับโมดูล (ทริกเกอร์เปิด WebUI)

`index.html` ของโฮสต์โหลดสองไฟล์และเรียกสามฟังก์ชัน:

```html
<link rel="stylesheet" href="vdlu.css">
<script src="vdlu.js"></script>
<script>
  VDLU.init({
    moduleDir: '/data/adb/modules/' + MODID,   // $MODULE_DIR (where the engine is vendored)
    vdluDir:   '/data/adb/' + MODID + '/vdlu',  // $VDLU_DIR  (Tier-2 state, outside the module dir)
    modid:     MODID,
    module:    'Demo',        // friendly name shown in the toast (default: modid)
    exec:   ex,               // optional: the host's ksu.exec wrapper
    toast:  toast,            // optional: the host's transient toast
    confirm: askConfirm       // optional: the host's modal
  });

  VDLU.onWebUIOpen();                          // the WebUI-open trigger: banner + auto-update eval
  VDLU.mountUpdatesPanel('b-updates');         // render the "Updates" tab into an empty div
</script>
```

โฮสต์เพียงต้องจัดหาเส้นทาง Tier-2 และจัดสรร `<div>` ว่างหนึ่งอันสำหรับแผง; toast และแบนเนอร์ถูกฉีดเข้าไปใน `document.body` โดยวิดเจ็ต `onWebUIOpen()` คือทริกเกอร์เปิด WebUI: มันคือสิ่งที่ประเมินแบนเนอร์รีบูต เสนอ Resume เมื่อมีธุรกรรมที่ถูกขัดจังหวะ และรันการอัปเดตอัตโนมัติแบบเงียบเมื่อ `auto_on_webui_open` ถูกตั้งค่า

### ต้นทางเดียว ฝังซ้ำแบบไบต์ต่อไบต์

`vdlu.js` และ `vdlu.css` คือ **สำเนา canonical** โมดูลที่ฝังวิดเจ็ตจะฝังไฟล์เหล่านี้ซ้ำแบบไม่เปลี่ยนแปลงเข้าไปใน `webroot/` ของมัน; มันไม่เคยแก้ไขสำเนาของตัวเอง ณ ตำแหน่งเดิม ฟีเจอร์ใหม่เกิดในไฟล์ canonical และไหลลงมาด้วยการฝังซ้ำ การแก้ไขสำเนาที่ฝังไว้ทำให้เกิดการเบี่ยงเบนแบบเงียบ ๆ (มันเกิดขึ้นมาแล้ว: สำเนาเก่าค้างขาด `net_policy` toast DEFERRED และฟิลด์ลองใหม่ตอนบูต) ผู้พิทักษ์ความเท่าเทียม (parity guardian) ในต้นไม้ไฟล์ซอร์สจะหาทุกสำเนาและตั้งธงหรือฝังซ้ำอันที่เบี่ยงเบน โดยครอบคลุมเฉพาะวิดเจ็ตเท่านั้น; keyring มีจังหวะการตรวจสอบ-ไม่-คัดลอกของมันเอง

### API สาธารณะ (`window.VDLU`)

| ฟังก์ชัน | ทำอะไร |
|---|---|
| `init(opts)` | กำหนดค่าวิดเจ็ต; คืน `window.VDLU` |
| `onWebUIOpen()` | เรียกเมื่อโหลด: แบนเนอร์ ข้อเสนอ Resume และการอัปเดตอัตโนมัติแบบเงียบ |
| `mountUpdatesPanel(el)` | เรนเดอร์แผง Updates เข้าไปใน `el` (สตริง id หรือ element) |
| `check()` | รัน `update.sh check`; `Promise<{update, from, to, fetch, reboot}>` |
| `startUpdate()` | ยิง `run` ในพื้นหลังบวกกับ toast ความคืบหน้าพร้อม Cancel |
| `cancel()` | สร้าง `$VDLU_DIR/cancel` (เอนจินหยุด ณ จุดปลอดภัย) |
| `resume()` | ดำเนินธุรกรรมปัจจุบันต่อบวกกับ toast |
| `refreshBanner()` | ประเมินแบนเนอร์รอรีบูตแบบคงอยู่ใหม่ |

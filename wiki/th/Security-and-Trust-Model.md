# โมเดลความปลอดภัยและความเชื่อถือ

VDLU อัปเดตโมดูล ณ ตำแหน่งเดิม ผ่านเครือข่าย ในฐานะ root นั่นคืออำนาจมหาศาลที่เล็งไปยังไฟล์ที่มาจากฟีด ดังนั้นเอนจินทั้งหมดจึงสร้างขึ้นบนสมมติฐานเดียว:

> **ทุกฟิลด์ใน manifest เป็นอินพุตที่เป็นปฏิปักษ์**

ฟีดอาจถูกวางยาที่ต้นทาง หรือถูกสลับและบิดเบือนระหว่างทางโดย MITM เมื่อนั้นเกิดขึ้น manifest ก็ยังมาถึงโดยดูเหมือน manifest: มันบรรจุเส้นทางไฟล์ สตริง `sha256` รายการ `delete[]` mode คลาส และแฟล็ก encoding VDLU ไม่ถือว่าสิ่งใดในนั้นน่าเชื่อถือ มันตรวจสอบแผนทั้งหมดก่อนที่จะดาวน์โหลดแม้แต่ไบต์เดียว และมันไม่เคยปล่อยให้ค่าใน manifest ไปถึงเชลล์

หน้านี้คือเรื่องราวความเชื่อถือฉบับเต็ม ดู [[Feed Format]] สำหรับสคีมา manifest ที่มันตรวจสอบ และ [[Engine]] สำหรับตำแหน่งที่การตรวจสอบเหล่านี้อยู่ในธุรกรรม DIFF -> FETCH -> APPLY -> COMMIT

## แนวคิดหลัก: fail-closed ก่อนที่สิ่งใดจะเกิดขึ้น

`validate_plan()` รันภายในเฟส `check`/diff **ก่อน** การ fetch ใด ๆ และ **ก่อน** การ apply ใด ๆ มันเดินผ่านทุกรายการในต้นไม้ไฟล์ที่วางแผนไว้และทุกรายการใน `delete[]` และหากรายการเดียวใดผิดรูปแบบ มัน **ปฏิเสธ manifest ทั้งก้อน** และธุรกรรมไม่เคยเริ่ม ไม่มีการยอมรับบางส่วน ไม่มี "ข้ามอันที่เสียแล้ว apply ที่เหลือ" ฟิลด์ที่เสียอันเดียววางยาทั้งชุด โดยเจตนา

manifest จะถูกยอมรับก็ต่อเมื่อ **ทุก** ข้อต่อไปนี้เป็นจริงสำหรับ **ทุก** รายการ:

| ฟิลด์ | กฎ | ทำไม |
|---|---|---|
| `path` | ไม่ใช่แบบสมบูรณ์ (absolute), ไม่มีองค์ประกอบ `..`, ไม่มีองค์ประกอบ `.`, ไม่มี `./` นำหน้า, ไม่มี `/./` ฝังอยู่, ไม่มีสแลชต่อท้าย, ไม่มีอักขระควบคุม (แท็บ / ขึ้นบรรทัดใหม่) | เส้นทางต้องอยู่ภายใน `MODULE_DIR`; เส้นทางแบบสมบูรณ์หรือ `..` คือการเขียนที่ใดก็ได้ |
| `sha256` | ตรงกับ `^[0-9a-f]{64}$` เป๊ะ | sha ที่ไม่ใช่ hex จะถูกแทรกเข้าไปในเส้นทางเชลล์; มันคือที่อยู่ของเนื้อหา จึงต้องเป็น hex digest ล้วน ๆ และไม่มีอะไรอื่น |
| `mode` | ฐานแปด (octal) เท่านั้น (`[0-7]`) | สตริง mode กลายเป็นอาร์กิวเมนต์ `chmod` |
| `size` | ตัวเลขเท่านั้น และ `<=` เพดานขนาดของเอนจิน | จำกัดการดาวน์โหลดและการคลายบีบอัด |
| `class` | เป็น `live`, `soft` หรือ `reboot` เป๊ะ | คลาสตัดสินว่าไฟล์นำไปใช้สด ๆ หรือถูกจัดเตรียมไว้เพื่อรีบูต |
| `enc` | เป็น `raw` หรือ `gz` เป๊ะ | encoding ตัดสินว่า blob ถูก gunzip หรือไม่ |
| รายการ `delete[]` | กฎเส้นทางเดียวกับข้างต้น | รายการ `delete[]` ขับเคลื่อนการนำออก; `..` ที่ไม่ถูกตรวจสอบจะเป็น `rm` นอกต้นไม้ไฟล์ |

เพราะสิ่งนี้รันก่อน manifest ที่ถูกวางยาจึงไม่สามารถเขียนนอกโมดูล ไม่สามารถลบนอกโมดูล และไม่สามารถฉีด token ที่ไม่ใช่ hex เข้าไปในบรรทัดคำสั่งได้

### ค่าใน manifest ไม่เคยแตะเชลล์

ครึ่งหลังของกฎ: แม้หลังจากค่าผ่านการตรวจสอบแล้ว มันก็ไม่เคยถูกแทรกเข้าไปใน `sh` และไม่เคยถูกป้อนให้ `awk system()` คำสั่ง check ถูกเขียนใหม่โดยเจตนาให้ไม่มีการเรียก `system()` การกำหนดที่อยู่ด้วยเนื้อหาทำงานที่เหลือ: blob ถูก fetch ด้วย `sha256` ของมัน เขียนไปยังเส้นทางแคชที่ตั้งชื่อด้วย `sha256` เดียวกัน และไบต์ที่ดาวน์โหลดถูกแฮชซ้ำและเปรียบเทียบก่อนที่สิ่งใดจะถูกนำไปใช้ ค่าที่ไม่ใช่ 64-hex digest ที่สะอาดจะไม่เคยไปถึงขั้นนั้น เพราะ `validate_plan()` ปฏิเสธมันไปแล้ว

### แนวป้องกันที่สองในเวลา apply

`validate_plan()` บล็อก `..` **ในเชิงคำศัพท์ (lexically)** แต่ symlink ที่มีอยู่ก่อนแล้วภายในต้นไม้ไฟล์ยังคงสามารถเปลี่ยนเส้นทางการเขียนได้ ดังนั้นในเวลา apply `contained()` จะแปลเส้นทางเป้าหมายจริงและยืนยันว่ามันอยู่ภายใต้ฐานโมดูล โดยปิดเมื่อล้มเหลว (fail closed) เมื่อแปลไม่ได้ การเขียนเป็นอะตอมมิก (เขียนไปยังชื่อชั่วคราว แล้ว `rename` ทับเป้าหมาย) และทุกการเขียนทับถูกสำรองไปที่ `rollback/` ก่อน; การสำรองที่ล้มเหลวจะยกเลิกการ apply แทนที่จะเขียนทับโดยไม่มีตาข่ายความปลอดภัย

## สองโปรไฟล์

VDLU ทำงานในหนึ่งในสองโปรไฟล์ความเชื่อถือ กำหนดโดย `profile=` ในคอนฟิก

### `hardened` (ค่าเริ่มต้นสาธารณะ)

- **ลายเซ็นเป็นข้อบังคับ** manifest ต้องพกลายเซ็น ed25519 ที่ถูกต้องจากคีย์ใน keyring บนอุปกรณ์ มิฉะนั้นธุรกรรมจะยกเลิก
- **การลดเวอร์ชันถูกบล็อก** manifest ที่ `version` ต่ำกว่าเวอร์ชันที่ติดตั้งจะถูกปฏิเสธ ผู้โจมตีไม่สามารถย้อนคุณกลับไปยังบิลด์ที่รู้ว่ามีช่องโหว่ได้
- นี่คือโปรไฟล์สำหรับโมดูลใด ๆ ที่แจกจ่ายสู่สาธารณะผ่าน `https://`

### `trusted` (ส่วนตัว ต้นทางจัดเตรียมผ่าน SSH)

- การตรวจสอบลายเซ็นเป็น **แบบพยายามอย่างดีที่สุด**: ต้นทางเป็นฟีด `file://` ส่วนตัวหรือฟีดที่จัดเตรียมผ่าน SSH ที่คุณควบคุม ดังนั้นลายเซ็นที่ขาดหายหรือตรวจสอบไม่ได้จึงไม่ยกเลิกแบบหนัก
- **แต่ `sha256` ของทุก blob ก็ยังถูกตรวจสอบเสมอ** `trusted` ผ่อนปรน *ว่าใครลงลายเซ็น manifest* ไม่เคยผ่อนปรน *ว่าไบต์ตรงกับแผนหรือไม่* ความสมบูรณ์ของเนื้อหาเป็นสิ่งที่ต่อรองไม่ได้ในทั้งสองโปรไฟล์

## fail-closed ด้วยการกลับเงื่อนไข

นี่คือส่วนที่ละเอียดอ่อน และเป็นส่วนที่ระบบส่วนใหญ่ทำผิด

`trusted` เป็นสตริง **เดียว** ที่เลือกเข้าสู่การตรวจสอบแบบผ่อนปรน เอนจินไม่ได้ทดสอบ "นี่คือ `hardened` หรือไม่?" มันทดสอบ "นี่ **ไม่ใช่** `trusted` หรือไม่?":

```sh
prof=$(cfg profile hardened | tr -d '[:space:]')
...
if [ "$prof" != trusted ]; then
    # signature mandatory
fi
```

ดังนั้น **อะไรก็ตาม** ที่ไม่ใช่ `trusted` ตามตัวอักษรจะแปลงเป็นพฤติกรรม hardened:

- บรรทัดหายไปทั้งหมด -> hardened
- การพิมพ์ผิดอย่าง `hardend` -> hardened
- `trusted ` ที่มีช่องว่างต่อท้าย หรือ `\r` จาก CRLF -> hardened
- `Trusted` ที่ตัวพิมพ์ผิด -> hardened
- ค่าที่ถูก MITM บิดเบือน -> hardened

เวอร์ชันก่อนหน้าตั้งค่าเริ่มต้นบรรทัดที่ *หายไป* เป็น hardened ซึ่งยังคงปล่อยให้ *ค่า* ที่เสียหายหลุดรอดไปยังเส้นทางเปิด นั่นเป็น fail-open: สตริงโปรไฟล์ที่ถูกบิดเบือนสามารถยอมรับ manifest ที่ไม่ลงลายเซ็นได้อย่างเงียบ ๆ และ manifest ที่ไม่ลงลายเซ็นหมายถึง `.so` ที่ผู้โจมตีจัดหามาถูกสลับเข้าภายใต้ MITM ซึ่งเป็นการรันโค้ดระยะไกลระดับ root การกลับเงื่อนไขปิดมัน วิธีเดียวที่จะได้การตรวจสอบแบบผ่อนปรนคือการสะกด `trusted` ให้เป๊ะ และแม้กระนั้นแฮชของ blob ก็ยังถูกตรวจสอบ เอนจินไม่เคยอยู่ห่างจากการยอมรับโค้ดที่ไม่ลงลายเซ็นเพียงการพิมพ์ผิดเดียว (`tr -d` ตัดช่องว่างที่หลงเหลือออกเพื่อให้ `trusted` ที่ถูกต้องตามกฎหมายแต่มีช่องว่างเลอะเทอะไม่ถูกปฏิเสธผิด ๆ โดยไม่เปิดช่องโหว่ซ้ำ)

**การทดสอบนี้เป็นตัวรับน้ำหนัก (load-bearing) มันต้องคงเป็น `!= trusted` และไม่เคยกลายเป็น `== hardened`**

## manifest ถูกผูกกับโมดูล

คีย์รีลีสเดียวลงลายเซ็นหลายโมดูล ดังนั้น manifest ที่ลงลายเซ็นถูกต้อง สำหรับโมดูล *อื่น* ในหลักการแล้วอาจถูกเสิร์ฟมายังอันนี้ (การตั้งค่าฟีดผิด การสลับต้นทาง หรือการเปลี่ยนเส้นทางแบบ MITM) และลายเซ็นของมันก็จะผ่าน

VDLU ปิดสิ่งนี้ด้วยการผูก: ฟิลด์ `module` ที่ลงลายเซ็นภายใน manifest ต้องเท่ากับ `MODID` ของการติดตั้งนี้ มิฉะนั้น manifest จะถูกปฏิเสธในฐานะฟีดข้ามโมดูล เพราะ `module` อยู่ภายในรูปแบบ canonical ที่ลงลายเซ็น ผู้โจมตีจึงไม่สามารถเปลี่ยนมันได้โดยไม่ทำลายลายเซ็น ฟีดที่ลงลายเซ็นถูกต้องสำหรับโมดูล B ไม่สามารถถูกนำไปใช้กับโมดูล A ได้เลย

## ตัวตรวจสอบบนอุปกรณ์ที่เพรียวบาง

การตรวจสอบบนอุปกรณ์ใช้ **ed25519-mini** ตัวตรวจสอบขนาดจิ๋วที่ตรวจสอบได้อย่างเดียวซึ่งสร้างบน TweetNaCl (public domain) **ไม่มี `openssl` บนอุปกรณ์**

- รายการ keyring คือ **คีย์สาธารณะดิบ 32 ไบต์** จัดเก็บเป็น `keyring/<key_id>.pub` (คีย์สาธารณะ PEM เป็นเพียงอาร์ติแฟกต์ฝั่ง PC; การคัดลอก PEM เข้า keyring ของอุปกรณ์ทำลายการตรวจสอบ เพราะตัวตรวจสอบคาดหวังไบต์ดิบ 32 ไบต์พอดี)
- `vdlu-verify <manifest.json> <keyring_dir>` สร้างรูปแบบ canonical ขึ้นใหม่ (ข้อความ manifest โดยลบฟิลด์ `sig` ออก กระชับ คีย์เรียงลำดับ) แฮชมันไปเป็นข้อความ hex 64 ตัวที่ลายเซ็นครอบคลุม ถอดรหัสลายเซ็น base64 ตรวจสอบว่ามันคือ 64 ไบต์ และถาม `ed25519-mini <pub32> <msg> <sig64>` เพื่อขอคำตัดสิน rc 0 = ถูกต้อง อย่างอื่น = ปฏิเสธ
- ไบนารีเป็นแบบสแตติกต่อ ABI (arm64-v8a, armeabi-v7a, x86, x86_64) พร้อม `PROVENANCE.json` ที่ตรึงซอร์ส TweetNaCl ที่แน่ชัด แฮชของ wrapper และแฟล็กบิลด์ เพื่อให้สิ่งที่รันในฐานะ root ตรวจสอบได้ (auditable)
- `key_id` จาก manifest เองถูกทำให้สะอาด (ไม่มี `/`, ไม่มี `..`, ไม่มีเครื่องหมายคำพูด) ก่อนที่มันจะถูกใช้เลือกไฟล์ keyring ดังนั้นมันจึงหนีออกจากไดเรกทอรี keyring ไม่ได้

### keyring เป็นแบบ flash เท่านั้น ตรวจสอบ-ไม่-คัดลอก เสถียร

keyring ถูกส่งมาภายในโมดูลในเวลาแฟลชและไม่ถูกเขียนใหม่โดยเอนจินอัปเดต เมื่อฝังซ้ำ กฎคือ **ตรวจสอบ อย่าคัดลอก**: keyring เปลี่ยนเฉพาะเมื่อมีการหมุนคีย์โดยเจตนา ไม่เคยเป็นผลข้างเคียงของการอัปเดต

### การหมุนคีย์ไม่ทำให้การติดตั้งเก่ากลายเป็นอิฐ

เมื่อมีการหมุนคีย์ลงลายเซ็น keyring จะส่ง **ทั้งคีย์สาธารณะดิบปัจจุบันและก่อนหน้า** ตัวตรวจสอบเลือกไฟล์คีย์ตาม `key_id` ของ manifest ดังนั้นฟีดที่ยังลงลายเซ็นด้วยคีย์เก่าจะตรวจสอบกับ pubkey เก่า และฟีดที่ลงลายเซ็นด้วยคีย์ใหม่จะตรวจสอบกับคีย์ใหม่ อุปกรณ์ที่ยังไม่ได้อัปเดตผ่านการหมุนคีย์ยังคงทำงานได้; ไม่มีสิ่งใดถูกทิ้งค้าง

## allowlist ของ key_id สำหรับการอัปเดตโมดูล

การหมุนคีย์อยู่แล้วหมายความว่า keyring สามารถถือคีย์ได้มากกว่าหนึ่งอย่างชอบธรรม และโมดูลสามารถถือได้มากกว่าหนึ่งด้วยเหตุผลที่สอง: มันอาจส่งคีย์ที่มีความเชื่อถือต่ำกว่าซึ่งลงลายเซ็นให้ฟีด*อื่น* ฟีดฟิงเกอร์พรินต์เป็นกรณีนั้นพอดี โมดูลสามารถพกคีย์แคบ ๆ ที่มีงานเดียวคือลงลายเซ็นฟีดฟิงเกอร์พรินต์ โดยนั่งอยู่ใน keyring เดียวกันถัดจากคีย์ release ที่ลงลายเซ็นตัวโมดูลเอง

นั่นทำให้เกิดคำถามที่เรื่องการหมุนคีย์เพียงอย่างเดียวตอบไม่ได้: เมื่อมีสองคีย์อยู่ใน keyring แล้ว *คีย์ใด* ในนั้นได้รับอนุญาตให้ลงลายเซ็น**การอัปเดตโมดูล**? การอัปเดตโมดูลเป็นสิ่งที่ทรงพลังที่สุดที่ manifest ขอได้ เพราะมันเขียนทับไฟล์ที่อุปกรณ์รันในฐานะ root ตัวตรวจสอบเคยเลือก pubkey ที่ `key_id` ของ manifest ระบุ และยอมรับคีย์ใด ๆ ที่บังเอิญมีอยู่ใน keyring ดังนั้นคีย์ฟีดฟิงเกอร์พรินต์ที่มีความเชื่อถือต่ำกว่า หากรั่วไหล ก็สามารถลงลายเซ็น manifest การอัปเดตโมดูลได้ และอุปกรณ์จะยอมรับมัน นั่นคือการข้ามรากความเชื่อถือ: คีย์ที่ตั้งใจไว้สำหรับงานแคบ ๆ งานเดียวสามารถขับเคลื่อนการอัปเดต root แบบ flashless เต็มรูปแบบได้

การแก้ไขนี้ปักหมุด `key_id` ของการอัปเดตโมดูลที่ยอมรับไว้กับ **allowlist** แบบ fail-closed ซึ่งถูกตรวจสอบ **ก่อน** ที่จะเลือก pubkey เสียอีก คีย์การตั้งค่าคือ `key_id` และเอนจินแก้ค่ามันแบบนี้:

- **keyring ที่มีคีย์เดียวปักหมุดคีย์นั้นโดยอัตโนมัติ** กรณีทั่วไปไม่ต้องการการตั้งค่าใด ๆ เลย: หาก keyring ถือคีย์เพียงหนึ่งเดียว คีย์นั้น*คือ* allowlist และไม่มีสิ่งอื่นใดสามารถลงลายเซ็นการอัปเดตโมดูลได้
- **keyring ที่มีหลายคีย์ต้องตั้งค่า `key_id`** ทันทีที่คีย์ที่สองปรากฏขึ้น เอนจินปฏิเสธที่จะเดา มันล้มเหลวแบบปิดด้วย "multiple keys in keyring; config must pin key_id" จนกว่าการตั้งค่าจะระบุคีย์ (หรือหลายคีย์ คั่นด้วยจุลภาคในช่วงหน้าต่างการหมุนคีย์) ที่อาจลงลายเซ็นการอัปเดตโมดูล

เพราะการตรวจสอบรันก่อนการเลือก pubkey manifest ที่ระบุคีย์ซึ่งมีอยู่แต่ไม่อยู่ใน allowlist จะถูกปฏิเสธโดยที่ตัวตรวจสอบไม่เคยโหลดคีย์นั้นเลย ชุดที่แก้ค่าแล้วถูกสะท้อนเข้าไปใน `vdlu-verify` ผ่าน `VDLU_KEYID_ALLOW` ดังนั้นตัวตรวจสอบบนอุปกรณ์ที่เพรียวบางบังคับใช้การปักหมุดเดียวกัน และทั้งสองไม่สามารถขัดแย้งกันได้ สิ่งนี้เป็นจริงใน**ทั้งสอง**โปรไฟล์: ทั้ง `hardened` และ `trusted` ต่างปรึกษา allowlist เพราะ allowlist ตัดสิน*ว่าคีย์ใด*เป็นรากการอัปเดตโมดูลที่ถูกต้อง ไม่ใช่*ว่าจำเป็นต้องมีลายเซ็นหรือไม่*

ฟีดฟิงเกอร์พรินต์เก็บรากความเชื่อถือที่ปักหมุดแยกของตัวเองไว้ คือ `FEED_KEY_ID` มันเป็นรากที่ชัดเจนด้วยงานที่ชัดเจน ไม่สามารถเข้าถึงได้ผ่านเส้นทางการอัปเดตโมดูลข้างต้น ดังนั้นการปักหมุด allowlist ของการอัปเดตโมดูลจึงไม่แตะมัน และคีย์ฟีดที่รั่วไหลก็ยังคงลงลายเซ็นการอัปเดตโมดูลไม่ได้ การเปลี่ยนแปลงนี้ดัน `ENGINE_VERSION` เป็น 4

## สิ่งที่ tools-manifest ปิด

ตัว bootstrap fetch ที่เพรียวบางดาวน์โหลด `curl` แบบสแตติกเมื่อใช้ครั้งแรกสำหรับโมดูลที่ไม่ได้ส่ง curl ของตัวเองมา เพราะไบนารีนั้นรันในฐานะ root ลายเซ็น manifest ของมันเอง (ed25519-mini) และแฮชของมันจึงเป็น **ข้อบังคับในทุกโปรไฟล์** รวมถึง `trusted` ก่อนที่มันจะถูกติดตั้งหรือรัน webview เป็นเพียงการขนส่ง; ความเชื่อถือมาจากการตรวจสอบลายเซ็นและแฮชบนอุปกรณ์ ไม่เคยมาจากข้อเท็จจริงที่ว่าการดาวน์โหลดสำเร็จ

## สิ่งที่ผู้โจมตีทำไม่ได้

แม้จะเป็นเจ้าของฟีด หรือนั่งอยู่บนสายในฐานะ MITM เต็มตัว ผู้โจมตีก็ไม่สามารถ:

- **เขียนนอกโมดูล** เส้นทางแบบสมบูรณ์, `..`, `.`, อักขระควบคุม และสแลชต่อท้าย ถูกปฏิเสธทั้งหมดก่อนการ apply ใด ๆ และการเปลี่ยนเส้นทางด้วย symlink ถูกจับได้อีกครั้งในเวลา apply
- **ลบนอกโมดูล** รายการ `delete[]` ผ่านการตรวจสอบเส้นทางเดียวกัน
- **ฉีดคำสั่ง** ไม่มีค่าใน manifest ถูกแทรกเข้าไปในเชลล์หรือ `awk system()`; `sha256` ต้องเป็น 64-hex ล้วน มิฉะนั้น manifest ทั้งก้อนถูกปฏิเสธ
- **ส่งโค้ดที่ไม่ลงลายเซ็นไปยังการติดตั้งสาธารณะ** `hardened` ทำให้ลายเซ็นเป็นข้อบังคับ และโปรไฟล์เป็น fail-closed ด้วยการกลับเงื่อนไข ดังนั้นไม่มีการพิมพ์ผิดหรือค่าที่ถูกบิดเบือนใดลดระดับมันได้
- **ลงลายเซ็นการอัปเดตโมดูลด้วยคีย์ที่มีความเชื่อถือต่ำกว่า** `key_id` ของการอัปเดตโมดูลถูกปักหมุดกับ allowlist แบบ fail-closed ซึ่งตรวจสอบก่อนที่จะเลือก pubkey ดังนั้นคีย์ฟีดฟิงเกอร์พรินต์ที่รั่วไหลซึ่งใช้ keyring ร่วมกันไม่สามารถลงลายเซ็นการอัปเดต root เต็มรูปแบบได้
- **เสิร์ฟฟีดที่ลงลายเซ็นของโมดูลอื่นที่นี่** ฟิลด์ `module` ที่ลงลายเซ็นต้องเท่ากับ `MODID` นี้
- **ย้อนคุณกลับ** การลดเวอร์ชันถูกบล็อกใน `hardened`
- **ทำให้ blob เสียหายโดยไม่ถูกตรวจจับ** ทุก blob ที่ดาวน์โหลดถูกแฮชซ้ำเทียบกับ `sha256` ของ manifest ในทั้งสองโปรไฟล์; ความไม่ตรงกันหลังจากสามครั้งยกเลิกเฟสโดยไม่นำสิ่งใดไปใช้
- **สลับตัวดึง root ปลอมเข้ามา** `curl` ที่ bootstrap ถูกตรวจสอบลายเซ็นและแฮชก่อนที่จะถูกติดตั้งหรือรัน ในทุกโปรไฟล์
- **นำการอัปเดตที่เสียหายไปใช้ครึ่งเดียว** ธุรกรรมไปถึง `DONE` เฉพาะเมื่อการแฮชซ้ำทุกอย่างตรงกัน; การ apply ที่ล้มเหลวจะย้อนกลับแทนที่จะเขียนทับโดยไม่มีการสำรอง

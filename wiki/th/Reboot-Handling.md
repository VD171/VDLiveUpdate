# การจัดการการรีบูต

จุดประสงค์ทั้งหมดของ VDLU คือการอัปเดตโมดูลโดยไม่ต้องแฟลชมันใหม่ และเมื่อทำได้ ก็โดยไม่ต้องรีบูตเลย ไฟล์ส่วนใหญ่ในโมดูลสามารถถูกแทนที่ได้ขณะอุปกรณ์กำลังทำงาน มีเพียงไม่กี่ตัวที่ทำไม่ได้จริง ๆ เพราะเคอร์เนลหรือโปรเซส zygote ได้แมปพวกมันไว้แล้วและจะไม่สังเกตการเปลี่ยนแปลงจนกว่าจะบูตครั้งถัดไป

หน้าที่ของ VDLU คือการแยกแยะสองกลุ่มนั้นโดยอัตโนมัติ นำทุกอย่างที่มันทำได้อย่างปลอดภัยไปใช้ **สด ๆ** และเลื่อนเฉพาะไฟล์ที่ผูกกับการบูตจริง ๆ ไปยังการรีบูตที่มันตั้งธงไว้อย่างชัดเจน หน้านี้อธิบายว่าอย่างไร

สำหรับกลไกเอนจินที่อยู่ภายใต้สิ่งนี้ ดู [[Engine]] สำหรับภาพรวม ดู [[Architecture]]

## ทำไมไม่รีบูตทุกครั้งเลย

การรีบูตเป็นสิ่งที่แพงที่สุดที่การอัปเดตจะขอจากใครได้ มันขัดจังหวะสิ่งที่พวกเขากำลังทำ มันใช้เวลาหนึ่งนาทีหรือมากกว่า และมันฝึกผู้คนให้กลัวการอัปเดต ตัวอัปเดตแบบเพิ่มทีละส่วนที่ดีควรรู้สึกราวกับมองไม่เห็น: คุณแตะอัปเดต ไฟล์ไม่กี่ตัวเปลี่ยนภายใต้ระบบที่ทำงานอยู่ และคุณก็อยู่บนเวอร์ชันใหม่แล้ว

ดังนั้น VDLU กลับสมมติฐานปกติ ค่าเริ่มต้นคือสด ๆ ไฟล์จะถูกเลื่อนไปยังการรีบูตเฉพาะเมื่อมันพิสูจน์ได้ว่าเป็นหนึ่งในชนิดที่ผูกกับเคอร์เนลหรือ zygote และแม้กระนั้นก็มีเพียงไฟล์นั้นที่รอ ทุกอย่างรอบมันยังอัปเดตทันที

## สามคลาส

ทุกไฟล์ในฟีดถูกกำหนดคลาส producer สามารถตั้งมันอย่างชัดแจ้งใน manifest ได้ แต่ในทางปฏิบัติคลาสถูกได้มาจากเส้นทาง และเอนจินจะยกระดับไฟล์ไปทาง `reboot` เท่านั้น ไม่เคยลดระดับมันไปทาง `live` คลาสต่าง ๆ มีดังนี้:

**LIVE** คือกรณีทั่วไป: แอสเซ็ต web UI, ไบนารี, สคริปต์ที่อ่านตามต้องการ, ไฟล์คอนฟิก, `module.prop` และสิ่งอื่นใดที่ไม่ตรงกับกฎด้านล่าง ไฟล์ live ถูกสำรองแล้ว rename ทับเป้าหมายแบบอะตอมมิกขณะระบบทำงานอยู่ ไม่ต้องรีบูต และการเปลี่ยนแปลงมีผลในวินาทีที่การ rename ลงที่

**SOFT** คือสคริปต์วงจรชีวิตของตัวโมดูลเอง: `service.sh`, `post-fs-data.sh` และ `boot-completed.sh` ไฟล์เหล่านี้ถูกนำไปใช้สด ๆ เหมือนกับไฟล์ LIVE เป๊ะ ดังนั้นสำเนาใหม่จึงอยู่บนดิสก์แล้ว เหตุผลที่พวกมันได้คลาสของตัวเองคือระบบที่ทำงานอยู่ได้รันสำเนาเก่าไปแล้วในการบูตนี้; สำเนาใหม่เพียงรันในการบูตถัดไป โดยไม่มีการจัดเตรียมและไม่มีแบนเนอร์ ไม่มีอะไรให้เลื่อน เป็นเพียงการส่งมอบตามธรรมชาติ

**REBOOT-hard** คือชุดเล็ก ๆ ที่ไม่สามารถเปลี่ยนแปลงได้ภายใต้ระบบที่ทำงานอยู่:

- ไลบรารีเนทีฟ `*.so` (อะไรก็ตามภายใต้เส้นทาง `zygisk/`) เพราะ zygote แมปมันเข้าสู่ทุกแอปตอนเริ่มต้น;
- ไฟล์ overlay ของ `/system` เพราะ overlay ถูกเมานต์ตอนบูต;
- ไฟล์ `sepolicy.rule` เพราะนโยบาย SELinux ถูกโหลดแต่เนิ่น ๆ

ไฟล์ REBOOT-hard ไม่เคยถูกเขียนทับ inode ที่ใช้งานอยู่ขณะระบบขึ้นอยู่ การเขียนทับ `.so` ที่ zygote แมปไว้แล้วคือวิธีที่คุณจะได้การล่มและสถานะที่ไม่สอดคล้องกัน แทนที่จะเป็นเช่นนั้น เนื้อหาใหม่จะถูก **จัดเตรียม (staged)** ไว้ข้าง ๆ ไดเรกทอรีสถานะและสลับเข้าในการบูตครั้งถัดไป ก่อนที่สิ่งใดจะแมปมันได้

## เส้นทางสู่คลาส ในภาพรวม

เอนจินได้มาซึ่งคลาสจากเส้นทางดังนี้:

| รูปแบบเส้นทาง | คลาส | นำไปใช้ |
|---|---|---|
| `zygisk/**`, `**/zygisk/**` (ไฟล์ `.so`) | REBOOT-hard | จัดเตรียม สลับก่อน zygote ตอนบูต |
| `system/**` (overlay) | REBOOT-hard | จัดเตรียม สลับตอนบูต |
| `*.rule` (sepolicy) | REBOOT-hard | จัดเตรียม สลับตอนบูต |
| `service.sh`, `post-fs-data.sh`, `boot-completed.sh` | SOFT | เขียนสด ๆ รันในการบูตถัดไป |
| `webroot/**`, `bin/**`, `lib/**`, คอนฟิก, `module.prop`, ทุกอย่างอื่น | LIVE | เขียนสด ๆ มีผลทันที |

manifest อาจพก `class` ที่ชัดแจ้งต่อไฟล์ แต่คลาสที่ได้มาทำหน้าที่เป็นพื้น (floor): หากไฟล์ดูเป็น REBOOT-hard ตามเส้นทางของมัน มันจะถูกปฏิบัติเป็น REBOOT-hard แม้ว่า manifest จะบอกเป็นอย่างอื่น นี่ป้องกันฟีดที่ติดป้ายผิดจากการพยายามสลับร้อน (hot-swap) `.so`

## การรันจัดการทั้งสองกลุ่มพร้อมกันอย่างไร

ระหว่างการ `run` ปกติ (วงจร DIFF ไป FETCH ไป APPLY ไป COMMIT ที่อธิบายใน [[Engine]]) ทั้งสองกลุ่มถูกจัดการในธุรกรรมเดียวกัน:

```
run:
  LIVE + SOFT  --> backup -> write .vdlu-tmp -> verify -> atomic rename   (effective now)
  REBOOT-hard  --> materialize into staged/<path>.vdlu-new                (live inode untouched)

  re-hash every LIVE + SOFT file
       |
       +-- nothing staged  --> DONE
       +-- something staged --> PENDING_REBOOT  (reboot banner in the WebUI)
```

ดังนั้นหลังจากการรันที่แตะต้อง `.so` คุณก็อยู่บนเวอร์ชันใหม่สำหรับทุกไฟล์ live แล้ว และมีเพียงชิ้นส่วนที่จัดเตรียมไว้ที่รออยู่ journal รายงาน `reboot_pending` และ WebUI แสดงแบนเนอร์แบบคงอยู่ที่เชิญชวนให้รีบูตเพื่อเปิดใช้งานไฟล์ที่จัดเตรียมไว้ ไม่มี "done" ปลอม ๆ: การรันที่มีไฟล์จัดเตรียมไว้จบใน `PENDING_REBOOT` ไม่ใช่ `DONE`

## การสลับเปลี่ยนตอนบูต

ไฟล์ที่จัดเตรียมไว้ถูกนำไปใช้โดยคำสั่ง `boot` ซึ่งโมดูลโฮสต์ต่อเชื่อมเข้ากับ `post-fs-data.sh` เพื่อให้มันรันแบบ synchronous และ **ก่อน zygote** ก่อนที่โปรเซสใดจะแมป `.so` ใหม่ได้

`boot` ทำ `resume` (เพื่อจบเฟสที่ถูกขัดจังหวะใด ๆ) แล้วจึงสลับเปลี่ยน สำหรับไฟล์ REBOOT-hard ที่จัดเตรียมไว้แต่ละตัว มันจะ:

1. ยืนยันว่าเส้นทางที่จัดเตรียมไว้อยู่ภายในไดเรกทอรีโมดูล (การตรวจสอบการบรรจุ);
2. แฮชซ้ำ `staged/<path>.vdlu-new` เทียบกับแฮชของ manifest;
3. สำรองไฟล์ live ปัจจุบัน;
4. `mv -f` ไฟล์ที่จัดเตรียมไว้ทับไฟล์ที่ใช้งานอยู่และ `chmod` มัน;
5. แฮชซ้ำไฟล์ที่อยู่ที่แล้ว เพื่อยืนยันว่าการสลับลงที่ถูกต้อง;
6. ทำเครื่องหมายว่านำไปใช้แล้ว

เฉพาะเมื่อทุกไฟล์ที่จัดเตรียมไว้ได้สลับและตรวจสอบซ้ำแล้วเท่านั้น ธุรกรรมจึงปิดจาก `PENDING_REBOOT` เป็น `DONE` หากขั้นตอนใดล้มเหลว journal จะบันทึกข้อผิดพลาดและโมดูลคงไฟล์ก่อนหน้าของมันไว้; ไม่มีสิ่งใดถูกปล่อยให้สลับไปครึ่งเดียว

เพราะการสลับเปลี่ยนเป็นลำดับของการแฮชซ้ำและการ rename แบบอะตอมมิก การรัน `boot` จึงปลอดภัยแม้ว่ามันจะถูกขัดจังหวะครั้งที่แล้ว มันเพียงหยิบไฟล์ที่จัดเตรียมไว้ขึ้นมาใหม่

## auto_on_reboot

การจัดเตรียมเป็นเพียงครึ่งหนึ่งของความรู้สึกไม่ต้องรีบูต; อีกครึ่งหนึ่งคือผู้ใช้ไม่ควรต้องจำว่าต้องรันการสลับเปลี่ยน ด้วย `auto_on_reboot=1` ในคอนฟิก `post-fs-data.sh` ของโมดูลโฮสต์เรียก `update.sh boot` ในทุกการบูต นั่นหมายถึง:

- หากธุรกรรมรอรีบูต ไฟล์ที่จัดเตรียมไว้จะถูกสลับเข้าโดยอัตโนมัติก่อนที่ zygote จะเริ่ม และผู้ใช้ก็พบว่าตัวเองอยู่บนเวอร์ชันใหม่โดยสมบูรณ์;
- หากไม่มีอะไรรออยู่ `boot` สามารถรันวงจรใหม่และนำทุกอย่างไปใช้ รวมถึง `.so` ในการบูตครั้งเดียวนั้น เพราะมันรันก่อน zygote อยู่แล้ว

กล่าวอีกนัยหนึ่ง `.so` ที่จัดเตรียมไว้ไม่ทำให้ผู้ใช้เสียอะไรนอกเหนือจากการรีบูตที่พวกเขาจะทำอยู่แล้ว พวกเขาไม่ต้องแตะอะไรเป็นครั้งที่สอง

## ออฟไลน์ตอนบูต โดยไม่ทำให้แบตเตอรี่หมด

บางครั้ง `boot` ต้องการตรวจสอบฟีดแต่อุปกรณ์ยังไม่มีเครือข่าย VDLU สามารถรอมันได้ อย่างอดทนและราคาถูก ควบคุมโดย `boot_retry_minutes` (0 ปิดมัน) การรอถูกออกแบบให้ปลอดภัยต่อแบตเตอรี่โดยเจตนา:

- ระหว่างความพยายาม มันเพียง `sleep` ซึ่งหยุดนิ่งในโหมดหลับลึก ดังนั้นอุปกรณ์จึงหลับตามปกติและการลองใหม่ดำเนินต่อก็ต่อเมื่ออุปกรณ์ตื่นอยู่แล้ว;
- มันไม่ถือ wakelock และไม่ถือล็อกเอนจินขณะรอ ดังนั้นการรันด้วยมือจึงไม่เคยถูกบล็อก;
- ก่อนแต่ละความพยายาม มันตรวจสอบว่าเครือข่ายได้รับอนุญาตหรือไม่ด้วยการค้นหาเส้นทางเคอร์เนลที่ไม่ส่งแพ็กเก็ตและไม่ปลุกวิทยุ;
- มันไม่เคยลองใหม่กับความล้มเหลวที่กำหนดผลแน่นอนเช่นลายเซ็นที่ไม่ดีหรือการลดเวอร์ชันที่ถูกบล็อก มีเพียงภาวะเครือข่ายไม่มีอยู่จริง ๆ เท่านั้น

การตรวจสอบ manifest เองยังคงฟรีบนเครือข่ายใดก็ได้ ดังนั้นคุณจึงรู้เสมอว่ามีการอัปเดตอยู่; มีเพียงการดาวน์โหลดที่รอให้นโยบายเครือข่ายได้รับการตอบสนอง โดยเลื่อนออกไปอย่างสะอาดแทนที่จะเกิดข้อผิดพลาด

# เอนจิน

เอนจินคือฝั่งอุปกรณ์ของ VDLU: ส่วนที่ทำงานบนโทรศัพท์ ตัดสินว่าอะไรเปลี่ยนไป ดาวน์โหลดมัน และนำไปใช้ มันคือสคริปต์เชลล์ POSIX ไฟล์เดียวคือ `engine/update.sh` บวกกับตัวตรวจสอบลายเซ็นขนาดจิ๋ว `engine/vdlu-verify` ทั้งคู่ถูกฝังเข้าไปในโมดูลโฮสต์ที่ `<module>/vdlu/` และรันโดย root

เอนจินทั้งหมดสร้างขึ้นรอบแนวคิดเดียว: การอัปเดตคือ **ธุรกรรมที่ดำเนินต่อได้ (resumable transaction)** หากโทรศัพท์ถูกรีบูต ถูกฆ่า หรือเครือข่ายหลุดกลางคัน การรันครั้งถัดไปจะทำต่อ ณ จุดที่หยุดพอดี และโมดูลจะไม่เคยถูกปล่อยให้นำไปใช้เพียงครึ่งเดียวในขณะที่แสร้งว่าเสร็จแล้ว

หากต้องการภาพรวมก่อน ดู [[Architecture]] สำหรับวิธีที่การอัปเดตเลี่ยงการรีบูตเมื่อทำได้ ดู [[Reboot Handling]]

## เขียนสำหรับอุปกรณ์ ไม่ใช่สำหรับแล็ปท็อปของคุณ

`update.sh` เป็น POSIX `sh` ล้วน ๆ มันทำงานบน mksh, busybox หรือ toybox โดยไม่มีฟีเจอร์เฉพาะของ bash และมันผ่าน `sh -n` นี่สำคัญเพราะสภาพแวดล้อมบนอุปกรณ์ Android ที่ root แล้วนั้นเล็กและเข้มงวด

โดยเฉพาะอย่างยิ่ง ไม่มี `jq` VDLU แจง `manifest.json` ด้วยตัวทำให้แบนสไตล์ gron ขนาดเล็กที่เขียนด้วย `awk`: มันเดินผ่าน JSON ทีละตัวอักษรและปล่อยบรรทัด `path<TAB>value` หนึ่งบรรทัดต่อหนึ่งใบ (leaf) (ตัวอย่างเช่น `files/0/sha256<TAB>ab..` หรือ `version<TAB>6`) จากนั้นเชลล์อ่านบรรทัดเหล่านั้นด้วย `grep` และ `cut` วิธีนี้ใช้ได้ทั้งกับ JSON แบบกระชับและแบบจัดรูปสวยงาม และมันไม่เคยเรียกเครื่องมือ JSON ที่ไม่มีอยู่

เอนจินพึ่งพาเฉพาะสิ่งที่ toybox มีมาให้อยู่แล้ว (`sha256sum`, `gzip`/`gunzip`, `base64`, `date`) ตัวตรวจสอบ `ed25519-mini` ที่ฝังมา และสำหรับฟีด `https://` เท่านั้น ก็มี `curl` แบบสแตติกขนาดเล็กที่ถูกดึงมาและตรวจสอบครั้งเดียว ฟีด `file://` ไม่ต้องใช้ `curl` เลย

## หกคำสั่ง

คุณเรียกเอนจินด้วยเส้นทางของโมดูลในสภาพแวดล้อมและหนึ่งคำสั่ง:

```sh
VDLU_DIR=/data/adb/<mod>/vdlu MODULE_DIR=/data/adb/modules/<mod> MODID=<mod> \
  sh "$MODULE_DIR/vdlu/update.sh" <cmd>
```

รหัสออก (exit code) `0` หมายถึงสำเร็จ; รหัสอื่นใดหมายถึงข้อผิดพลาด พร้อมเหตุผลพิมพ์ไปที่ stderr

| คำสั่ง | สิ่งที่มันทำ |
|---|---|
| `check` | diff แบบอ่านอย่างเดียว ดาวน์โหลด manifest เปรียบเทียบกับสิ่งที่ติดตั้งไว้ และพิมพ์สรุป JSON หนึ่งบรรทัด: `{"update":bool,"from":N,"to":M,"fetch":K,"reboot":bool}` ไม่เปลี่ยนอะไรบนดิสก์ หากอุปกรณ์ใหม่กว่าฟีด (การลดเวอร์ชันที่ถูกบล็อก) มันรายงาน `{"update":false,"ahead":true,...}` ด้วยรหัสออก `0` ไม่ใช่ข้อผิดพลาด |
| `run` | วงจร live เต็มรูปแบบ: DIFF, FETCH, APPLY, COMMIT นำทุกไฟล์ live ไปใช้ทันทีและจัดเตรียมไฟล์คลาสรีบูตไม่กี่ตัว เคารพ `cancel` เขียนความคืบหน้าไปที่ `journal.json` |
| `resume` | ดำเนินธุรกรรมที่ถูกขัดจังหวะต่อ โดยเริ่มจากเฟสที่มันอยู่ เป็น idempotent มัน **ไม่** สลับเปลี่ยน `.so` ที่จัดเตรียมไว้ (นั่นสงวนไว้สำหรับ `boot`) |
| `boot` | เส้นทางก่อน zygote ทำ `resume` แล้วสลับเปลี่ยนไฟล์ `*.vdlu-new` ที่จัดเตรียมไว้ทั้งหมดเข้าที่ ปิด `PENDING_REBOOT` เป็น `DONE` หากไม่มีธุรกรรมที่ค้างอยู่ มันจะรันวงจรใหม่และนำทุกอย่างไปใช้ รวมถึง `.so` ในการบูตครั้งเดียวนั้น |
| `status` | พิมพ์ `journal.json` หรือ `{"state":"idle"}` เมื่อไม่มีอะไรดำเนินอยู่ |
| `cancel` | สร้างเครื่องหมาย `cancel` การ `run` ที่กำลังดำเนินจะหยุดอย่างสะอาด ณ จุดปลอดภัยถัดไป |

คำสั่ง `check` ถูกออกแบบให้ถูก (cheap) โดยเจตนา เพื่อให้ UI บอกคุณได้ว่ามีการอัปเดตบนเครือข่ายใดก็ได้ ส่วนการดาวน์โหลดจริงถูกควบคุมแยกต่างหาก (ดูเฟส fetch ด้านล่าง)

## ธุรกรรม ทีละขั้นตอน

ทุก `run` เคลื่อนผ่านเครื่องสถานะที่ตายตัว บันทึกไว้ใน `journal.json` เพื่อให้ WebUI (และคุณ) เฝ้าดูได้:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> (PENDING_REBOOT | DONE)
```

**DIFF** เอนจินดึง `manifest.json` ตรวจสอบทุกฟิลด์ (ดูด้านล่างและ [[Security and Trust Model]]) และเปรียบเทียบส่วนต่างของต้นไม้ไฟล์เป้าหมายที่ลงลายเซ็นกับ `current.json` ซึ่งเป็น manifest ของเวอร์ชันที่ติดตั้งอยู่แล้ว ผลลัพธ์คือแผนรายไฟล์ที่เขียนลง `plan.tsv`: หนึ่งแถวต่อหนึ่งไฟล์ บรรจุคลาส แฮชเป้าหมาย mode และสถานะความคืบหน้า ไฟล์ที่มีแฮชตรงกับเป้าหมายอยู่แล้วจะถูกทำเครื่องหมายให้ข้าม

**FETCH** สำหรับแต่ละไฟล์ที่ยังต้องการ เอนจินดาวน์โหลด blob แบบกำหนดที่อยู่ด้วยเนื้อหาของมันจาก `<source>/blobs/<sha>` (หรือ `<sha>.gz` เมื่อบีบอัด) ลงในไฟล์ `.part` หาก blob ถูก gzip ไว้ มันจะถูกคลายบีบอัด แล้วจึงตรวจสอบ SHA-256 ของมันเทียบกับ manifest เฉพาะเมื่อตรงกันเท่านั้นจึงจะถูก `mv` เข้าสู่ `blobs/<sha>` แบบอะตอมมิก blob ที่แคชไว้แล้วพร้อมแฮชที่ถูกต้องจะถูกข้ามทั้งหมด และไฟล์ในเครื่องที่ไม่เปลี่ยนสามารถ seed แคชได้โดยไม่ต้องดาวน์โหลด ความล้มเหลวสามครั้งบน blob เดียวกันยกเลิกเฟสโดยไม่นำสิ่งใดไปใช้ เฟสจะไปถึง `FETCHED` ก็ต่อเมื่อทุก blob ในแผนมีครบและตรวจสอบแล้ว สำหรับ [[Feed Format]] ที่ blob เหล่านี้มาจาก ดูหน้านั้น

การ fetch ถูกควบคุมโดยนโยบายเครือข่าย: ฟีดอาจถูกจำกัดให้ใช้ Wi-Fi เท่านั้น มือถือเท่านั้น หรือเครือข่ายใดก็ได้ เมื่อเครือข่ายปัจจุบันไม่ได้รับอนุญาต การ fetch จะไม่ล้มเหลว; มันเข้าสู่สถานะ `DEFERRED` ที่ไม่เป็นอันตราย คงแผนและเป้าหมายที่ตรึงไว้ และดำเนินต่อในการตรวจสอบหรือการบูตครั้งถัดไปเมื่อเครือข่ายที่ถูกต้องปรากฏ ไม่มีการใช้ข้อมูลในระหว่างนั้น

**APPLY** เข้าได้จาก `FETCHED` เท่านั้น สำหรับแต่ละไฟล์ เอนจินดำเนินการตามคลาส:

- ไฟล์ `live` และ `soft`: สำรองไฟล์ปัจจุบันไปที่ `rollback/<version>/<path>` เขียนเนื้อหาใหม่ลงในไฟล์พี่น้อง `.vdlu-tmp` `chmod` มัน ตรวจสอบแฮชของมัน แล้ว `rename` มันทับเป้าหมายแบบอะตอมมิก ไฟล์ที่มีแฮชตรงกับเป้าหมายอยู่แล้วจะถูกข้าม
- ไฟล์ `reboot` (ไฟล์ `.so`, overlay ของ `/system`, `sepolicy.rule`): สร้างเป็นรูปธรรมใน `staged/<path>.vdlu-new` inode ที่ใช้งานอยู่ไม่เคยถูกแตะต้องที่นี่ ดู [[Reboot Handling]]
- การลบ: สำรอง แล้วจึงนำออก การลบจะถูกนำไปใช้เฉพาะตอนสุดท้ายสุด บน `DONE` ที่สะอาด ไม่เคยในขณะที่ยังมีรีบูตค้างอยู่

**COMMIT** เอนจินแฮชซ้ำทุกไฟล์ live และ soft ที่มันแตะต้อง เฉพาะเมื่อทั้งหมดตรงกันเท่านั้นมันจึงเขียน `current.json` ทำให้เวอร์ชันใหม่เป็นฐาน diff หากมีไฟล์คลาสรีบูตใดถูกจัดเตรียม สถานะจะกลายเป็น `PENDING_REBOOT` แทน `DONE`; การสลับเปลี่ยนและการตรวจสอบซ้ำครั้งสุดท้ายจะเกิดภายหลังภายใต้คำสั่ง `boot`

## ปลอดภัยต่อความล้มเหลวโดยการออกแบบ

การรับประกันที่ทำให้สิ่งนี้ปลอดภัยที่จะรันโดยไม่มีผู้ดูแล:

- **ไม่มีสิ่งใดถูกทำเครื่องหมาย `DONE` โดยไม่มีการแฮชซ้ำที่ตรงกัน** `DONE` ไปถึงเฉพาะหลังจากทุกไฟล์ที่นำไปใช้ถูกอ่านกลับมาและ SHA-256 ของมันถูกเทียบกับ manifest ไฟล์รีบูตที่จัดเตรียมไว้บังคับให้เป็น `PENDING_REBOOT` ไม่เคยเป็น `DONE` ปลอม ๆ
- **ไม่มีสิ่งใดสูญหาย** ทุกไฟล์ถูกสำรองไปที่ `rollback/<version>/` ก่อนที่จะถูกเขียนทับ และเก็บสามเวอร์ชันล่าสุดไว้ หากการนำไปใช้ล้มเหลว ไฟล์ live จะถูกคืนค่าจากสำเนาสำรอง; โมดูลไม่เคยถูกปล่อยให้นำไปใช้ครึ่งเดียวแล้วโกหกเกี่ยวกับมัน `apply_live` ยกเลิกทันทีหากขั้นตอนการสำรองล้มเหลว แทนที่จะเขียนทับโดยไม่มีทางกลับ
- **ทุกอย่างเป็นอะตอมมิก** เนื้อหาใหม่ลงที่ผ่าน `rename`/`mv` ทับเป้าหมาย ดังนั้นผู้อ่านจึงเห็นไม่ไฟล์เก่าก็ไฟล์ใหม่ ไม่เคยเห็นการเขียนที่ขาดวิ่น
- **ดำเนินต่อได้หลังการล่มหรือถูกฆ่า** การล่ม เครือข่ายหลุด หรือรีบูตกลางคันจะทิ้ง journal ที่ถูกต้องไว้; `resume` (หรือ `boot`) ดำเนินต่อจากเฟสที่บันทึกไว้ การออกแบบถือว่ามันจะถูกขัดจังหวะ
- **เสื่อมถอยอย่างสะอาด** ไบนารีที่ขาดหาย เครือข่ายที่ล่ม หรือดิสก์ที่เต็มจะสร้างข้อผิดพลาดที่ชัดเจนบน stderr และ `state:ERROR` ใน journal โดยไม่ทำให้โมดูลเสียหาย

## ล็อก

มีเพียงหนึ่งธุรกรรมเท่านั้นที่แตะต้องสถานะได้ในแต่ละครั้ง `flock` ไม่น่าเชื่อถือบน toybox VDLU จึงทำแบบลำดับด้วยล็อกไดเรกทอรี: `mkdir "$VDLU_DIR/lock.d"` สำเร็จสำหรับผู้เรียกเพียงหนึ่งเดียวและล้มเหลวสำหรับที่เหลือ ซึ่งเป็นอะตอมมิกบนระบบไฟล์ที่สมเหตุสมผลใด ๆ ล็อกเก่าค้างที่ถูกทิ้งไว้โดยโปรเซสที่ตายแล้วจะถูกกู้คืนด้วยการตรวจสอบ PID ที่บันทึกไว้

การลองใหม่ตอนบูตอย่างอดทน (ใช้เมื่ออุปกรณ์ออฟไลน์ตอนบูต) **ไม่** ถือล็อกนี้ขณะรอ มันขอและปล่อยล็อกระหว่างความพยายามแต่ละครั้ง ดังนั้นการ `run` ด้วยมือจึงไม่เคยถูกบล็อกโดยการบูตที่กำลังรอเครือข่าย และมันไม่เคยถือ wakelock ปลอดภัยต่อแบตเตอรี่โดยการออกแบบ มีเพิ่มเติมใน [[Reboot Handling]]

## การตรวจสอบลายเซ็น: `vdlu-verify`

`vdlu-verify` คือตัวตรวจสอบลายเซ็นบนอุปกรณ์ ถูกทำให้เพรียวบางโดยเจตนา:

```
vdlu-verify <manifest.json> <keyring_dir>
```

รหัสออก `0` หมายถึงลายเซ็นของ manifest ถูกต้องเทียบกับคีย์สาธารณะของ keyring ที่ id ตรงกับ `key_id` ของ manifest; รหัสอื่นใดคือการปฏิเสธ

สิ่งที่ทำให้มันเพรียวบางคือมันใช้ **ไม่มี `openssl` บนอุปกรณ์** มันอ่านคีย์สาธารณะของ keyring เป็นไฟล์ **ดิบ 32 ไบต์** ทำให้ manifest เป็น canonical (ข้อความ manifest โดยลบฟิลด์ `sig` ออก) แฮชมันด้วย toybox `sha256sum` ถอดรหัส base64 ของลายเซ็น และส่งคีย์ดิบ ข้อความ และลายเซ็น 64 ไบต์ให้กับไบนารี `ed25519-mini` ที่ฝังมา ตัวตรวจสอบยังปฏิเสธสิ่งที่ผิดรูปแบบก่อนที่จะตรวจสอบยืนยันด้วยซ้ำ: `key_id` หรือ `sig` ที่ขาดหายหรือว่างเปล่า, `key_id` ที่มีตัวคั่นเส้นทาง, คีย์สาธารณะที่ไม่ได้มีขนาดพอดี 32 ไบต์ หรือลายเซ็นที่ไม่ได้มีขนาดพอดี 64 ไบต์

ก่อนที่มันจะเลือกคีย์เสียด้วยซ้ำ เอนจินบังคับใช้ **allowlist ของ `key_id`**: `key_id` ของ manifest ต้องเป็นคีย์ที่การตั้งค่าอนุญาตให้ลงลายเซ็น*การอัปเดตโมดูล* และคีย์ที่เพียงแค่มีอยู่ใน keyring แต่ไม่อยู่ใน allowlist จะถูกปฏิเสธก่อนที่ pubkey ของมันจะถูกโหลด keyring ที่มีคีย์เดียวปักหมุดคีย์นั้นโดยอัตโนมัติโดยไม่ต้องตั้งค่า; keyring ที่มีหลายคีย์ต้องปักหมุด `key_id` ไม่เช่นนั้นเอนจินจะล้มเหลวแบบปิด ชุดที่อนุญาตถูกส่งต่อลงไปยัง `vdlu-verify` ในชื่อ `VDLU_KEYID_ALLOW` และมันมีผลในทั้งสองโปรไฟล์ สิ่งนี้หยุดคีย์ที่มีความเชื่อถือต่ำกว่า เช่นคีย์ฟีดฟิงเกอร์พรินต์ที่ใช้ keyring ร่วมกัน ไม่ให้ลงลายเซ็นการอัปเดต root เต็มรูปแบบ; ฟีดฟิงเกอร์พรินต์ที่แยกต่างหากเก็บคีย์ที่ปักหมุดของตัวเองไว้ คือ `FEED_KEY_ID` เรื่องราวฉบับเต็มอยู่ใน [[Security and Trust Model]]

การทำ canonical เป็นแบบไบต์ต่อไบต์ที่เหมือนกับตัวลงลายเซ็นของ producer ซึ่งเป็นสิ่งที่ทำให้ลายเซ็นตรวจสอบได้ข้ามเครื่องมือ คีย์ส่วนตัวที่คู่กันไม่เคยแตะต้องอุปกรณ์หรือ CI; มีเพียงคีย์สาธารณะดิบเท่านั้นที่ถูกฝัง เรื่องราวความเชื่อถือฉบับเต็ม สองโปรไฟล์ และเหตุผลที่ `hardened` เป็น fail-closed ด้วยการกลับเงื่อนไข อยู่ใน [[Security and Trust Model]]

เอนจินเรียก `vdlu-verify` ในระหว่างเฟส diff ภายใต้โปรไฟล์ `hardened` การตรวจสอบที่ล้มเหลวจะยกเลิกการอัปเดตทั้งหมด; ภายใต้ `trusted` การตรวจสอบเป็นแบบพยายามอย่างดีที่สุด แต่แฮชของทุก blob ก็ยังคงถูกตรวจสอบเสมอ ดังนั้นเนื้อหาที่เสียหายจึงถูกจับได้ไม่ว่าจะโปรไฟล์ใด

## สถานะบนดิสก์

สถานะทั้งหมดของเอนจินอยู่ใน `$VDLU_DIR` (นอกไดเรกทอรีโมดูล) ดังนั้นต้นไม้ไฟล์โมดูลเองจึงเก็บเฉพาะไฟล์ที่เสร็จสมบูรณ์เท่านั้น:

| เส้นทาง | บทบาท |
|---|---|
| `config` | ค่าตั้งแบบ key=value (source, profile, channel, นโยบายเครือข่าย, การลองใหม่ตอนบูต) |
| `current.json` | manifest ของเวอร์ชันที่ใช้งานอยู่; นี่คือฐาน diff การไม่มีอยู่หมายถึงไม่เคยอัปเดต |
| `target.json` | manifest ที่ตรึงไว้ของธุรกรรมที่กำลังดำเนินอยู่ การมีอยู่ของมันทำเครื่องหมายธุรกรรมที่ใช้งานอยู่; มันกลายเป็น `current.json` เมื่อ `DONE` |
| `plan.tsv` / `plan.del` | แผนและความคืบหน้ารายไฟล์ และรายการเส้นทางที่จะลบ |
| `journal.json` | ความคืบหน้าสำหรับ WebUI เขียนใหม่ทุกครั้งที่สถานะเปลี่ยน |
| `blobs/<sha256>` | แคชของเนื้อหาต้นฉบับที่ตรวจสอบและคลายบีบอัดแล้ว |
| `rollback/<version>/<path>` | สำเนาสำรองของไฟล์ที่เขียนทับ; เก็บสามเวอร์ชันล่าสุด |
| `staged/<path>.vdlu-new` | ไฟล์คลาสรีบูตที่รอการสลับเปลี่ยนตอนบูต |
| `lock.d/` | ล็อก mkdir |
| `tools/<abi>/curl` | curl แบบสแตติกที่ดึงมาและตรวจสอบแล้ว; คงอยู่ข้ามการอัปเดต |
| `cancel` | คำขอยกเลิก |

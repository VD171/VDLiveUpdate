# สถาปัตยกรรม

VDLU มีสองฝั่งที่เชื่อมกันด้วยสิ่งหนึ่งตรงกลาง บน PC [[Producer]] จะแปลงต้นไม้ไฟล์โมดูลให้เป็นฟีดที่ลงลายเซ็นและกำหนดที่อยู่ด้วยเนื้อหา บนอุปกรณ์ [[Engine]] จะอ่านฟีดนั้น หาว่าอะไรเปลี่ยนไป และนำไปใช้ รอยต่อระหว่างทั้งสองคือ **manifest ที่ลงลายเซ็นบวกกับที่เก็บ blob** (ดู [[Feed Format]]) ไม่มีสิ่งอื่นข้ามช่องว่างนี้

```
        PC / release host                                device
  +--------------------------+                 +---------------------------+
  |  Producer                |                 |  Engine  (update.sh)      |
  |  vdlu-pack  -> manifest  |    signed       |  POSIX sh, no jq          |
  |  vdlu-sign  -> sig       |    feed         |  DIFF FETCH APPLY COMMIT  |
  |  vdlu-gc    -> prune     | =============>  |  journal + rollback       |
  +--------------------------+   manifest.json |  ed25519-mini verify      |
                                 blobs/<sha>   +-------------+-------------+
                                                             |
                                                       +-----v------+
                                                       |  WebUI     |
                                                       |  Updates   |
                                                       |  panel     |
                                                       +------------+
```

ทั้งสองฝั่งไม่เคยใช้รันไทม์ร่วมกัน Producer ใช้ `python3` และ `openssl`; Engine เป็น POSIX `sh` ล้วน ๆ พร้อม toybox และ `ed25519-mini` ที่ฝังมา ทั้งสองสอดคล้องกันได้ก็เพราะทั้งคู่ได้มาซึ่ง **ไบต์แบบ canonical เดียวกัน** จาก manifest (ดู [[Security and Trust Model]]) WebUI เป็นแผงบาง ๆ ที่เขียนด้วย vanilla JS ซึ่งขับเคลื่อนเอนจินผ่านสะพาน (bridge) ของโปรแกรมจัดการ root และอ่าน journal ความคืบหน้าของมัน มันไม่มีตรรกะการอัปเดตเป็นของตัวเอง ดู [[WebUI]]

## ทั้งสองฝั่ง

| ฝั่ง | ทำงานบน | สร้างจาก | หน้าที่ |
|---|---|---|---|
| [[Producer]] | PC / CI | `python3` + `sh` + `openssl` | เดินสำรวจต้นไม้ไฟล์โมดูลไปเป็น `manifest.json` + `blobs/`, ลงลายเซ็น, ตัด blob กำพร้า |
| [[Engine]] | อุปกรณ์ | POSIX `sh` + toybox + `ed25519-mini` | เปรียบเทียบส่วนต่างของต้นไม้ไฟล์ที่ติดตั้งกับฟีด, ดึงส่วนต่าง, นำไปใช้, commit |
| [[WebUI]] | อุปกรณ์ (webview) | vanilla JS/CSS | สั่งอัปเดต, แสดงความคืบหน้า, แก้ไขคอนฟิก, แสดงแบนเนอร์รีบูต |

## ไปป์ไลน์การอัปเดต

ทุกการอัปเดตคือหนึ่งธุรกรรม ดำเนินในลำดับที่ตายตัว:

```
  DIFF  ------>  FETCH  ------>  APPLY  ------>  COMMIT
  read feed      download        write live     re-hash all,
  + validate     only missing    files now,      promote target
  + plan         blobs, verify   stage reboot     -> current,
  (no changes)   each sha256     ones             DONE or
                                                  PENDING_REBOOT
```

- **DIFF** (`update.sh check` คือเฟสนี้ แบบอ่านอย่างเดียว) เอนจินดาวน์โหลดเฉพาะ manifest รัน `validate_plan()` ทุกฟิลด์ **ก่อน** ที่จะแตะต้องสิ่งใด แล้วเปรียบเทียบฟีดกับ `current.json` เพื่อสร้างแผนรายไฟล์ มันไม่เปลี่ยนอะไรบนดิสก์ อุปกรณ์ที่ล้ำหน้าฟีดเป็นผลลัพธ์ "ahead" ที่ไม่เป็นอันตราย ไม่ใช่ข้อผิดพลาด
- **FETCH** ดาวน์โหลดเฉพาะ blob ที่แผนขาดหายไป ลงใน `<sha>.part` คลายบีบอัด `gz` ตรวจสอบ `sha256sum` เทียบกับ manifest และ `mv` แต่ละ blob ที่ตรวจสอบแล้วเข้าสู่แคชแบบอะตอมมิก blob ที่แคชไว้แล้ว (หรือถูก seed จากไฟล์ในเครื่องที่ไม่เปลี่ยน) จะถูกข้าม ดังนั้นการย้อนกลับหรือไฟล์ที่ใช้ร่วมกันจึงไม่เสียค่าใช้จ่าย ความล้มเหลวสามครั้งบน blob เดียวยกเลิกเฟสโดยไม่นำสิ่งใดไปใช้ การดาวน์โหลดที่ถูกบล็อกโดยนโยบายเครือข่ายจะออกเป็น `DEFERRED` (ดำเนินต่อได้) ไม่ใช่ข้อผิดพลาด
- **APPLY** ไฟล์ธรรมดา (`live` / `soft`) จะถูกเขียนตอนนี้: สำรองไปที่ `rollback/<v>/` เขียน `.vdlu-tmp` `chmod` ตรวจสอบ แล้วทำ `rename` แบบอะตอมมิกทับเป้าหมาย ไฟล์คลาสรีบูตจะถูกสร้างเป็นรูปธรรมใน `staged/<path>.vdlu-new` และ inode ที่ใช้งานอยู่ (live) จะไม่ถูกแตะต้อง รายการ `delete[]` จะถูกสำรองไว้ก่อนแล้วจึงลบ ทุกขั้นตอนเป็น idempotent: ไฟล์ที่มีแฮชตรงกับเป้าหมายอยู่แล้วจะถูกข้าม
- **COMMIT** แฮชซ้ำทุกไฟล์ live เฉพาะเมื่อทุกอย่างตรงกันเท่านั้นเอนจินจึงเลื่อน `target.json` ขึ้นเป็น `current.json` หากมีสิ่งใดถูกจัดเตรียมไว้ ธุรกรรมจะจบด้วย `PENDING_REBOOT`; มิฉะนั้นเป็น `DONE`

## manifest และ blob แบบกำหนดที่อยู่ด้วยเนื้อหา

ฟีดกำหนดที่อยู่ด้วยเนื้อหา: manifest ระบุต้นไม้ไฟล์เป้าหมาย **ทั้งหมด** โดยแต่ละไฟล์ถูกอ้างด้วย `sha256` ของมัน และที่เก็บ blob เก็บเนื้อหาที่แตกต่างแต่ละชิ้นไว้หนึ่งสำเนาภายใต้ `blobs/<sha256>` (หรือ `blobs/<sha256>.gz`)

- **การตัดข้อมูลซ้ำ** เนื้อหาที่เหมือนกันไม่ว่าจะอยู่ที่ใดในต้นไม้ไฟล์ หรือข้ามรีลีส ก็เป็น blob เดียว การเผยแพร่เป็นแบบเพิ่มทีละส่วน: blob ที่ `sha256` มีอยู่บนโฮสต์แล้วจะไม่ถูกส่งซ้ำ และอุปกรณ์ไม่เคยดึงเนื้อหาที่มีอยู่แล้วซ้ำ
- **sha256 เป็นของต้นฉบับ** แฮชจะตั้งชื่อตามเนื้อหาที่ไม่บีบอัดเสมอ; `enc` (`raw` หรือ `gz`) บันทึกเพียงว่า blob นั้นถูกจัดเก็บอย่างไร อุปกรณ์คลายบีบอัด `gz` ด้วย toybox `gunzip` จึงไม่มีตัวบีบอัดเพิ่มที่ต้องแพ็กมา
- **เสถียรต่อรสชาติ/ตัวแปร** เพราะอุปกรณ์เปรียบเทียบส่วนต่างกับสิ่งที่ติดตั้งจริง ฟีดจึงบรรจุตระกูลโมดูลทั้งตระกูลได้ การติดตั้งแต่ละแบบดึงเฉพาะ blob ที่ทำให้รสชาติ/ตัวแปรของตัวเองครบถ้วน

โครงสร้างแบบฟิลด์ต่อฟิลด์ฉบับเต็มอยู่ใน [[Feed Format]]

## journal ที่ดำเนินต่อได้

ทุกธุรกรรมปลอดภัยต่อการล่มเพราะความคืบหน้าของมันอยู่ใน journal (`journal.json`) และเป้าหมายที่ตรึงไว้ (pinned) ของธุรกรรมที่กำลังดำเนินอยู่อยู่ใน `target.json` เครื่องสถานะ (state machine) ทำงานในลำดับที่ตายตัว:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> ( PENDING_REBOOT | DONE )
                                                               \-> ERROR / DEFERRED
```

| สถานะ | ความหมาย |
|---|---|
| `PLANNED` | สร้างแผนแล้ว ยังไม่ดึงอะไร |
| `FETCHING` / `FETCHED` | กำลังดาวน์โหลด blob / blob ทั้งหมดมีครบและตรวจสอบแล้ว |
| `APPLYING` / `APPLIED_LIVE` | กำลังเขียนไฟล์ / เขียนไฟล์ live ทั้งหมดแล้ว |
| `PENDING_REBOOT` | ไฟล์คลาสรีบูตถูกจัดเตรียมไว้ รอการสลับเปลี่ยนตอนบูต |
| `DONE` | การแฮชซ้ำทุกอย่างตรงกัน; เลื่อน `current.json` ขึ้นแล้ว |
| `ERROR` | ล้มเหลวหนัก; โมดูลไม่เสียหาย ไฟล์ live ถูกคืนค่าจาก `rollback/` |
| `DEFERRED` | การดาวน์โหลดถูกหน่วงไว้โดยนโยบายเครือข่าย; แผนยังคงอยู่ ดำเนินต่อภายหลัง |

`DONE` จะไปถึง **ก็ต่อเมื่อ** การแฮชซ้ำทุกอย่างตรงกัน ดังนั้น journal จึงไม่เคยอ้างว่าการอัปเดตที่นำไปใช้เพียงครึ่งเดียวเสร็จสมบูรณ์ การล่ม เครือข่ายหลุด หรือรีบูตกลางคันจะทิ้ง journal ที่ดำเนินต่อได้ไว้; `update.sh resume` (หรือ `boot`) จะทำต่อจากเฟสปัจจุบัน ดู [[Engine]] สำหรับชุดคำสั่งและไฟล์สถานะบนอุปกรณ์

## ความเป็นอะตอมมิกและการย้อนกลับ

ไม่มีสิ่งใดถูกเขียนทับ ณ ตำแหน่งเดิม และไม่มีสิ่งใดสูญหาย:

- **การเขียนแบบอะตอมมิก** แต่ละไฟล์ลงที่ผ่านไฟล์ชั่วคราว (`.vdlu-tmp`) และ `rename` / `mv` แบบอะตอมมิก ดังนั้นผู้อ่านจึงไม่เคยเห็นไฟล์ที่เขียนไปครึ่งเดียว
- **สำรองก่อนเขียนทับ** เนื้อหาเดิมจะไปที่ `rollback/<version>/<path>` ก่อนที่ไฟล์ใหม่จะถูก rename ทับ (เก็บไว้ไม่กี่เวอร์ชันล่าสุด) หากการนำไปใช้ล้มเหลว ไฟล์ live จะถูกคืนค่าจากสำเนา rollback แทนที่จะปล่อยให้เสียหาย การสำรองที่ล้มเหลวจะ **ยกเลิก** การนำไปใช้แทนที่จะเขียนทับโดยไม่มีตาข่ายความปลอดภัย
- **ทำแบบลำดับ (serialized)** ล็อกแบบ `mkdir` (`lock.d/` เนื่องจาก `flock` ใช้ไม่ได้บน toybox พร้อมการกู้คืนล็อกเก่าค้างด้วย PID) ทำให้การรันพร้อมกันเป็นลำดับ

## หลักการไม่ต้องรีบูต

ไฟล์ส่วนใหญ่สามารถสลับเปลี่ยนได้ขณะโมดูลทำงานอยู่ VDLU จึงนำไปใช้ทันที มีเพียงสามคลาสที่ต้องรีบูต เพราะโปรเซสที่ทำงานอยู่ได้แมป (map) ไฟล์เหล่านั้นไว้แล้ว: ไฟล์ `.so` (โหลดโดย Zygisk), overlay ของ `/system`, และ `sepolicy.rule` ไฟล์เหล่านี้จะถูก **จัดเตรียม ไม่เคยเขียนทับ inode ที่ใช้งานอยู่** และสลับเปลี่ยนในขั้นตอนก่อน zygote เพียงครั้งเดียวในการบูตครั้งถัดไป การจำแนกประเภทฉบับเต็มและโฟลว์การบูตอยู่ใน [[Reboot Handling]]

## ท่าทีความเชื่อถือแบบ fail-closed

ฟีดเป็นสิ่งเดียวที่ข้ามจาก PC มายังอุปกรณ์ เอนจินจึงปฏิบัติต่อทุกไบต์ของมันเสมือนเป็นปฏิปักษ์ `validate_plan()` รันในเฟส DIFF ก่อนการดาวน์โหลดใด ๆ และปฏิเสธ manifest ทั้งก้อนเมื่อเจอฟิลด์ที่ผิดรูปแบบ การตรวจสอบลายเซ็นใช้ `ed25519-mini` ที่ฝังมา (ไม่มี `openssl` บนอุปกรณ์) คีย์ส่วนตัวไม่เคยแตะต้องอุปกรณ์หรือ CI และโปรไฟล์ `hardened` เป็น fail-closed ด้วยการกลับเงื่อนไข ดังนั้นค่าโปรไฟล์ที่เสียหายจึงไม่สามารถยอมรับฟีดที่ไม่ลงลายเซ็นได้อย่างเงียบ ๆ โมเดลฉบับเต็ม สองโปรไฟล์ และภัยคุกคามที่แต่ละอันตอบสนองอยู่ใน [[Security and Trust Model]]

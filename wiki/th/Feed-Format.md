# รูปแบบฟีด

**ฟีด** คือสิ่งที่ VDLU เสิร์ฟผ่านสายส่งและเป็นสิ่งที่อุปกรณ์อัปเดตจากมัน มันเป็นไดเรกทอรีสแตติกธรรมดา เสิร์ฟได้ด้วยอะไรก็ได้ (GitHub Pages, เป้าหมาย rsync, เส้นทาง `file://`):

```
<source>/
  manifest.json          # the signed description of the current release
  blobs/<sha256>         # one blob per distinct file content
  blobs/<sha256>.gz      # (when the blob is stored gzipped)
```

ตัวโมดูลเองยังส่งไฟล์เพิ่มอีกหนึ่งไฟล์คือ `baseline.json` อยู่ภายในไฟล์ `.zip` (ไม่ได้เสิร์ฟจากฟีด) producer ที่สร้างทั้งหมดนี้อธิบายไว้ใน [[Producer]]; หน้านี้คือสัญญาบนสายส่ง

---

## manifest.json

manifest คือคำอธิบายฉบับสมบูรณ์ของหนึ่งรีลีส: ทุกไฟล์ในต้นไม้ไฟล์เป้าหมาย สิ่งที่จะลบ และลายเซ็นครอบคลุมทั้งก้อน

```json
{
  "schema": 1,
  "module": "demo",
  "version": 106,
  "version_name": "v106",
  "built": "2026-11-19T12:00:00Z",
  "engine_min": 5,
  "channel": "stable",
  "key_id": "release-2026",
  "files": [
    {
      "path": "webroot/index.html",
      "sha256": "<hex64>",
      "size": 1234,
      "mode": "0644",
      "enc": "raw",
      "class": "live"
    }
  ],
  "delete": ["webroot/old.html"],
  "sig": "<base64>"
}
```

### ฟิลด์

| ฟิลด์ | ความหมาย |
|---|---|
| `schema` | เวอร์ชันรูปแบบของตัว manifest เอง (ปัจจุบันคือ `1`) |
| `module` | id ของโมดูล อุปกรณ์ปฏิเสธ manifest หากไม่ตรงกับ id โมดูลของตัวเอง ดังนั้นฟีดที่ลงลายเซ็นถูกต้องสำหรับโมดูลอื่นจึงไม่สามารถถูกเสิร์ฟแทนที่ได้ |
| `version` | เวอร์ชันแบบจำนวนเต็ม เอนจินอัปเดตไปข้างหน้าเท่านั้น; ฟีดที่เก่ากว่าอุปกรณ์เป็นสถานะ "ahead" ที่ไม่เป็นอันตราย ไม่ใช่ข้อผิดพลาด |
| `version_name` | สตริงเวอร์ชันที่มนุษย์อ่านได้ (ตัวอย่างเช่น `v106`) |
| `built` | timestamp บิลด์แบบ ISO 8601 เคารพ `SOURCE_DATE_EPOCH` เพื่อความสามารถในการทำซ้ำ |
| `engine_min` | เวอร์ชันเอนจินขั้นต่ำที่ต้องใช้เพื่อนำ manifest นี้ไปใช้ |
| `channel` | ช่องทางรีลีส (ตัวอย่างเช่น `stable`) |
| `key_id` | คีย์ใดใน keyring ของอุปกรณ์ที่ลงลายเซ็น manifest นี้ เลือกคีย์สาธารณะสำหรับการตรวจสอบ และต้องอยู่ใน allowlist ของการอัปเดตโมดูลของเอนจิน (ดู [[Security and Trust Model]]); คีย์ที่เพียงแค่มีอยู่ใน keyring แต่ไม่อยู่ใน allowlist จะถูกปฏิเสธก่อนที่ pubkey ของมันจะถูกโหลด |
| `files[]` | ต้นไม้ไฟล์เป้าหมาย **ทั้งหมด** (ไม่ใช่ diff) แต่ละรายการ: `path`, `sha256`, `size`, `mode`, `enc` (`raw`/`gz`), `class` (`live`/`soft`/`reboot`) |
| `delete[]` | เส้นทางที่มีอยู่ในรีลีสก่อนหน้าแต่หายไปแล้วตอนนี้ ให้อุปกรณ์นำออก |
| `sig` | ลายเซ็น ed25519 แบบ base64 ดูการทำ canonical ด้านล่าง |

`files[]` อธิบายต้นไม้ไฟล์ **ทั้งหมด** ไม่ใช่ delta อุปกรณ์คำนวณ delta เองโดยการเปรียบเทียบ manifest กับสิ่งที่มันมีอยู่แล้ว และ fetch เฉพาะ blob ที่ `sha256` ของมันขาดหายไป `sha256` เป็นของเนื้อหาต้นฉบับ (ที่ไม่บีบอัด) เสมอ; `enc` เพียงบอกว่า blob นั้นถูกจัดเก็บใน `blobs/` อย่างไร ความหมายของ `class` และสิ่งที่อุปกรณ์ทำกับแต่ละค่าถูกครอบคลุมใน [[Reboot Handling]]

## การทำ canonical (ไบต์ที่ลงลายเซ็น)

นี่คือค่าคงที่ที่สำคัญที่สุดเพียงหนึ่งเดียวในรูปแบบนี้ ตัวลงลายเซ็นบน PC และตัวตรวจสอบบนอุปกรณ์รันบนรันไทม์ที่ต่างกันโดยสิ้นเชิง (openssl บน PC, toybox + ตัวตรวจสอบจิ๋วที่ฝังมาบนอุปกรณ์ และ **ไม่มีไลบรารี JSON เลย** บนอุปกรณ์) ทั้งคู่ต้องได้มาซึ่งไบต์เดียวกันเป๊ะเพื่อลงลายเซ็นและตรวจสอบ กฎจึงเป็น **การแปลงไบต์** โดยเจตนา ไม่ใช่การ serialize JSON ใหม่

**ขั้นตอนที่ 1: รูปแบบจัดเก็บที่ตายตัว** `vdlu-pack` เขียน `manifest.json` แบบกระชับ ด้วยคีย์เรียงลำดับ UTF-8 รวม `key_id` และ `sig` เสมอ (เป็นสตริงว่างจนกว่าจะลงลายเซ็น):

```
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

**ขั้นตอนที่ 2: ตัดเฉพาะ `sig`** รูปแบบ canonical คือข้อความนั้นเป๊ะโดย **ลบเฉพาะฟิลด์ `"sig"`** เพราะคีย์ถูกเรียงลำดับ `sig` จึงปรากฏเป็น `,"sig":"<value>",` เสมอ ขนาบด้วย `"schema"` ก่อนและ `"version"` หลัง (ทั้งคู่มีอยู่เสมอ) ดังนั้นการลบมันจึงเหลือข้อความที่รูปแบบถูกต้อง JSON escape ทุก `"` ภายในค่าสตริงเป็น `\"` ดังนั้น token เชิงโครงสร้าง `"sig":"` จึงไม่กำกวมแม้เทียบกับชื่อไฟล์ที่มี `"sig":"` อยู่จริง ๆ

การลบคือการขยายพารามิเตอร์ POSIX เพียงไม่กี่ตัว เหมือนกันในตัวลงลายเซ็นและตัวตรวจสอบ โดยไม่มี `sed` และไม่มี `jq`:

```sh
# $1 = the full manifest text
_pre=${_c%%\"sig\":\"*}     # up to  ...,"schema":N,
_rest=${_c#*\"sig\":\"}      # after "sig":"
_tail=${_rest#*\",}          # after <value>",  ->  "version":...
printf '%s%s' "$_pre" "$_tail" | sha256sum | cut -d' ' -f1
```

**ขั้นตอนที่ 3: ลงลายเซ็นแฮชของสิ่งนั้น** ข้อความที่ลงลายเซ็น/ตรวจสอบคือ **sha256 hex** (64 อักขระ ASCII ไม่มีการขึ้นบรรทัดใหม่) ของรูปแบบ canonical ed25519 ลงลายเซ็น hex นั้น

ผลที่ตามมาสองอย่างเกิดขึ้นจากสิ่งนี้โดยโครงสร้าง:

- `key_id` เป็นส่วนหนึ่งของรูปแบบ canonical (ตัดเฉพาะ `sig`) `vdlu-sign` ตั้งค่า `key_id` **ก่อน** การแฮช ดังนั้นอัตลักษณ์ของคีย์จึงถูกครอบคลุมโดยลายเซ็น
- ไม่ว่าตัวแทน `sig` จะว่างเปล่า (`"sig":""` ในเวลาลงลายเซ็น) หรือถูกเติม (ในเวลาตรวจสอบ) การตัดมันออกให้ไบต์ canonical ที่เหมือนกัน การลงลายเซ็นและการตรวจสอบสอดคล้องกันโดยอัตโนมัติ

เครื่องมือ POSIX sh ทั้งสองเป็นผู้มีอำนาจตัดสิน (authoritative) ตัวเทียบเท่า Python คือ `re.sub(r'"sig":"[^"]*",', '', text, count=1)` แล้ว sha256 มีอยู่เพียงเพื่อตรวจสอบไขว้กับมัน

เหตุผลด้านความเชื่อถือรอบ ๆ ทั้งหมดนี้ (ทำไมการตรวจสอบจึงอยู่บนอุปกรณ์ `hardened` ปิดเมื่อล้มเหลวอย่างไร) อยู่ใน [[Security and Trust Model]]

## baseline.json (seed การติดตั้ง)

เมื่อโมดูลเพิ่งถูกติดตั้งใหม่ มันควรเป็น "ปัจจุบัน" สำหรับเวอร์ชันที่ส่งมาของตัวเองอยู่แล้ว โดยไม่มีการอัปเดตตัวเองที่ไม่จำเป็นของเวอร์ชันที่เพิ่งติดตั้ง นั่นคือสิ่งที่ `baseline.json` ทำ

`baseline.json` ถูกส่งมา **ภายใน zip ของโมดูล** (ที่ `vdlu/baseline.json`) ไม่ใช่บนฟีด เมื่อติดตั้งใหม่ เอนจิน seed บันทึก "เวอร์ชันที่ใช้งานอยู่" ของมันจากไฟล์นี้ ดังนั้นอุปกรณ์จึงเกิดมาเป็นปัจจุบัน โดยไม่มี `from:0` และไม่มีการ fetch ซ้ำสิ่งที่มันมีอยู่แล้ว

คุณสมบัติสำคัญ:

- มันเป็น **สำเนาไร้คีย์ของ manifest ที่ลงลายเซ็น** สำหรับเวอร์ชันที่ส่งมา: เอาต์พุต `vdlu-pack` เดียวกัน ที่ปล่อยไว้โดยไม่ลงลายเซ็น (`key_id` และ `sig` ยังคงว่างเปล่า)
- มัน **ไม่ถูกตรวจสอบ** เอนจินถือว่ามันเป็น seed ท้องถิ่นที่เชื่อถือได้เพราะมันมาถึงภายใน zip ที่แฟลช ซึ่งเป็นขอบเขตความเชื่อถือของการติดตั้ง เฉพาะ manifest ที่ *fetch มาจากฟีด* เท่านั้นที่ผ่านการตรวจสอบลายเซ็น
- เพราะมันไม่ต้องการลายเซ็น **CI จึงสร้างมันแบบไร้คีย์ได้** ซึ่งเป็นสิ่งที่ทำให้คีย์ลงลายเซ็นอยู่นอก CI โดยสมบูรณ์ (ดู [[Producer]])
- `vdlu-pack` **กีดกัน `baseline.json` ออกจาก manifest ของตัวเอง** ดังนั้น manifest จึงไม่เคยอ้างถึง baseline (นั่นจะเป็นลูปอ้างอิงตัวเอง: manifest ไป baseline ไป manifest)
- มัน **ไม่ร้ายแรงหากขาดหาย** หากไม่มีมัน อุปกรณ์เพียงเริ่มจาก `from:0` ในการอัปเดตครั้งแรกและ fetch สิ่งที่มันต้องการ ไม่เคยพัง เพียงไม่เหมาะที่สุด

## Blobs

เนื้อหาไฟล์ที่แตกต่างกันแต่ละชิ้นเป็นหนึ่ง blob ภายใต้ `blobs/` ตั้งชื่อตาม **sha256 ของเนื้อหาต้นฉบับ**:

- `blobs/<sha256>` สำหรับ blob แบบ raw
- `blobs/<sha256>.gz` สำหรับ blob ที่ gzip แล้ว (gzip ถูกเก็บไว้เฉพาะเมื่อไฟล์มีขนาดอย่างน้อย 4096 ไบต์และการบีบอัดประหยัดได้อย่างน้อย 10 เปอร์เซ็นต์)

blob ถูกจัดเก็บครั้งเดียว ในหนึ่งรูปแบบ การกำหนดที่อยู่ด้วยเนื้อหาให้การตัดข้อมูลซ้ำฟรี: เนื้อหาที่ไม่เปลี่ยน ใช้ร่วมกัน หรือถูกย้อนกลับ แมปไปยัง blob ที่มีอยู่แล้ว ดังนั้นฟีดจึงโตขึ้นเฉพาะด้วยเนื้อหาใหม่จริง ๆ และอุปกรณ์ดาวน์โหลดเฉพาะแฮชที่มันขาดหายไป อุปกรณ์ตรวจสอบ `sha256` ของทุก blob ที่ดาวน์โหลดเทียบกับ manifest (หลังจากคลายบีบอัด blob `gz`) ก่อนใช้งาน

## สิ่งที่ถูกกีดกันออกจากฟีด และทำไม

ฟีดบรรจุ **เฉพาะเนื้อหาของตัวโมดูลเอง** ชุดเส้นทางที่ตายตัวถูกกันออกจากมันโดยเจตนา `vdlu-pack` ใช้ predicate การกีดกันหนึ่งอันทั้งเมื่อเดินสำรวจต้นไม้ไฟล์และเมื่อคำนวณ `delete[]`

| ถูกกีดกัน | ทำไม |
|---|---|
| `vdlu/keyring/`, `vdlu/verify/` (รากความเชื่อถือ: คีย์สาธารณะดิบ + ไบนารีตัวตรวจสอบ) | **นี่คือเหตุผลความปลอดภัยหลัก** จุดยึดความเชื่อถือ (trust anchor) เป็นแบบ **flash เท่านั้น** หาก keyring หรือตัวตรวจสอบสามารถส่งผ่านฟีดได้ manifest ก็สามารถเขียนทับสิ่งที่ตรวจสอบตัวมันเองได้ การกันพวกมันออกจากสายส่งหมายความว่า manifest ไม่สามารถเขียนทับจุดยึดความเชื่อถือบนอุปกรณ์ได้เลย ในฐานะ guard ที่สองซึ่งเป็นอิสระ (`ENGINE_VERSION` 5) engine ยัง **เพิกเฉย** ทุก path `vdlu/` ใน plan ที่ fetch มาด้วย ดังนั้นแม้แต่ฟีดที่พกมันมาก็ไม่สามารถแตะจุดยึดความเชื่อถือได้ |
| `vdlu/baseline.json` | มันเป็นสำเนาของ manifest ที่ลงลายเซ็น (seed การติดตั้ง); การ pack มันจะเป็นลูปอ้างอิงตัวเอง |
| โครงสร้างพื้นฐานแฟลช `.vd/` | นั่งร้าน flash-gate ที่ส่งมาใน zip ไม่เคยถูกนำไปใช้สด ๆ |
| `update.json`, `update-mmrl.json` | ขนาด/sha ของพวกมันถูกเติมโดย CI *หลังจาก* สร้าง zip แล้ว ดังนั้นสำเนาที่ส่งมาจึงต่างจากสำเนาฟีดใด ๆ การป้อนพวกมันจะทำให้เกิดการ fetch ไฟล์เดียวแบบหลอน (phantom) ในการอัปเดตตัวเองครั้งแรกของทุกการติดตั้ง และพวกมันก็เป็นส่วนเกินบนอุปกรณ์อยู่แล้ว (ตัวจัดการอ่านอัปเดต JSON ดิบจากระยะไกล) |
| `META-INF/`, `customize.sh` (นั่งร้านตัวติดตั้ง) | ถูกบริโภคโดยตัวจัดการในเวลา **แฟลช** และไม่ถูกเก็บไว้ในโมดูลที่ติดตั้งแล้ว พวกมันไม่ใช่เนื้อหา VDLU; การเสิร์ฟพวกมันสิ้นเปลือง blob และหากอันใดเคยเปลี่ยนระหว่างเวอร์ชัน มันจะถูกเขียนเป็นไฟล์ตัวติดตั้งเข้าไปในไดเรกทอรีโมดูลที่ใช้งานอยู่ |
| ไฟล์คู่ `.sha256` ต่อไฟล์ | พวกมันเป็นของ zip ที่แฟลชได้เท่านั้น เก่าค้างหลังการอัปเดตแบบเพิ่มทีละส่วน และจะทำให้ manifest ใหญ่เป็นสองเท่า |
| ไฟล์ dev/doc (`RELEASE.md`, `CLAUDE.md`, `.gitignore`) | ไม่เคยส่งไปยังอุปกรณ์; การเสิร์ฟพวกมันสิ้นเปลือง blob และปั่น manifest ที่ลงลายเซ็นทุกครั้งที่แก้ไข doc |

เหตุผลเบื้องหลังการกีดกันรากความเชื่อถือถูกขยายความใน [[Security and Trust Model]]

## ความหมายของ delete[]

`delete[]` บอกอุปกรณ์ว่าเส้นทางใดที่จะนำออก เพื่อให้ไฟล์ที่ถูกตัดระหว่างรีลีสไม่ค้างอยู่บนอุปกรณ์ในฐานะกำพร้า มันถูกคำนวณโดยการส่ง `--prev <previous manifest.json>` ให้ `vdlu-pack`: เส้นทางที่อยู่ในรีลีสก่อนหน้าและไม่อยู่ในรีลีสปัจจุบันจะกลายเป็นรายการ delete

กฎสำคัญ: **เส้นทางที่ถูกกีดกันจะไม่เคยถูกปล่อยออกมาเป็นการลบ แม้ด้วย `--prev`** ทุกเส้นทางก่อนหน้าถูกรันผ่าน predicate การกีดกันเดียวกับที่ใช้เมื่อเดินสำรวจต้นไม้ไฟล์ หาก `--prev` ชี้ไปยัง manifest ที่เก่ากว่าซึ่งยังระบุเส้นทางที่ตอนนี้ถูกกีดกัน (`baseline.json` ที่หลงเหลือ, `META-INF/*`, รายการ keyring และอื่น ๆ) เส้นทางเหล่านั้นจะ **ไม่** ถูกเปลี่ยนเป็นรายการ delete เส้นทางที่ถูกกีดกันไม่เคยเป็นเนื้อหาฟีด ดังนั้นมันจึงไม่ใช่ของ VDLU ที่จะลบ และอุปกรณ์ไม่เคยถูกสั่งให้นำไฟล์ที่ไม่ได้ถูกเสิร์ฟผ่านฟีดออก นี่คือสิ่งที่ป้องกันรายการการกีดกันจากการย้อนกลับมาเป็นคำสั่งทำลายล้าง

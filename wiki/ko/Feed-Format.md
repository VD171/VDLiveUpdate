# Feed Format

**피드**는 VDLU가 회선을 통해 제공하는 것이자 기기가 업데이트하는 대상입니다. 무엇으로든(GitHub Pages, rsync 대상, `file://` 경로) 제공 가능한 평범한 정적 디렉터리입니다:

```
<source>/
  manifest.json          # the signed description of the current release
  blobs/<sha256>         # one blob per distinct file content
  blobs/<sha256>.gz      # (when the blob is stored gzipped)
```

모듈 자체는 또한 추가 파일 하나인 `baseline.json`을 `.zip` 안에 배포합니다(피드에서 제공되지 않음). 이 모든 것을 빌드하는 producer는 [[Producer]]에 설명되어 있습니다. 이 페이지는 회선상의 계약입니다.

## manifest.json

매니페스트는 하나의 릴리스에 대한 완전한 설명입니다: 대상 트리의 모든 파일, 무엇을 삭제할지, 그리고 전체에 대한 서명.

```json
{
  "schema": 1,
  "module": "demo",
  "version": 106,
  "version_name": "v106",
  "built": "2026-11-19T12:00:00Z",
  "engine_min": 3,
  "channel": "stable",
  "key_id": "release-2026",
  "files": [
    {
      "path": "webroot/index.html",
      "sha256": "<hex64>",
      "size": 1234,
      "mode": "0644",
      "enc": "raw",
      "class": "live"
    }
  ],
  "delete": ["webroot/old.html"],
  "sig": "<base64>"
}
```

### 필드

| 필드 | 의미 |
|---|---|
| `schema` | 매니페스트 자체의 포맷 버전(현재 `1`). |
| `module` | 모듈 id. 기기는 자신의 모듈 id와 일치하지 않으면 매니페스트를 거부하므로, 다른 모듈을 위한 유효하게 서명된 피드가 그 자리에 제공될 수 없습니다. |
| `version` | 정수 버전. 엔진은 앞으로만 업데이트합니다. 기기보다 오래된 피드는 오류가 아니라 무해한 "ahead" 상태입니다. |
| `version_name` | 사람이 읽을 수 있는 버전 문자열(예: `v106`). |
| `built` | ISO 8601 빌드 타임스탬프. 재현성을 위해 `SOURCE_DATE_EPOCH`를 존중합니다. |
| `engine_min` | 이 매니페스트를 적용하는 데 필요한 최소 엔진 버전. |
| `channel` | 릴리스 채널(예: `stable`). |
| `key_id` | 기기 keyring의 어느 키가 이 매니페스트에 서명했는지. 검증용 공개 키를 선택합니다. 그리고 엔진의 모듈 업데이트 허용 목록에 있어야 합니다([[Security and Trust Model]] 참조). keyring에 단지 존재하지만 허용 목록에 없는 키는 그 pubkey가 로드되기 전에 거부됩니다. |
| `files[]` | **완전한** 대상 트리(diff 아님). 각 항목: `path`, `sha256`, `size`, `mode`, `enc`(`raw`/`gz`), `class`(`live`/`soft`/`reboot`). |
| `delete[]` | 이전 릴리스에는 있었지만 지금은 사라진 경로로, 기기가 제거할 것. |
| `sig` | ed25519 서명, base64. 아래 정규화를 참조. |

`files[]`는 델타가 아니라 **전체** 트리를 설명합니다. 기기는 매니페스트를 자신이 이미 가진 것과 비교하여 델타를 스스로 계산하고, `sha256`이 누락된 블롭만 가져옵니다. `sha256`은 항상 원본(압축되지 않은) 콘텐츠의 것입니다. `enc`는 그 블롭이 `blobs/`에 어떻게 저장되었는지만 말합니다. `class`의 의미와 기기가 각 값으로 하는 일은 [[Reboot Handling]]에서 다룹니다.

## 정규화(서명되는 바이트)

이것은 이 포맷에서 가장 중요한 단일 불변식입니다. PC 서명기와 기기 내 검증기는 완전히 다른 런타임에서 실행됩니다(PC에서는 openssl, 기기에서는 toybox + 아주 작은 내장 검증기, 그리고 기기에는 **JSON 라이브러리가 전혀 없음**). 그래도 둘은 서명하고 검증할 정확히 같은 바이트를 도출해야 합니다. 따라서 규칙은 JSON 재직렬화가 아니라 의도적인 **바이트 변환**입니다.

**1단계: 고정된 저장 형식.** `vdlu-pack`은 `manifest.json`을 compact하게, 키 정렬, UTF-8, 항상 `key_id`와 `sig` 포함(서명될 때까지는 빈 문자열)으로 씁니다:

```
json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
```

**2단계: `sig`만 벗겨 냄.** 정규 형식은 **오직 `"sig"` 필드만 제거된** 바로 그 텍스트입니다. 키가 정렬되어 있으므로, `sig`는 항상 그 앞의 `"schema"`와 그 뒤의 `"version"`(둘 다 항상 존재)으로 괄호 쳐진 `,"sig":"<value>",`로 나타나므로, 그것을 제거하면 올바른 형식의 텍스트가 남습니다. JSON은 문자열 값 안의 모든 `"`를 `\"`로 이스케이프하므로, 구조적 토큰 `"sig":"`는 글자 그대로 `"sig":"`를 담은 파일명에 대해서도 모호하지 않습니다.

제거는 몇 개의 POSIX 매개변수 확장이며, 서명기와 검증기에서 동일하고, `sed`도 `jq`도 없습니다:

```sh
# $1 = the full manifest text
_pre=${_c%%\"sig\":\"*}     # up to  ...,"schema":N,
_rest=${_c#*\"sig\":\"}      # after "sig":"
_tail=${_rest#*\",}          # after <value>",  ->  "version":...
printf '%s%s' "$_pre" "$_tail" | sha256sum | cut -d' ' -f1
```

**3단계: 그것의 해시에 서명.** 서명되고 검증되는 메시지는 정규 형식의 **sha256 16진수**(64 ASCII 문자, 개행 없음)입니다. ed25519가 그 16진수에 서명합니다.

이로부터 두 가지 결과가 구성상 따라 나옵니다:

- `key_id`는 정규 형식의 일부입니다(`sig`만 벗겨짐). `vdlu-sign`은 해시하기 **전에** `key_id`를 설정하므로, 키 정체성이 서명에 의해 커버됩니다.
- `sig` 자리표시자가 비어 있든(`"sig":""`, 서명 시점) 채워져 있든(검증 시점), 그것을 벗겨 내면 동일한 정규 바이트가 나옵니다. 서명과 검증은 자동으로 일치합니다.

두 POSIX sh 도구가 권위를 가집니다. Python 등가물 `re.sub(r'"sig":"[^"]*",', '', text, count=1)` 다음 sha256은 그것들을 교차 확인하기 위해서만 존재합니다.

이 모든 것을 둘러싼 신뢰 추론(검증이 왜 기기 내에서 이루어지는지, `hardened`가 어떻게 fail-closed인지)은 [[Security and Trust Model]]에 있습니다.

## baseline.json(설치 seed)

모듈이 막 설치될 때, 그것은 자신이 방금 설치한 버전을 불필요하게 자가 업데이트하지 않고, 이미 자신의 배포 버전에 대해 "current"여야 합니다. 그것이 `baseline.json`이 하는 일입니다.

`baseline.json`은 피드가 아니라 **모듈 zip 안**(`vdlu/baseline.json`에)에 배포됩니다. 새 설치에서 엔진은 그것으로부터 자신의 "active version" 기록을 seed하므로, 기기가 `from:0` 없이, 이미 가진 것을 다시 가져오는 일 없이 current 상태로 태어납니다.

주요 속성:

- 배포 버전에 대한 **서명된 매니페스트의 키 없는 사본**입니다: 같은 `vdlu-pack` 출력을 서명되지 않은 채로 둔 것(`key_id`와 `sig`는 비어 있음).
- **검증되지 않습니다.** 엔진은 그것이 플래시된 zip 안에 도착했으므로(그것이 설치 신뢰 경계) 로컬 신뢰 seed로 취급합니다. 오직 *피드에서 가져온* 매니페스트만 서명 검증을 거칩니다.
- 서명이 필요 없으므로 **CI가 키 없이 생성할 수 있고**, 그것이 서명 키를 CI에서 전적으로 벗어나게 유지합니다([[Producer]] 참조).
- `vdlu-pack`은 **`baseline.json`을 자신의 매니페스트에서 제외**하므로, 매니페스트는 baseline을 절대 참조하지 않습니다(그것은 자기 참조 루프가 될 것: manifest에서 baseline으로 manifest로).
- **없어도 치명적이지 않습니다.** 그것 없이 기기는 그저 첫 업데이트에서 `from:0`으로 시작하여 필요한 것을 가져옵니다. 고장은 아니고, 그저 덜 최적일 뿐입니다.

## 블롭

서로 다른 각 파일 콘텐츠는 **원본 콘텐츠의 sha256**으로 이름 붙여진 `blobs/` 아래의 블롭 하나입니다:

- raw 블롭의 경우 `blobs/<sha256>`.
- gzip된 블롭의 경우 `blobs/<sha256>.gz`(gzip은 파일이 최소 4096바이트이고 압축이 최소 10퍼센트를 절약할 때만 유지됨).

블롭은 한 번, 한 형식으로 저장됩니다. 콘텐츠 주소화는 중복 제거를 공짜로 줍니다: 변경되지 않거나, 공유되거나, 되돌려진 콘텐츠는 이미 존재하는 블롭에 매핑되므로, 피드는 진정으로 새로운 콘텐츠로만 커지고, 기기는 누락된 해시만 다운로드합니다. 기기는 사용하기 전에(`gz` 블롭을 압축 해제한 뒤) 다운로드된 모든 블롭의 `sha256`을 매니페스트와 대조합니다.

## 피드에서 제외되는 것, 그리고 이유

피드는 **오직 모듈 자신의 콘텐츠만** 실어 나릅니다. 고정된 경로 집합이 의도적으로 빠져 있습니다. `vdlu-pack`은 트리를 순회할 때와 `delete[]`를 계산할 때 모두 하나의 제외 판정식을 적용합니다.

| 제외 대상 | 이유 |
|---|---|
| `vdlu/keyring/`, `vdlu/verify/`(신뢰 루트: 원시 공개 키 + 검증기 바이너리) | **이것이 핵심 보안 이유입니다.** 신뢰 앵커는 **flash 전용**입니다. keyring이나 검증기가 피드로 전달 가능하다면, 매니페스트가 자신을 검증하는 바로 그것을 덮어쓸 수 있습니다. 그것들을 회선에서 빼 두면 매니페스트가 기기 내 신뢰 앵커를 절대 다시 쓸 수 없습니다. |
| `vdlu/baseline.json` | 서명된 매니페스트의 사본(설치 seed)입니다. 그것을 packing하면 자기 참조 루프가 됩니다. |
| `.vd/` flash 인프라 | zip에 배포되고 절대 라이브로 적용되지 않는 flash-gate 스캐폴딩. |
| `update.json`, `update-mmrl.json` | 그 size/sha는 zip이 빌드된 *뒤에* CI가 채우므로, 배포된 사본이 어떤 피드 사본과도 다릅니다. 그것들을 피드에 넣으면 모든 설치의 첫 자가 업데이트마다 유령 단일 파일 fetch를 일으키며, 어차피 기기 내에서는 흔적만 남은 것입니다(관리자가 원격 raw update JSON을 읽음). |
| `META-INF/`, `customize.sh`(설치 스캐폴딩) | **flash** 시점에 관리자가 소비하고 설치된 모듈에 보관되지 않습니다. VDLU 콘텐츠가 아닙니다. 그것들을 제공하면 블롭을 낭비하고, 만약 버전 간에 바뀌기라도 하면 설치 파일로 라이브 모듈 디렉터리에 쓰이게 됩니다. |
| 파일별 `.sha256` 동반 파일 | 플래시 가능한 zip에만 속하고, 증분 업데이트 후 오래되며, 매니페스트를 두 배로 늘립니다. |
| 개발/문서 파일(`RELEASE.md`, `CLAUDE.md`, `.gitignore`) | 기기에 절대 배포되지 않습니다. 그것들을 제공하면 블롭을 낭비하고 문서 편집마다 서명된 매니페스트를 요동치게 합니다. |

신뢰 루트 제외의 배경 논리는 [[Security and Trust Model]]에서 확장됩니다.

## delete[] 의미론

`delete[]`는 기기에 어느 경로를 제거할지 알려 주므로, 릴리스 사이에 떨어져 나간 파일이 기기에 고아로 머물지 않습니다. `vdlu-pack`에 `--prev <previous manifest.json>`을 전달하여 계산됩니다: 이전 릴리스에는 있었고 현재에는 없는 경로가 삭제 항목이 됩니다.

중요한 규칙: **제외된 경로는 `--prev`가 있어도 절대 삭제로 내보내지지 않습니다.** 모든 이전 경로는 트리를 순회할 때 사용되는 것과 같은 제외 판정식을 거칩니다. `--prev`가 이제는 제외된 경로를 여전히 나열하던 더 오래된 매니페스트를 가리키면(떠도는 `baseline.json`, `META-INF/*`, keyring 항목 등), 그 경로들은 삭제 항목으로 **바뀌지 않습니다**. 제외된 경로는 애초에 피드 콘텐츠가 아니었으므로, VDLU가 삭제할 것이 아니며, 기기는 피드를 통해 제공되지 않은 파일을 제거하라는 명령을 절대 받지 않습니다. 이것이 제외 목록이 파괴적 명령으로 되돌아오는 것을 막습니다.

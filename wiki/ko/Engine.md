# Engine

엔진은 VDLU의 기기 측입니다: 폰에서 실행되어 무엇이 바뀌었는지 판단하고, 그것을 다운로드하고, 적용하는 부분입니다. 단일 POSIX 셸 스크립트인 `engine/update.sh`와 아주 작은 서명 검사기 `engine/vdlu-verify`로 이루어집니다. 둘 다 호스트 모듈의 `<module>/vdlu/`에 vendor되어 루트로 실행됩니다.

엔진 전체는 하나의 아이디어를 중심으로 만들어졌습니다: 업데이트는 **재개 가능한 트랜잭션**이라는 것. 폰이 재부팅되거나, 종료되거나, 도중에 네트워크를 잃어도, 다음 실행이 멈춘 바로 그 지점에서 이어 받으며, 모듈은 완료된 척하면서 절반만 적용된 채로 절대 남겨지지 않습니다.

큰 그림을 먼저 보려면 [[Architecture]]를 참조하세요. 업데이트가 가능할 때마다 어떻게 재부팅을 피하는지는 [[Reboot Handling]]을 참조하세요.

## 노트북이 아니라 기기를 위해 작성됨

`update.sh`는 순수 POSIX `sh`입니다. bash 전용 기능 없이 mksh, busybox, 또는 toybox에서 실행되며, `sh -n`을 통과합니다. 루팅된 Android 기기의 환경이 작고 엄격하기 때문에 이것이 중요합니다.

특히 `jq`가 없습니다. VDLU는 `awk`로 작성된 작은 gron 스타일 평탄화기로 `manifest.json`을 파싱합니다: JSON을 한 글자씩 순회하며 리프마다 `path<TAB>value` 줄 하나를 내보냅니다(예: `files/0/sha256<TAB>ab..` 또는 `version<TAB>6`). 그런 다음 셸이 `grep`과 `cut`으로 그 줄들을 읽습니다. 이것은 compact JSON과 pretty-print JSON 모두에서 동작하며, 거기 없는 JSON 도구로 절대 빠져나가지 않습니다.

엔진은 toybox가 이미 제공하는 것(`sha256sum`, `gzip`/`gunzip`, `base64`, `date`), 내장된 `ed25519-mini` 검증기, 그리고 `https://` 피드의 경우 한 번 가져와 검증되는 작은 정적 `curl`에만 의존합니다. `file://` 피드는 `curl`이 전혀 필요 없습니다.

## 여섯 가지 명령

엔진을 호출할 때는 환경에 모듈의 경로를 담고 명령 하나를 줍니다:

```sh
VDLU_DIR=/data/adb/<mod>/vdlu MODULE_DIR=/data/adb/modules/<mod> MODID=<mod> \
  sh "$MODULE_DIR/vdlu/update.sh" <cmd>
```

종료 코드 `0`은 성공을 뜻합니다. 그 외의 코드는 오류를 뜻하며, 이유가 stderr에 출력됩니다.

| 명령 | 하는 일 |
|---|---|
| `check` | 읽기 전용 diff. 매니페스트를 다운로드하고, 설치된 것과 비교하여, 한 줄 JSON 요약을 출력합니다: `{"update":bool,"from":N,"to":M,"fetch":K,"reboot":bool}`. 디스크의 어떤 것도 바꾸지 않습니다. 기기가 피드보다 최신이면(차단된 다운그레이드) 오류가 아니라 종료 `0`과 함께 `{"update":false,"ahead":true,...}`를 보고합니다. |
| `run` | 전체 라이브 사이클: DIFF, FETCH, APPLY, COMMIT. 모든 라이브 파일을 즉시 적용하고 소수의 reboot 클래스 파일을 스테이징합니다. `cancel`을 존중합니다. 진행 상황을 `journal.json`에 기록합니다. |
| `resume` | 중단된 트랜잭션을 그것이 있던 단계부터 이어서 진행합니다. 멱등적입니다. 스테이징된 `.so`를 교체하지는 **않습니다**(그것은 `boot` 전용). |
| `boot` | pre-zygote 경로. `resume`을 수행한 뒤 스테이징된 `*.vdlu-new` 파일들을 제자리에 교체하여 `PENDING_REBOOT`를 `DONE`으로 닫습니다. 보류 중인 트랜잭션이 없으면 새 사이클을 실행하여 `.so`를 포함한 모든 것을 그 단일 부팅에서 적용합니다. |
| `status` | `journal.json`을 출력하거나, 진행 중인 것이 없으면 `{"state":"idle"}`를 출력합니다. |
| `cancel` | `cancel` 마커를 만듭니다. 진행 중인 `run`은 다음 안전 지점에서 깨끗하게 멈춥니다. |

`check` 명령은 의도적으로 저렴하여, UI가 어떤 네트워크에서도 업데이트가 있음을 알려 줄 수 있습니다. 실제 다운로드는 별도로 게이팅됩니다(아래 fetch 단계 참조).

## 트랜잭션, 단계별

모든 `run`은 `journal.json`에 기록되는 고정된 상태 기계를 거치므로, WebUI(그리고 여러분)가 지켜볼 수 있습니다:

```
PLANNED -> FETCHING -> FETCHED -> APPLYING -> APPLIED_LIVE -> (PENDING_REBOOT | DONE)
```

**DIFF.** 엔진은 `manifest.json`을 가져와 모든 필드를 검증하고(아래와 [[Security and Trust Model]] 참조), 서명된 대상 트리를 이미 설치된 버전의 매니페스트인 `current.json`과 비교합니다. 그 결과가 `plan.tsv`에 기록되는 파일별 계획입니다: 파일마다 한 행으로, 그 클래스, 대상 해시, 모드, 진행 상태를 담습니다. 이미 대상 해시인 파일은 건너뛰도록 표시됩니다.

**FETCH.** 여전히 필요한 각 파일에 대해, 엔진은 그 콘텐츠 주소화 블롭을 `<source>/blobs/<sha>`(압축된 경우 `<sha>.gz`)에서 `.part` 파일로 다운로드합니다. 블롭이 gzip이면 압축 해제한 뒤, 그 SHA-256을 매니페스트와 대조합니다. 일치할 때만 원자적으로 `blobs/<sha>`로 `mv`됩니다. 올바른 해시로 이미 캐시된 블롭은 완전히 건너뛰고, 변경되지 않은 로컬 파일은 다운로드 없이 캐시를 seed할 수 있습니다. 같은 블롭에 세 번 실패하면 아무것도 적용하지 않고 단계를 중단합니다. 계획의 모든 블롭이 존재하고 검증되어야만 비로소 `FETCHED`에 도달합니다. 이 블롭들이 나오는 [[Feed Format]]에 대해서는 해당 페이지를 참조하세요.

fetch는 네트워크 정책에 의해 게이팅됩니다: 피드는 Wi-Fi 전용, 모바일 전용, 또는 모든 네트워크로 제한될 수 있습니다. 현재 네트워크가 허용되지 않을 때 fetch는 실패하지 않습니다. 무해한 `DEFERRED` 상태로 진입하여 계획과 대상을 고정해 두고, 올바른 네트워크가 나타나면 다음 check나 boot에서 재개합니다. 그동안 데이터는 전혀 쓰이지 않습니다.

**APPLY.** 오직 `FETCHED`에서만 진입합니다. 각 파일에 대해 엔진은 클래스별로 동작합니다:

- `live` 및 `soft` 파일: 현재 파일을 `rollback/<version>/<path>`로 백업하고, 새 콘텐츠를 형제 `.vdlu-tmp`에 쓰고, `chmod`하고, 해시를 검증한 다음, 대상 위로 원자적 `rename`을 합니다. 이미 대상 해시인 파일은 건너뜁니다.
- `reboot` 파일(`.so`, `/system` 오버레이, `sepolicy.rule`): `staged/<path>.vdlu-new`로 구체화합니다. 라이브 inode는 여기서 절대 건드리지 않습니다. [[Reboot Handling]] 참조.
- 삭제: 백업한 뒤 제거합니다. 삭제는 깨끗한 `DONE`에서 맨 마지막에만 적용되며, 재부팅이 아직 보류 중인 동안에는 절대 적용되지 않습니다.

**COMMIT.** 엔진은 건드린 모든 live 및 soft 파일을 재해시합니다. 모두 일치할 때만 `current.json`을 써서 새 버전을 diff 기준으로 만듭니다. reboot 클래스 파일이 스테이징되었다면 상태는 `DONE` 대신 `PENDING_REBOOT`가 됩니다. 교체와 최종 재검증은 나중에 `boot` 명령 아래에서 이루어집니다.

## 구성으로 보장되는 fail-safe

무인으로 실행해도 안전하게 만드는 보장:

- **일치하는 재해시 없이는 어떤 것도 `DONE`으로 표시되지 않음.** `DONE`은 적용된 모든 파일을 다시 읽어 그 SHA-256을 매니페스트와 비교한 뒤에만 도달합니다. 스테이징된 reboot 파일은 가짜 `DONE`이 아니라 `PENDING_REBOOT`를 강제합니다.
- **어떤 것도 잃어버리지 않음.** 모든 파일은 덮어쓰이기 전에 `rollback/<version>/`에 백업되고, 최근 세 개 버전이 보관됩니다. 적용이 실패하면 라이브 파일은 백업에서 되돌려집니다. 모듈은 완료된 척하며 절반만 적용된 채로 절대 남겨지지 않습니다. `apply_live`는 백업 단계가 실패하면 되돌릴 길 없이 덮어쓰는 대신 즉시 중단합니다.
- **모든 것이 원자적.** 새 콘텐츠는 대상 위로 `rename`/`mv`를 거쳐 안착하므로, 읽는 쪽은 잘린 쓰기가 아니라 언제나 옛 파일이나 새 파일 중 하나를 봅니다.
- **크래시나 종료 이후 재개 가능.** 크래시, 끊긴 네트워크, 또는 도중의 재부팅은 유효한 저널을 남깁니다. `resume`(또는 `boot`)이 기록된 단계에서 이어집니다. 설계는 중단될 것을 전제합니다.
- **깨끗하게 저하됨.** 빠진 바이너리, 끊긴 네트워크, 또는 꽉 찬 디스크는 모듈을 손상시키지 않고 stderr에 명확한 오류와 저널에 `state:ERROR`를 냅니다.

## 잠금

한 번에 하나의 트랜잭션만 상태를 건드릴 수 있습니다. `flock`은 toybox에서 신뢰할 수 없으므로, VDLU는 디렉터리 잠금으로 직렬화합니다: `mkdir "$VDLU_DIR/lock.d"`는 정확히 한 호출자에게만 성공하고 나머지에게는 실패하며, 이는 멀쩡한 어떤 파일시스템에서도 원자적입니다. 죽은 프로세스가 남긴 오래된 잠금은 기록된 PID를 확인하여 복구됩니다.

인내심 있는 부팅 시 재시도(기기가 부팅 시 오프라인일 때 사용됨)는 기다리는 동안 이 잠금을 **쥐고 있지 않습니다**. 시도 사이에 획득하고 해제하므로, 네트워크를 기다리는 부팅 때문에 수동 `run`이 절대 막히지 않고, wakelock도 절대 쥐지 않습니다. 설계상 배터리에 안전합니다. 이에 대한 더 자세한 내용은 [[Reboot Handling]]에 있습니다.

## 서명 검사: `vdlu-verify`

`vdlu-verify`는 의도적으로 가볍게 유지된 기기 내 서명 검사기입니다:

```
vdlu-verify <manifest.json> <keyring_dir>
```

종료 `0`은 매니페스트의 서명이 매니페스트의 `key_id`와 일치하는 id를 가진 keyring 공개 키에 대해 유효함을 뜻합니다. 그 외의 코드는 거부입니다.

가볍게 만드는 요인은 **기기에 `openssl`을 전혀 사용하지 않는다**는 것입니다. keyring 공개 키를 **원시 32바이트** 파일로 읽고, 매니페스트를 정규화하고(`sig` 필드를 제거한 매니페스트 텍스트), toybox `sha256sum`으로 해시하고, 서명을 base64 디코드한 다음, 원시 키, 메시지, 64바이트 서명을 내장된 `ed25519-mini` 바이너리에 넘깁니다. 검사기는 또한 검증하기 전에 잘못된 것은 무엇이든 거부합니다: 빠졌거나 비어 있는 `key_id` 또는 `sig`, 경로 구분자를 포함한 `key_id`, 정확히 32바이트가 아닌 공개 키, 또는 정확히 64바이트가 아닌 서명.

정규화는 producer의 서명기와 바이트 단위로 동일하며, 바로 이것이 도구들을 넘나들며 서명이 검증되게 하는 요인입니다. 일치하는 개인 키는 기기나 CI에 절대 닿지 않습니다. 오직 원시 공개 키만 내장됩니다. 전체 신뢰 이야기, 두 프로필, 그리고 `hardened`가 왜 반전에 의해 fail-closed인지는 [[Security and Trust Model]]에 있습니다.

엔진은 diff 단계에서 `vdlu-verify`를 호출합니다. `hardened` 프로필에서는 검증 실패가 업데이트 전체를 중단시킵니다. `trusted`에서는 검증이 best-effort이지만, 모든 블롭의 해시는 여전히 항상 확인되므로 손상된 콘텐츠는 프로필과 무관하게 잡힙니다.

## 디스크 상의 상태

엔진의 모든 상태는 `$VDLU_DIR`(모듈 디렉터리 밖)에 있으므로, 모듈 트리 자체는 언제나 완성된 파일만 담습니다:

| 경로 | 역할 |
|---|---|
| `config` | key=value 설정(source, profile, channel, 네트워크 정책, 부팅 재시도) |
| `current.json` | 활성 버전의 매니페스트, 이것이 diff 기준. 없으면 한 번도 업데이트되지 않은 것 |
| `target.json` | 진행 중인 트랜잭션의 고정된 매니페스트. 존재 자체가 활성 트랜잭션을 표시하며, `DONE`에서 `current.json`이 됨 |
| `plan.tsv` / `plan.del` | 파일별 계획과 진행 상황, 그리고 삭제할 경로 목록 |
| `journal.json` | WebUI용 진행 상황, 상태가 바뀔 때마다 다시 쓰임 |
| `blobs/<sha256>` | 검증되고 압축 해제된 원본 콘텐츠의 캐시 |
| `rollback/<version>/<path>` | 덮어쓰인 파일의 백업, 최근 세 개 버전이 보관됨 |
| `staged/<path>.vdlu-new` | 부팅 교체를 기다리는 reboot 클래스 파일 |
| `lock.d/` | mkdir 잠금 |
| `tools/<abi>/curl` | 가져와 검증된 정적 curl, 업데이트를 넘어 지속됨 |
| `cancel` | 취소 요청 |

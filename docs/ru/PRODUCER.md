# Слой producer + подписи VDLU

Строит адресуемую по содержимому доставку (манифест + блобы) для модуля и подписывает её.
Соответствует [`INTERFACES.md`](INTERFACES.md) §3/§6/§7.

| инструмент | работает на | язык | задача |
|---|---|---|---|
| `producer/vdlu-pack` | ПК / CI | python3 | обход финального дерева модуля -> `manifest.json` + `blobs/` |
| `producer/vdlu-keygen` | ПК | sh + openssl | пара ключей ed25519 (`<id>.pem` priv, `<id>.pub` PEM, `<id>.pub.raw` RAW 32B для компактного keyring) |
| `producer/vdlu-sign` | ПК | sh + openssl | внедрить `key_id` + `sig` в манифест, in place |
| `engine/vdlu-verify` | **устройство** | sh + ed25519-mini | проверить `sig` через встроенный ed25519-mini; keyring = pubkey RAW 32B (БЕЗ openssl на устройстве) |

## Конвейер

```sh
# 1. однократно: ключ подписи. Держите .pem вне каждого устройства и вне любого push в репозиторий.
producer/vdlu-keygen release-2026 ./keys

# 2. каждый релиз: упакуйте финальное дерево (то же дерево, что поставляет .zip, после whitelist).
producer/vdlu-pack  ./module_tree  ./out  demo 106 --version-name v106 --channel stable \
                    [--prev ./prev/manifest.json]      # delete[] = пути, исчезнувшие с prev

# 3. подпишите манифест in place.
producer/vdlu-sign  ./out/manifest.json  ./keys/release-2026.pem  release-2026

# 4. опубликуйте ./out/{manifest.json,blobs/} в <source> (batch Pages для публичного; rsync для приватного).
#    Компактный keyring устройства хранит ./keys/release-2026.pub.raw как keyring/release-2026.pub (RAW 32B).
```

`vdlu-pack` адресуем по содержимому и дедуплицирует: блоб, чей `<sha256>` уже существует, не
переписывается, поэтому публикация инкрементальна, а неизменное / откаченное содержимое никогда не пере-отправляется.

### Решение `enc` (vdlu-pack)

`sha256` **всегда** от оригинального (несжатого) содержимого; `enc` только называет, как блоб хранится.

- `gz`, когда `size >= 4096` **и** gzip (`-9 -n`, детерминированный) экономит минимум 10% (`comp <= raw*0.90`).
- `raw` иначе (маленький текст, который HTTP gzip уже покрывает, или уже-несжимаемые данные).
- gzip отсутствует на хосте сборки -> всё `raw` (никогда не падает).

Блоб хранится один раз, в одном формате: `blobs/<sha256>` (raw) или `blobs/<sha256>.gz` (gz). Устройство
распаковывает через toybox `gunzip` (всегда присутствует), поэтому zstd не поставляется.

### Решение `class` (vdlu-pack) - таксономия reboot

Выводится из path (INTERFACES §3, doc §4). Только дефолты; правило path никогда не понижает `reboot`->`live`.

| class | сопоставляется | применяется |
|---|---|---|
| `reboot` | `system/**`, `zygisk/**/*.so`, `*.rule` | инсценирован `.vdlu-new`, swap при загрузке |
| `soft` | корневые `service.sh` / `post-fs-data.sh` / `boot-completed.sh` | записан live, запускается при следующей загрузке |
| `live` | всё остальное (webroot, bin, lib, confs, module.prop, ...) | записан live, атомарно |

Симлинки **не отслеживаются** (никогда не утекает содержимое извне дерева, напр. ссылка на
`/etc/shadow`) и пропускаются с предупреждением, так как схема манифеста не имеет типа симлинк.
Нерегулярные файлы (каталоги, fifo, устройства) пропускаются. `built` уважает `SOURCE_DATE_EPOCH` для
воспроизводимых манифестов.

### Baseline (семя установки) - без подписи, без ключа

`baseline.json` (поставляется по `vdlu/baseline.json` в zip модуля) сеет `current.json` при чистой установке,
чтобы устройство рождалось "актуальным" (без from:0, без повторной загрузки). Engine рассматривает его как **локальное доверенное семя**
(оно прибыло в прошитом zip, который является границей доверия установки) и **НЕ проверяет его подпись** -
только манифест, ЗАГРУЖЕННЫЙ из фида, проходит через `vdlu-verify`. Поэтому baseline не нужен **ключ**: это
просто вывод `vdlu-pack` над поставляемым деревом (без подписи; `sig`/`key_id` остаются пустыми). CI может поэтому
генерировать его **без ключа**, держа ключ подписи на 100% вне CI - только опубликованный ФИД подписывается (оператор,
локально). `vdlu-pack` исключает `baseline.json` из собственного манифеста (анти самоссылка). Не фатально, если
отсутствует: устройство просто начинает с from:0 при первом обновлении, никогда не сломано.

## Канонизация (точка сходимости)

`vdlu-sign` и `engine/vdlu-verify` должны выводить **одни и те же байты** из манифеста, на двух
разных рантаймах (openssl на ПК vs toybox + openssl на устройстве). Правило намеренно является байтовым
преобразованием, а не ре-сериализацией JSON, поэтому ему не нужна библиотека JSON на устройстве:

1. `vdlu-pack` пишет `manifest.json` **компактный, ключи отсортированы, UTF-8**
   (`json.dumps(obj, sort_keys=True, separators=(",",":"), ensure_ascii=False)`), всегда включая
   поля `key_id` и `sig` (плейсхолдеры в виде пустой строки до подписи). Это каноническая
   форма хранения.
2. **Каноническая форма = тот текст с удалённым полем `"sig"`.** Поскольку ключи отсортированы, `sig`
   всегда появляется как `,"sig":"<value>",` в окружении `"schema"` (до) и `"version"` (после),
   оба всегда присутствуют. Его удаление оставляет корректный `...,"schema":N,"version":...`.
   JSON экранирует каждую `"` внутри строковых значений в `\"`, поэтому структурный токен `"sig":"`
   однозначен даже против имени файла, буквально содержащего `"sig":"` (протестировано).
3. Подписанное/проверяемое сообщение это **hex sha256** (64 ASCII-символа, без newline) канонической
   формы. ed25519 над этим hex (`openssl pkeyutl -sign/-verify -rawin`).

Удаление в POSIX sh (идентичная функция в обоих инструментах, без `sed`/`jq`):

```sh
# $1 = полный текст манифеста (завершающий newline уже удалён $(cat ...))
_pre=${_c%%\"sig\":\"*}     # до  ...,"schema":N,
_rest=${_c#*\"sig\":\"}      # после "sig":"
_tail=${_rest#*\",}          # после <value>",  ->  "version":...
printf '%s%s' "$_pre" "$_tail" | sha256sum | cut -d' ' -f1
```

`key_id` является частью канонической формы (удаляется только `sig`); `vdlu-sign` устанавливает `key_id` **до**
хэширования. Плейсхолдер значения, будучи пустым (`"sig":""`, время подписи) или заполненным (время проверки), даёт
идентичные канонические байты, поэтому sign и verify согласуются по построению.

Python воспроизводит это как `re.sub(r'"sig":"[^"]*",', '', text.rstrip("\\n"), count=1)`, затем sha256 - используется
только для перекрёстной проверки; авторитетные производители это два sh-инструмента.

## Подпись (ed25519)

- `vdlu-keygen` (ПК): `openssl genpkey -algorithm ed25519` (priv `0600`) + `openssl pkey -pubout` (pub **PEM**,
  для подписи/openssl) + `openssl pkey -pubout -outform DER | tail -c 32` -> **`.pub.raw` (RAW 32B)** (ed25519
  SPKI DER это 12-байтовый префикс + 32-байтовый ключ, поэтому `tail -c 32` ЕСТЬ ключ). Выдаёт ОБА.
- `vdlu-sign` (ПК): `openssl pkeyutl -sign -rawin` над каноническим sha256 hex; подпись хранится в base64.
- `vdlu-verify` (**устройство, компактный**): `ed25519-mini <pubkey32> <msg> <sig64>` - читает keyring как pubkey **RAW 32B**,
  БЕЗ openssl на устройстве. `key_id` санируется по path (без `/`, `.`, `..`, `"`). 🚨 Keyring поставляет
  **`.pub.raw` (32B)**, никогда `.pub` PEM (113B): PEM только на стороне ПК, и `ed25519-mini` не может его прочитать.

Модель доверия (INTERFACES §6, doc §11/§13): `profile=hardened` (публичный) делает verify обязательным - сбойная
или отсутствующая подпись прерывает обновление. `profile=trusted` (приватный, источник staged через SSH) рассматривает
verify по возможности, но sha256 каждого блоба проверяется в любом случае.

## Keyring + ротация

Keyring это каталог файлов `<key_id>.pub`, каждый из которых pubkey ed25519 **RAW 32B** (из
`.pub.raw` от `keygen`), НЕ PEM - `ed25519-mini` читает сырые 32 байта. Поставляйте текущий **и** предыдущий
сырой pubkey (doc §13), чтобы ротированный ключ не ломал старые установки. `vdlu-sign` с новым `key_id` и устройство,
выбирающее `<keyring>/<key_id>.pub` (сырой), это весь механизм ротации - без изменения engine. Keyring
**стабилен** между релизами (его меняет только ротация ключа): пере-вендоринг должен **проверять-не-копировать** и никогда
не перезаписывать его PEM-файлом `.pub` со стороны ПК.

# Політика безпеки та модель довіри

VDLiveUpdate (VDLU) застосовує **flashless root-оновлення** до живого модуля: воно пише в
`/data/adb/modules/<mod>` і обмінює Zygisk `.so` під час boot. Кожне поле завантаженого маніфесту
(`path`, `sha256`, `delete[]`, `mode`, ...) є **ворожим входом** - отруєна стрічка чи MITM його доставляє.
Ця сторінка - модель довіри та політика відповідального розкриття. Щодо повного seam-контракту див.
[`INTERFACES.md`](INTERFACES.md), а внутрішню будову engine/producer - у [`ENGINE.md`](ENGINE.md) та
[`PRODUCER.md`](PRODUCER.md); вікі-сторінка **Security-and-Trust-Model** несе ту саму модель для читачів
поза repo.

## Підтримувані версії

Виправлення безпеки потрапляють у найновіший `ENGINE_VERSION`; підписаний маніфест оголошує мінімальний
engine, який йому потрібен, через `engine_min`, а engine на пристрої відхиляє маніфест, що просить більше,
ніж він реалізує. Від старіших vendor-ованих engine очікується **повторна вендоризація** задля отримання
виправлення, а не back-patch на місці.

| ENGINE_VERSION | статус |
|---|---|
| 4 (поточний) | підтримується - allowlist `key_id`, відхилення path з dot-segment/trailing-slash, обмеження розміру, check-time lock |
| 3 | замінений - `hardened` за замовчуванням, fail-closed `profile` через інверсію, прив'язка module/MODID, блок downgrade |
| <= 2 | не підтримується - повторно вендоризуйте поточний engine |

Будь-яка зміна у verify engine чи logic apply піднімає `ENGINE_VERSION`.

## Модель довіри

- **Detached-підписи ed25519.** Producer підписує канонічний маніфест на ПК (openssl); пристрій перевіряє
  вбудованим `ed25519-mini` - **без openssl на пристрої**. Підписане повідомлення - це sha256 hex маніфесту
  без його поля `sig` (ключі відсортовані, compact, UTF-8), тож sign і verify виводять ті самі байти на двох
  середовищах виконання без JSON-бібліотеки на пристрої.
- **Keyring = RAW 32-байтові публічні ключі**, лише flash. Keyring пристрою відвантажує `<key_id>.pub` як
  сирий 32-байтовий ключ (ніколи PEM); `vdlu-pack` **виключає** keyring і бінарники `verify/` зі стрічки, тож
  маніфест ніколи не може переписати якір довіри на пристрої по мережі.
- **Allowlist `key_id` для module-update (fail-closed, перед вибором pubkey).** Keyring може законно нести
  більш ніж один ключ (наприклад, ключ fingerprint-feed нижчої довіри поруч із release-ключем). Перш ніж
  `<key_id>.pub` узагалі буде обрано, `verify_manifest` відхиляє будь-який маніфест, чий `key_id` не входить
  до налаштованої allowlist, в **обох** profiles, і віддзеркалює розв'язану множину в `vdlu-verify` через
  `VDLU_KEYID_ALLOW`. Це закриває bypass, за якого витік ключа нижчої довіри міг би інакше підписати повне
  flashless root-оновлення. Безпечно за замовчуванням, коли `key_id` невстановлено: keyring з **одним ключем**
  авто-закріплюється на той єдиний ключ; **багатоключовий** keyring відхиляється, доки `key_id` не закріплено
  (через кому для ротації).
- **Корінь довіри fingerprint-feed - окремий, закріплений path** зі власним ключем; він ніколи не досяжний
  через шлях module-update вище.
- **Baseline - це локальне довірене насіння.** `baseline.json` прибуває всередині прошитого zip - межа довіри
  установки - тож воно непідписане й без ключа і **не** проганяється через `vdlu-verify`; перевіряється лише
  маніфест, **завантажений** зі стрічки. Це тримає ключ підпису поза CI.

## Гарантії fail-closed

- **`validate_plan` виконується перед будь-яким fetch чи apply.** У `do_diff`, fail-closed, воно відхиляє
  **весь** маніфест, якщо будь-який `path` є absolute, містить сегмент `..` чи `.`, закінчується на `/` або
  містить control-символ; якщо будь-який `sha256` не відповідає `^[0-9a-f]{64}$`; або якщо будь-який
  `mode`/`class`/`enc` недійсний. Жодне ворожe поле не досягає shell, і `cmd_check` не несе інтерполяції
  `system()`.
- **Контейнмент path.** Кожен запис і видалення обмежені `MODULE_DIR` через `contained()` - apply, delete і
  reboot-овий `stage_file` усі проходять одну й ту саму перевірку. Символьні посилання в дереві пропускаються
  producer-ом (ніколи не витікає вміст ззовні нього).
- **Два profiles, fail-closed через інверсію.** `trusted` (приватний, SSH-стейджене джерело) - **єдиний**
  opt-in до best-effort verify; **будь-яке** інше значення - включно з опискою, trailing пробілом/CR чи іншим
  регістром - трактується як `hardened`, де дійсний підпис є **обов'язковим**, а збій перериває. `sha256`
  кожного блоба перевіряється в обох profiles.
- **Підпис + геш перед будь-яким exec інструмента.** Завантажений статичний `curl` виконується як root, тож
  `install-tool` перевіряє підпис tools-manifest (ed25519-mini, обов'язковий у **будь-якому** profile) і геш
  curl **перед** тим, як його встановлено й виконано - sig+hash перед exec закриває RCE.
- **Поновлювана, pin-безпечна транзакція.** Маніфест у польоті закріплений у `target.json`; крах, втрата
  мережі чи reboot поновлюються з журналу без переобдумування плану. Downgrade заблоковано (монотонна
  `version`), підписане поле `module` мусить дорівнювати `MODID`, а `delete[]` виконується лише на
  `finalize_done` (`PENDING_REBOOT` нічого не видаляє). Ніщо ніколи не є "готовим" без повного re-hash; ніщо
  не перезаписується без попередньої резервної копії `rollback/<v>/`.

## Hardening (ешелонована оборона)

- **Обмеження розміру.** Маніфест, tools-manifest і path завантаження через `wget`/`head -c` без curl усі
  обмежені перед читанням (anti-OOM / anti-flood). Блоб зазнає невдачі у своїй фазі після 3 спроб.
- **Check-time lock.** `check` бере mkdir-lock перед перебудовою свого work dir, тож одночасний запуск не може
  з ним змагатися.
- **Контейнмент staging.** `stage_file` має ту саму перевірку `contained()`, що й примітиви живого apply, тож
  застейджений reboot-hard path теж не може вийти за межі `MODULE_DIR`.
- **TLS - це ешелонована оборона, а не корінь довіри.** Статичний curl використовує mbedTLS із trust store
  Android (`--capath`, override через `ca_path`); гарантією цілісності є підпис ed25519, перевірка сертифіката
  - другий шар.
